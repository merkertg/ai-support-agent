# Обновление Python-зависимостей

Эта инструкция описывает отдельный workflow
[Update Python dependencies](../.github/workflows/dependency-updates.yml).
Он готовит обновление в pull request (PR), запускает проверку и оставляет
решение о слиянии человеку. Основной [CI and GHCR](CI_CD.md) продолжает
проверять каждый push в `main` и PR.

## Что обновляется

Обновляются два файла:

- `pyproject.toml`: только дата `[tool.uv] exclude-newer`;
- `uv.lock`: версии, зависимости, даты публикации и hashes пакетов,
  выбранных `uv lock --upgrade` в пределах существующих ограничений проекта.

Например, 19 октября 2026 года новая граница — `2026-10-05T00:00:00Z`.
Пакет, опубликованный 6 октября, не попадёт в обновление. Выбор полуночи UTC
оставляет не менее четырнадцати полных суток до любого момента дня запуска.
Дополнительно [check_dependency_age.py](../scripts/check_dependency_age.py)
проверяет реальные `upload-time` в lock: одной правильной даты настройки
для прохождения проверки недостаточно.

Точные ограничения сохраняются. Сейчас `streamlit==1.65.0` не обновится
до следующей версии автоматически, а `langgraph>=1.2.12,<1.3` останется в
ветке 1.2. Для пересмотра таких ограничений нужна отдельная PR с объяснением,
проверкой документации соответствующего инструмента и полным CI.

Этот workflow не обновляет Python, uv, GitHub Actions и Docker-образы.
Их версии/SHA/digest пересматриваются отдельно. Подмена digest движущимся
тегом запрещена проверкой `tests/test_image_pins.py`.

## Когда он запускается

Расписание: каждый понедельник в **06:17 UTC / 11:17 в Ташкенте**.
GitHub может запустить scheduled workflow с задержкой; это не точный таймер.
Расписание начинает действовать после попадания workflow в default branch.

Для ручного запуска: GitHub → Actions → **Update Python dependencies** →
**Run workflow**, ветка `main`.

Установка расписания не означает, что удалённое обновление уже выполнялось.
Первый реальный запуск и настройки разрешений проверяются в GitHub Actions.

## Как проходит подготовка

Задание `prepare` имеет только `contents: read`:

1. Получает конкретный SHA доверенной `main`, без сохранения git-учётных данных.
2. Устанавливает закреплённый uv 0.12.23 и Python 3.12.
3. Запускает стандартным Python
   [update_dependencies.py](../scripts/update_dependencies.py) в режиме `prepare`.
4. Меняет только дату `exclude-newer`, сохраняя остальные настройки и комментарии.
5. Выполняет `uv lock --upgrade --no-build`.
6. Проверяет возраст всех пакетов и передаёт два файла в артефакте сроком на сутки.

`--no-build` запрещает запуск backend сборки пакета при разрешении зависимостей.
Если для получения metadata нужна сборка исходников, обновление завершится
ошибкой и потребует отдельного разбора. Runtime-пакеты и их код на этом шаге
не устанавливаются. Write-токена в задании подготовки нет.

Обновление берётся из `main`, а не из существующей bot-ветки. Workflow
отклоняет запуск из fork и ручной запуск с другой ветки.

## Как создаётся PR

Задание `publish` имеет `contents: write`, `pull-requests: write`,
`actions: write`. Оно:

1. Получает тот же доверенный SHA `main`. Код из PR не выполняется с write-токеном.
2. Читает артефакт и требует ровно два обычных файла; отклоняет symlink,
   посторонние файлы и файлы больше 10 MB.
3. Сверяет `pyproject.toml` с доверенной версией: разрешена только дата границы.
4. Отклоняет git/path/неожиданные package registry в lock и повторяет age check.
5. Проверяет, что `main` не изменилась после начала подготовки. При изменении
   останавливается с просьбой повторить workflow.
6. Через GitHub API создаёт commit с родителем из `main` и только двумя файлами.
7. Создаёт либо обновляет одну ветку `automation/python-dependencies` и одну PR.
8. Явно запускает **CI and GHCR** через `workflow_dispatch` для этой ветки.

Ветка `automation/python-dependencies` зарезервирована для автоматики и
пересоздаётся от актуальной `main`. Не вносите туда ручные изменения:
следующий запуск может их заменить. Пользовательские ветки и `main` скрипт
не перезаписывает. Если оба файла уже совпадают с `main`, PR и лишний CI
не создаются.

Запросы writer идут только на `api.github.com` по HTTPS, с timeout 30 секунд.
Редиректы отклоняются: заголовок Authorization не пересылается на другой адрес.
Ответ читается с ограничением 2 MB; токен и тело HTTP-ошибки в журнал не выводятся.

Новый PAT или GitHub App не нужен. Достаточно встроенного `GITHUB_TOKEN`.
Явный `workflow_dispatch` нужен, чтобы проверка не зависела от поведения PR,
созданной токеном Actions: GitHub может оставить её pull_request-запуски
в ожидании ручного разрешения. `workflow_dispatch` запускает обычные проверки
для того же commit. Публикация API/UI в GHCR при этом не выполняется: она
ограничена разрешёнными push в `main` и релизными тегами.

Если подготовка и публикация пересекли полночь UTC, проверка даты может
отклонить предложение предыдущего дня. Повторный запуск создаст согласованную
пару файлов с новой датой; ослаблять age check не нужно.

## Что сделать после появления PR

1. Открыть diff: должны изменяться только дата `exclude-newer` и `uv.lock`.
2. Посмотреть версии обновлённых пакетов и release notes существенных обновлений.
3. Дождаться Python checks, dependency audit, сборки и smoke-проверки API/UI,
   сканирования образов. Отдельный dispatch виден в Actions для bot-ветки.
4. Если GitHub показывает **Approve workflows to run**, разрешить PR-проверки
   после просмотра diff. Не включать автослияние для обхода этой проверки.
5. После успешных проверок слить PR обычным способом. Push в `main` запускает
   полный CI/CD и публикацию проверенных образов.

Скрипт не одобряет и не сливает PR. Наличие PR или успешный job `prepare`
не заменяют полный CI и review.

## Если GitHub отказал в создании PR

В Settings → Actions → General → Workflow permissions проверьте разрешение
**Allow GitHub Actions to create and approve pull requests**. Название настройки
включает approval, однако наш скрипт PR не одобряет. Политика организации может
запрещать изменение настройки — тогда решение принимает администратор.

Без разрешения запись PR вернёт HTTP 403; workflow останется failed.
Скрипт не подставляет PAT и не ослабляет правила. Bot-ветка к этому моменту
может уже существовать: после исправления настройки повторный запуск
использует её повторно. При необходимости PR можно создать вручную из
`automation/python-dependencies` в `main` и дождаться её CI.

| Ошибка | Следующее действие |
| --- | --- |
| Пакет моложе 14 дней | Проверить границу/metadata; дождаться допуска либо выбрать более старую совместимую версию. |
| Для metadata нужна сборка | Отдельно проверить источник и способ обновления; не убирать `--no-build` из writer. |
| `main изменилась после подготовки` | Повторить workflow на актуальной `main`. |
| `HTTP 403` при PR | Проверить настройки Actions и политику организации. |
| Ошибка резолвера | Изучить конфликт диапазонов; менять ограничения отдельной осмысленной PR. |
| Ошибка CI/аудита/Trivy | Исправить обновление или закрыть PR; не сливать с failed-проверкой. |

## Локальная проверка без PR

Следующая команда меняет локальные `pyproject.toml` и `uv.lock`, но не
обращается к GitHub для записи. Выполняйте её в отдельной рабочей ветке:

```bash
uv run --no-project --python 3.12 python scripts/update_dependencies.py prepare
uv sync --locked
uv run --locked python scripts/check_dependency_age.py --min-age-days 14
uv run --locked ruff check .
uv run --locked ruff format --check .
```

Интеграционные тесты и контейнерный smoke запускаются по
[инструкции полной проверки](VERIFICATION.md); им нужны изолированные PostgreSQL
и Qdrant. Не направляйте `TEST_DATABASE_URL` в рабочую БД.

`publish` предназначен для отдельного writer-job GitHub Actions. Не передавайте
токен в аргументе командной строки и не вставляйте его в чат или документацию.

## Почему выбран uv 0.12.23

Релиз uv 0.13.1 опубликован 14.10.2026 и на дату проверки 18.10.2026 ещё
моложе четырнадцати дней. uv 0.12.23 опубликован **03.10.2026**;
проверены metadata PyPI и реальный Docker index, дата создания которого —
`2026-10-03T16:57:06.978Z`.

Dockerfile использует в обеих builder-стадиях:

```text
ghcr.io/astral-sh/uv:0.12.23@sha256:61d393e44e249f2e4b526b6c7ddcecce245946826e608e11c93ad4f5bba55b21
```

Это digest многоархитектурного индекса, содержащего Linux amd64 и arm64.
Он получен командой `docker buildx imagetools inspect`, а не рассчитан из тега.

На временной копии актуального проекта с coverage-зависимостями проверены:

- `uv lock --check --offline`: читает lock на 100 записей без изменения;
- `uv export --locked --offline --no-dev --group ui --no-emit-project`;
- `uv sync --locked --offline --no-dev`: 69 API-пакетов;
- `uv sync --locked --offline --only-group ui`: 37 UI-пакетов;
- равенство lock-файла до и после проверки побайтово;
- импорты FastAPI, OpenAI, SQLAlchemy, Streamlit и httpx в раздельных окружениях.

Подготовка обновления дополнительно исполнена на временной копии:
`uv lock --upgrade --no-build` разрешил 100 записей, age check проверил
99 пакетов PyPI; итоговый lock совпал с исходным побайтово. Удалённые PR
и запуск workflow для этой проверки не создавались.

Новые runtime-запросы OpenAI для этих проверок не выполнялись.
Внутренний uv из wheel macOS arm64 загружен с PyPI с проверкой SHA256:
`99197c022afbd1edd0a295e9fdac5078c61eddf2e77657a77294cfe8ea0d94b9`.
Python/uv в GitHub Actions и Linux-сборки дополнительно проверяются обычным CI.
