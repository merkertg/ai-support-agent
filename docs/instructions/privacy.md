# Персональные данные: обезличивание и срок хранения

[← README](../../README.md) · [All documentation](../../README.md#documentation) · [Using the API](usage.md) · [Резервные копии](backup.md) · [Windows](windows.md)

В проекте два способа удалить персональные данные клиентов:

1. **Обезличивание клиента по его запросу.** Администратор вводит текущий
   email клиента: имя, email и компания заменяются заглушками, а тексты всех его
   обращений, сообщений, запусков агента и решений удаляются. Это делается в
   интерфейсе, через API или командой.
2. **Срок хранения закрытых обращений.** Команда находит закрытые обращения,
   которые не менялись дольше заданного срока, и удаляет их тексты. Без флага
   `--apply` она только показывает план.

Оба действия необратимы. Резервные копии, сделанные раньше, данные по-прежнему
содержат — см. [ограничения](#ограничения).

## Где лежат персональные данные и что с ними происходит

| Где | Что там было | После обезличивания |
| --- | --- | --- |
| `customers` | Имя, email, компания | `Клиент удалён`, `erased-<id>@erased.invalid`, компания пустая, `erased_at` — время |
| `tickets` | Тема и описание | `Обращение обезличено` и `[удалено]`; статус `closed` (решённое остаётся `resolved`); `anonymized_at` и `anonymized_reason` |
| `ticket_messages` | Текст сообщений, включая доставленный ответ | `[удалено]`; автор, сотрудник и время остаются |
| `agent_runs` | Аргументы и результаты инструментов (тема, описание, имя и email клиента), текст итога | Остаются только имена вызовов, категория итога, ключи статей базы знаний, шаги и токены |
| `agent_suggestions` | Черновик, одобренный текст, комментарий решения | `[удалено]`; статус, рецензент и время решения остаются |
| `checkpoint_*` (LangGraph) | Решение сотрудника с текстом правки и комментарием | Потоки удаляются целиком; `GET /api/agent-runs/{id}/workflow` восстанавливает итог (`delivered`/`rejected`) по фактам БД, уже без текстов |

Что остаётся и почему:

- **Лицензии** клиента: это учёт продукта. Ключ лицензии без имени и email на
  человека не указывает; API и интерфейс и так его не показывают.
- **Продукты, статусы, приоритеты и даты**: на них строятся показатели панели.
- **Статьи базы знаний** в Qdrant: там нет данных клиентов.
- **Сотрудники** (`users`) этим механизмом не обезличиваются: доступ сотрудника
  закрывается отзывом токенов и деактивацией.

## Обезличить клиента по запросу

Нужен токен роли `admin`. Сервер откажет (409), пока по какому-нибудь обращению
клиента идёт анализ или предложение агента ждёт решения: сначала одобрите или
отклоните его в очереди проверки. Иначе незавершённая работа снова записала бы
текст.

После обезличивания клиенту нельзя создать обращение или лицензию (409), а его
обращениям — сменить статус или запустить анализ (409).

### В интерфейсе

1. Войдите токеном администратора.
2. Откройте **Справочники → Клиенты** и найдите ID клиента в таблице.
3. Раскройте **Обезличить клиента по запросу**, введите ID и текущий email
   клиента, отметьте **Понимаю, что восстановить данные нельзя** и нажмите
   **Обезличить клиента**.
4. Интерфейс покажет, сколько обращений, сообщений, запусков и предложений
   обезличено и сколько лицензий сохранено. В таблице клиентов появится
   время в колонке `erased_at`.

Сотрудники с ролями `operator` и `reviewer` форму не видят.

### Через API

```bash
auth="Authorization: Bearer $API_TOKEN"
curl --silent --show-error --fail-with-body --request POST --header "$auth" \
  --header 'Content-Type: application/json' \
  --data '{"confirm_email":"anna@example.com"}' \
  http://127.0.0.1:8001/api/customers/5/erase
```

В PowerShell на Windows ([аналоги команд](windows.md)):

```powershell
$auth = @{ Authorization = "Bearer $env:API_TOKEN" }
$body = @{ confirm_email = 'anna@example.com' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Headers $auth -ContentType 'application/json; charset=utf-8' `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($body)) `
  http://127.0.0.1:8001/api/customers/5/erase
```

Ответ содержит только номера и счётчики:

```json
{
  "tickets": 3,
  "messages": 1,
  "agent_runs": 2,
  "suggestions": 2,
  "workflow_threads": 2,
  "customer_id": 5,
  "erased_at": "2026-10-19T09:30:00Z",
  "licenses_kept": 1
}
```

| Код | Когда |
| --- | --- |
| 200 | Клиент обезличен |
| 401 / 403 | Нет токена или роль ниже `admin` |
| 404 | Клиента с таким ID нет |
| 409 | Клиент уже обезличен; или у обращения N идёт анализ (запуск M); или предложение M ждёт решения |
| 422 | Email не совпадает с email клиента (сравнение без учёта регистра) или тело запроса неверное |

### Командой на сервере

Команда делает то же, что и API, и нужна, например, после восстановления
старой копии (см. ниже). Она печатает тот же JSON-отчёт:

```bash
docker compose exec -T api python -m app.privacy erase \
  --customer-id 5 --confirm-email anna@example.com
```

## Срок хранения закрытых обращений

Команда `retention` обезличивает обращения в статусе `resolved` или `closed`,
которые не менялись дольше `--older-than-days` дней (по `updated_at`). Клиента
она не трогает: имя и email удаляет только явный запрос. Обращения с
незавершённым анализом или предложением на проверке пропускаются с причиной.

Сначала посмотрите план — данные не меняются:

```bash
docker compose exec -T api python -m app.privacy retention --older-than-days 365
```

Если список подходит, выполните то же с `--apply`:

```bash
docker compose exec -T api python -m app.privacy retention --older-than-days 365 --apply
```

В PowerShell команды те же:

```powershell
docker compose exec -T api python -m app.privacy retention --older-than-days 365
docker compose exec -T api python -m app.privacy retention --older-than-days 365 --apply
```

Отчёт содержит `ticket_ids` (обезличенные или, в плане, подходящие обращения),
`skipped` с причинами и счётчики. Ограничения команды:

- срок не меньше **30 дней** — защита от опечатки вроде `--older-than-days 3`;
- за один запуск не больше `--limit` обращений (по умолчанию 500, максимум 1000);
  остальные обработает следующий запуск;
- обращение, с которым в этот момент работают, пропускается без ожидания и
  попадёт в следующий запуск.

Срок хранения выбирает владелец данных. Команду удобно запускать по расписанию
из папки проекта, например раз в неделю через cron (Linux, macOS):

```text
30 3 * * 1  cd /srv/ai-support-agent && docker compose exec -T api python -m app.privacy retention --older-than-days 365 --apply >> retention.log 2>&1
```

На Windows ту же команду запускает Планировщик заданий.

## Ограничения

- **Резервные копии.** Обезличивание не меняет уже сделанные
  [копии](backup.md). Восстановление копии, сделанной раньше, вернёт данные:
  после него повторите `python -m app.privacy erase` для этих клиентов.
  Поэтому ведите вне системы список обезличенных клиентов (дата и ID, без
  email) и храните копии не дольше, чем нужно.
- **Журнал API.** JSON-строки журнала содержат id, пути и коды ответов, но не
  тексты обращений и не email. Сколько хранится журнал контейнера, решает
  настройка Docker на площадке.
- **Реальная модель.** В режиме `mock` тексты никуда не отправляются. Если
  включён OpenAI, обращения уходили провайдеру, и обезличивание у провайдера
  ничего не удаляет.
- Это техническое средство, а не юридическая оценка: сроки хранения и порядок
  ответа на запросы клиентов определяет владелец данных.

## Как это проверяется

- `tests/integration/test_privacy_erasure.py` на настоящей PostgreSQL: после
  обезличивания имя, email, компания, тексты обращения, ответа и комментария не
  находятся ни в одной таблице, включая `bytea` в checkpoint LangGraph. До
  обезличивания тот же поиск их находит. Там же проверены 403 для
  `operator`/`reviewer`, 409 и 422, гонка с одновременным созданием обращения,
  срок хранения (план, применение, пропуск pending) и команда `app.privacy`.
- `tests/test_privacy.py` и тесты интерфейса проверяют очистку трассы и итога,
  контракт API, CLI и форму администратора.
- `scripts/smoke_test.py --check-privacy` в задании `container` CI проходит
  весь путь на собранном образе: клиент с уникальным маркером, mock-анализ,
  одобрение, обезличивание, чтение через API. Затем CI ищет маркер во всех
  таблицах PostgreSQL: он не должен найтись.

Проверить свой стенд можно тем же smoke (нужен токен `admin`, создаётся
учебный клиент, которого smoke сразу обезличивает):

```bash
uv run --locked python scripts/smoke_test.py \
  --base-url http://127.0.0.1:8001 --timeout 60 --check-privacy
```

Токен берётся из переменной окружения `API_TOKEN`, как в остальных проверках.
