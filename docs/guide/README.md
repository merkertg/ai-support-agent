# Наглядный PDF-гайд по AI Support Agent

[← README проекта](../../README.md) · [CI/CD подробно](../CI_CD.md)

[Открыть руководство](ai-support-agent-guide.pdf). Первые 14 разделов объясняют
архитектуру и все десять этапов, включая интерфейс оператора, оценки и
демонстрацию. Разделы 15–24 описывают полный прогон проекта, CI/CD, работу
оператора, перезапуск, диагностику и фактические результаты аудита.
Раздел 20 — перезапуску, сохранности томов и резервной копии с
восстановлением, раздел 22 — покрытию и восстановлению запусков, раздел 23 —
еженедельным обновлениям зависимостей, стабильным версиям образов,
их подписи cosign и очистке старых SHA-образов в GHCR.
На обложке — 24 пункта оглавления в двух колонках.

## Какие файлы составляют руководство

| Файл | Назначение |
| --- | --- |
| [ai-support-agent-guide.pdf](ai-support-agent-guide.pdf) | Итоговый документ для чтения и показа. |
| [verification.json](verification.json) | Проверенные результаты, дата аудита, исходный коммит, ограничения и статус удалённого CI. |
| [../../scripts/build_guide.py](../../scripts/build_guide.py) | Исходник макета, схем, таблиц и дополнения. |

Числа тестов на обложке и в разделе проверки, а также метрики оценок этапа 09
берутся из JSON. Исторический график по этапам сохраняет результаты тех этапов:
это история, а не новый прогон.
Тесты smoke CLI входят в unit и не прибавляются к общей сумме повторно.

## Как пересобрать

Нужен Python 3.12+ и ReportLab 4.4.9. Для обычного запуска API ReportLab
не требуется и в production-образ не устанавливается. Команды ниже выполняются
из корня проекта; `uv run --with` добавляет зависимость только для этой команды.

```bash
uv run --locked --with 'reportlab==4.4.9' python scripts/build_guide.py \
  --verification docs/guide/verification.json \
  --output docs/guide/ai-support-agent-guide.pdf
```

На Mac используются системные PT Sans и PT Mono из
`/System/Library/Fonts/Supplemental/`. На Linux генератор ищет DejaVu Sans
и DejaVu Sans Mono в `/usr/share/fonts/truetype/dejavu/`; их предоставляет
пакет `fonts-dejavu-core`. Если шрифты не найдены, сборка завершается понятной
ошибкой. Шрифты не копируются в Git.

При существующем выходном PDF генератор сначала сохраняет его копию
`ai-support-agent-guide-before-<дата-время>.pdf` в системном временном каталоге (`tempfile.gettempdir()`). Резервная копия не входит в Git. Новая версия сначала собирается во временный
файл рядом с результатом и заменяет PDF только при успехе; ошибка вёрстки
сохраняет исходный файл.
Импорт модуля не запускает сборку и не читает аргументы CLI.

## Как обновлять проверенные сведения

1. Заверши исправления и выполни полный прогон по
   [инструкции тестирования](../instructions/testing.md).
2. Запиши фактические результаты в `verification.json`: дата, исходный коммит,
   число прошедших тестов, число пропусков, проверки и ограничения.
3. Укажи удалённый статус отдельно. `not_verified` означает, что запуск GitHub
   Actions для итогового коммита ещё не подтверждён. Локальный успех не заменяет
   результат Actions и наличие SHA-тега в GHCR.
4. Пересобери PDF, извлеки текст и проверь рендер всех страниц.
5. Зафиксируй исходник, JSON, PDF и относящуюся к ним документацию вместе.

Генератор проверяет, что `total = unit + integration`, все счётчики
неотрицательны, а `smoke_cli <= unit`. Он требует реальные строки результатов
в `checks`, явный статус `remote_ci` и пояснение этого статуса.
В JSON и в PDF не помещают API-ключи, пароли или реальные клиентские данные.

## Как проверить PDF после сборки

Для структурной проверки можно использовать `pypdf`, для визуальной — Poppler
(`pdfinfo`, `pdftoppm`). Эти инструменты нужны проверяющему документ;
приложение поддержки от них не зависит.

```bash
pdfinfo docs/guide/ai-support-agent-guide.pdf
mkdir -p /tmp/ai-support-guide-preview
pdftoppm -r 110 -png docs/guide/ai-support-agent-guide.pdf \
  /tmp/ai-support-guide-preview/page
```

Проверь каждую страницу: кириллица читается, нет пустых квадратиков,
таблицы и команды помещаются в поля, подписи схем не пересекаются,
порядок и номера страниц верны. Сверь даты, числа тестов и статус GitHub с JSON.
Успешная сборка сама по себе не подтверждает качество вёрстки.

PDF не собирается в runtime Docker-образе. GitHub CI проверяет Python-исходник,
docstrings, ссылки и примеры документации; текст и вёрстку PDF проверяют при
обновлении документа. Конфигурация workflow — в
[../../.github/workflows/ci.yml](../../.github/workflows/ci.yml).

## Эксплуатационное дополнение

Руководство отражает текущую конфигурацию, а проверенные результаты
по-прежнему берёт из `verification.json` после реального прогона:

- Шесть заданий CI: `delivery → checks/security/portability → container → publish`;
  `portability` проверяет Linux, macOS и Windows, `container` — также arm64.
  Четыре проверенных образа (API/UI × amd64/arm64) передаются одним артефактом
  и проверяются по image ID и платформе; повторной сборки перед GHCR нет.
  Общий тег — index двух архитектур, рядом теги `-amd64` и `-arm64`.
- `main` публикует `sha-<полный SHA>`; `latest` меняется для актуальной вершины.
  Явный push строгого `vX.Y.Z` из истории `main` публикует обе версии,
  сохраняет `latest` и отклоняет конфликт существующего version-тега.
- uv 0.12.23 закреплён по версии/digest. Минимальный возраст PyPI-пакетов —
  14 дней. Weekly workflow по понедельникам в 06:17 UTC / 11:17 Ташкент
  готовит одну PR, явно запускает CI и не включает автослияние.
- Coverage имеет общий порог **85%** по строкам и ветвям, учитывает дочерние
  Python-процессы; артефакт `coverage-report` содержит XML, JSON и HTML.
- Recovery каждые 30 секунд завершает только `running` возрастом от 180 секунд;
  поздний worker не может создать предложение. SQL-ошибка откатывает проход.
- `scripts/backup.py` делает копию PostgreSQL и Qdrant с манифестом
  (Alembic, SHA256, строки), проверяет её и восстанавливает в чистые тома;
  CI повторяет этот круг в задании `container`. Копии секретны и в Git
  не попадают ([инструкция](../instructions/backup.md)).

Практические команды для скачивания версии задают **оба** `APP_IMAGE` и
`UI_IMAGE`, затем запускают Compose-сервис `ui`. В таблице следующих шагов
публикация UI заменена подтверждением фактического запуска удалённого CI.
Токены сотрудников, роли и лимит изменений API реализованы; корпоративный
вход (SSO), настоящая доставка, серверный deploy и реальные OpenAI-оценки
по-прежнему требуют отдельных следующих работ.

Подробности: [восстановление](../RUN_RECOVERY.md),
[обновления](../DEPENDENCY_UPDATES.md), [CI/CD](../CI_CD.md).
Исторический график числа тестов по этапам сохраняется; новые фактические
числа, coverage и статус Actions добавляются в JSON только после проверки.
