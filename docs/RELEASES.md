# Версии и публикация API и UI

[← README](../README.md) · [CI/CD подробно](CI_CD.md)

Проект публикует два отдельных Docker-образа в GitHub Container Registry:

| Компонент | Пакет GHCR | Содержимое |
| --- | --- | --- |
| API | `ghcr.io/merkertg/ai-support-agent` | FastAPI, агент, Alembic, база знаний и серверные зависимости |
| UI | `ghcr.io/merkertg/ai-support-agent-ui` | Streamlit, HTTP-клиент и интерфейс оператора |

UI обращается к API через HTTP. Ему не нужны ключ OpenAI, прямое подключение
к PostgreSQL и серверный код. Оба образа проходят отдельные проверки состава,
пользователя, известных уязвимостей и реальный сценарий совместной работы.

Настройка доставки реализована в `.github/workflows/ci.yml` и
`scripts/release_delivery.py`. Она не создаёт Git-теги и GitHub Releases
автоматически: номер версии выбирает человек.

## 1. Когда запускается публикация

| Событие | Полные проверки | Теги API и UI в GHCR | Обновление `latest` |
| --- | --- | --- | --- |
| `push` в `main` | Да | `sha-<полный SHA commit>` | Только если проверяемый commit — текущая вершина `main` на момент проверки |
| Явный `push` тега `vX.Y.Z` | Да, для commit этого тега | `vX.Y.Z` | Нет |
| Pull request в `main` | Да | Нет | Нет |
| Ручной `Run workflow` | Да | Нет | Нет |
| `workflow_dispatch` для ветки обновления зависимостей | Да | Нет | Нет |

Версионный запуск не меняет также SHA-тег: образ заново собирается для
проверки выпуска, а время сборки может изменить его ID даже при одинаковом
исходном commit. Ранее опубликованный SHA-образ сохраняет своё значение.

`latest` и `sha-...` — теги registry. Для указания точного содержимого
используется адрес с digest `@sha256:...`. SHA Git и digest Docker имеют
разный смысл: первый определяет исходный код, второй — manifest образа.

## 2. Какие проверки выполняются до GHCR

Порядок заданий:

```text
Validate delivery target
          ↓
Python checks + Audit runtime dependencies
          ↓ оба успешны
Build and smoke test Docker
          ↓
Publish tested image to GHCR
```

Для тегов первый job требует строгий формат `vX.Y.Z`, например `v0.1.0`
или `v1.12.3`. Запрещены ведущие нули, пробелы, prerelease/build-суффиксы,
добавочные компоненты и любые shell-конструкции. `v01.2.3`, `v1.2` и
`v1.2.3-rc1` не принимаются. Проверка опирается на полное регулярное
выражение, а Git/Docker запускаются списком аргументов без shell.

Затем проверяется, что сам тег после разрешения annotated tag указывает
именно на commit запуска GitHub Actions и что этот commit входит в историю
`origin/main`. Тег сторонней ветки до её включения в `main` отклоняется.
Достаточно принадлежности истории, а не только совпадения с последним
commit: это позволяет осознанно выпустить проверенную историческую версию.
У такого выпуска нет права менять `latest`.

После этого выполняются обычные проверки lock, возраста зависимостей,
workflow, документации, миграций, стиля, тестов, минимального покрытия 85%,
оценок качества, аудита зависимостей, сборки, Trivy и полного контейнерного
сценария. Ошибка любого обязательного шага блокирует публикацию.
CI использует mock-провайдеры без ключей OpenAI.

## 3. Как сохраняется связь с протестированными образами

`container` собирает два образа:

```text
ai-support-agent:ci
ai-support-agent-ui:ci
```

После всех проверок `release_delivery.py export` читает полный ID каждого
из них и экспортирует их одним вызовом `docker save`. Артефакт
`tested-docker-images` содержит:

| Файл | Назначение |
| --- | --- |
| `tested-images.tar` | Оба уже собранных и протестированных образа |
| `tested-images.json` | Полный SHA commit и словарь двух локальных имён с полными image ID |

`publish` скачивает артефакт именно своего запуска, проверяет структуру
JSON, SHA исходного commit, наличие обоих образов и формат ID. Затем делает
`docker load` и сравнивает оба загруженных image ID с сохранёнными.
Любое несовпадение останавливает доставку. В `publish` нет `docker build`.

Артефакт хранится один день. Срок его хранения не ограничивает время жизни
опубликованных пакетов GHCR. Для позднего повторения только `publish`
понадобится сохранившийся артефакт; правила восстановления описаны ниже.

## 4. Защита существующей версии

До первой записи релизного тега скрипт проверяет **оба** пакета GHCR.
Для авторизации используется временный `GITHUB_TOKEN` с `packages: write`
только в задании публикации. Registry token и пароли не передаются
аргументами команд и не выводятся в сообщения об ошибках.

Для каждой ссылки `vX.Y.Z` возможны три результата:

1. Manifest отсутствует: HTTP 404 разрешает создание версии.
2. Manifest/index уже существует и его подтверждённый идентификатор
   совпадает с ID соответствующего протестированного образа: ссылка
   считается корректной и повторно не записывается.
3. Ссылка указывает на другой образ: job завершается ошибкой до первого
   push любого из двух пакетов.

Поэтому конфликт версии UI не приводит к частичной записи новой версии API.
HTTP 401/403, ограничение запросов, сетевой сбой, повреждённый JSON и ошибки
registry не считаются отсутствием тега. Они блокируют публикацию.
После каждого нового push скрипт повторно читает manifest/index и сверяет
SHA256 **всего полученного тела** с `Docker-Content-Digest`.
Поддерживаются Docker schema 2 manifest/list и OCI manifest/index.
У classic Docker image ID — это `config.digest` одиночного manifest;
containerd может вернуть ID самого manifest либо OCI index. Поэтому для
одиночного manifest tested ID должен совпасть с config ID либо digest
полного manifest, а для index — только с digest **всего index**.
Совпадение с digest произвольного дочернего manifest не принимается.

Index обязан иметь `schemaVersion: 2`, распознанный media type и непустой
список корректных descriptors с media type, SHA256 digest и положительным
целым размером. Это позволяет сохранять provenance attestations из Docker
BuildKit вместе с самим образом. Наличие index не означает, что pipeline
стал собирать несколько архитектур: CI по-прежнему собирает `linux/amd64`.
Идентичность SHA/latest проверяется по одному полному manifest/index.
Переадресация HTTP не пересылает credentials другому адресу.

Публикации main и релизов сериализованы общей группой `ghcr-delivery`.
Это обеспечивает защиту от пересечения запусков данного workflow.
Registry не предоставляет здесь транзакцию сразу для двух пакетов:
внешний пользователь с правом записи технически может поменять тег.
Не следует вручную перезаписывать выпущенные версии; для Git-тегов
можно настроить запрет обновления и удаления через правила репозитория.

## 5. Как выпустить выбранную версию

Эти команды — инструкция. Они не выполнялись автоматически и не означают,
что версия `v0.1.0` уже выбрана или опубликована.
Перед выпуском выбери номер версии и проверь результат CI нужного commit.
Для выпуска commit должен содержать workflow с поддержкой release-тегов.

```bash
# Выполнить из корня репозитория; сначала проверить незакоммиченные изменения.
git status --short
git fetch origin main --tags
git log -5 --oneline origin/main

# Здесь v0.1.0 — пример. Подставь выбранный номер, который ещё не использован.
VERSION=v0.1.0
RELEASE_COMMIT=$(git rev-parse origin/main)

# Следующая команда должна закончиться без вывода. Занятый тег не перезаписывают.
git tag --list "$VERSION"

# Создать annotated tag с описанием для выбранного commit и отправить его.
git tag --annotate "$VERSION" "$RELEASE_COMMIT" --message "AI Support Agent $VERSION"
git push origin "refs/tags/$VERSION"
```

`git tag --list` лишь показывает совпадения: если тег уже найден, выбери новый
номер и не продолжай команды создания. Не используй `--force` и не удаляй
старую версию для повторного использования её номера.

На GitHub открой `Actions → CI and GHCR` и выбери запуск с нужным тегом.
Все шесть заданий должны пройти, включая три запуска `portability` на Linux, macOS и Windows. В сводке `publish` должны появиться обе
ссылки `:vX.Y.Z` и оба digest. Успех локального теста не подтверждает
выполнение удалённого workflow или существование пакета GHCR.

Создание записи GitHub Release с описанием версии пока остаётся отдельным
действием человека; CI публикует Docker-образы, а не выпуск на странице Releases.

## 6. Как повторить частично завершённую публикацию

API может успеть опубликоваться, а запись UI — прерваться из-за сети.
В этом случае открой исходный запуск и выбери `Re-run failed jobs`, пока
артефакт `tested-docker-images` ещё доступен. Повтор использует те же
image ID: существующий идентичный API пропускается, недостающий UI
публикуется и проверяется. Если оба образа уже идентичны, повтор не меняет
релизные ссылки.

`Re-run all jobs` создаёт новые сборки. Их ID могут измениться; если часть
старой версии уже опубликована, preflight обнаружит конфликт и остановится.
При истёкшем артефакте или изменившихся образах следует выбрать новый номер
версии, повторить полный CI и сохранить старые теги. Автоматической очистки
или перезаписи уже опубликованного релиза нет.

SHA-публикации main допускают повторную сборку того же commit и обновление
соответствующего SHA-тега. Для воспроизводимого скачивания старого
содержимого используй digest из сводки нужного запуска.

## 7. Как запустить готовую пару образов

Оба пакета впервые публикуются с приватной видимостью GHCR. Если Docker
ещё не авторизован для их скачивания, используй `docker login ghcr.io`;
учётной записи нужен доступ к пакетам. Для ручного входа применяют токен
с разрешением `read:packages`, переданный через `--password-stdin`, без
внесения токена в Git, `.env` проекта или текст команды.

В корне проекта при уже настроенном локальном `.env`:

```bash
# Подставить версию, успешная публикация которой подтверждена в GitHub Actions.
VERSION=v0.1.0
export APP_IMAGE="ghcr.io/merkertg/ai-support-agent:$VERSION"
export UI_IMAGE="ghcr.io/merkertg/ai-support-agent-ui:$VERSION"
docker compose pull api ui
docker compose up --detach --no-build --wait --wait-timeout 180 ui
```

Compose подставит `APP_IMAGE` и для миграции, и для API, а `UI_IMAGE` —
для интерфейса. Запуск ожидает готовность зависимостей и применяет миграции
выбранной версии. Постоянные тома PostgreSQL и Qdrant сохраняются.
Не удаляй их через `down --volumes`, если требуется сохранить данные.

Для точной фиксации содержимого вместо тега можно задать две независимые
ссылки `ghcr.io/...@sha256:...` из одной сводки публикации. Автоматический
откат схемы БД не реализован: возврат старого образа после новой миграции
требует предварительной проверки совместимости и резервной копии данных.

Публикация в GHCR сама по себе не перезапускает dev-стенд и не развёртывает
приложение на внешнем сервере. Локальный запуск остаётся явной командой.

## 8. Что проверить при ошибке

| Сообщение или симптом | Действие |
| --- | --- |
| `Версия должна иметь строгий формат` | Выбрать `vX.Y.Z` без ведущих нулей и суффиксов |
| `Тег изменён` | Сверить исходный commit запуска и текущую Git-ссылку; не менять тег опубликованной версии |
| `только для commit в истории origin/main` | Сначала включить изменения в `main`, затем выбрать новый корректный тег |
| `уже занята другим образом` | Не перезаписывать существующую версию; использовать прежний артефакт для идентичного повторения либо новый номер |
| HTTP 401/403 от GHCR | Проверить доступ workflow к обоим пакетам и `packages: write` у `publish`; не считать ссылку свободной |
| `Загруженный образ не совпадает` | Проверить артефакт исходного запуска; публикация была остановлена до push |
| API опубликован, UI отсутствует | Повторить failed publish с прежним артефактом, пока он хранится |
| `latest` пропущен | Для tag-запуска это ожидаемо; для main сверить актуальную вершину ветки |

Текущие фактические результаты проверок и статус удалённого запуска
фиксируются отдельно в [VERIFICATION.md](VERIFICATION.md). Документация
релизной процедуры не является подтверждением выполненной публикации.

Официальные сведения: [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)
и [Docker Registry HTTP API V2](https://distribution.github.io/distribution/spec/api/).
Формат containerd разобран в [Docker Desktop image store](https://docs.docker.com/desktop/features/containerd/),
структура индекса — в [OCI Image Index Specification](https://github.com/opencontainers/image-spec/blob/main/image-index.md).
