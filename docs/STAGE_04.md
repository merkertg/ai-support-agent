# Этап 04. Языковая модель и черновик ответа по обращению

Цель этапа — прочитать существующее обращение из PostgreSQL, подготовить контекст,
передать его отдельному LLM-клиенту и вернуть оператору структурированный черновик.
Появляются два режима: локальная демонстрация `mock` и запрос к OpenAI `openai`.

Инструкция описывает порядок действий, назначение кода, ожидаемые ответы, ошибки
и проверки. Фактические результаты этой итерации находятся в
[журнале разработки](DEVELOPMENT_LOG.md). Основа БД разобрана в
[этапе 02](STAGE_02.md), HTTP API ресурсов — в [этапе 03](STAGE_03.md),
проверки и доставка Docker-образа — в [инструкции CI/CD](CI_CD.md).

> **Windows.** Команды в этом руководстве написаны для Bash (Linux, macOS).
> В Windows выполняй их в Git Bash или WSL 2 либо используй аналоги для PowerShell
> из страницы [Windows и PowerShell](instructions/windows.md).

## 1. Что должно работать после этапа

Добавлены две HTTP-операции:

| Запрос | Назначение |
| --- | --- |
| `GET /api/llm/status` | Показать провайдера, имя модели и готовность настроек без ключа и запроса к модели. |
| `POST /api/tickets/{resource_id}/draft` | Прочитать обращение по ID и вернуть краткое описание, категорию и черновик ответа. |

Первый режим работы — `mock`. Он возвращает явно помеченный учебный результат,
не обращается во внешнюю сеть и не требует ключа. Это позволяет изучить маршрут,
формат JSON и обработку ошибок до подключения платного сервиса. Mock не выполняет
реальный AI-анализ: его ответ нельзя использовать как подтверждённое решение проблемы.

Режим `openai` использует Responses API и Structured Outputs. Ключ остаётся
на сервере, а модель получает только подготовленный контекст обращения и продукта.
Запрос черновика может вызвать платный внешний запрос, когда этот режим включён.

Результат требует проверки человеком: `requires_human_review` всегда равен `true`.
Генерация возвращает предварительный ответ в HTTP JSON. Она не записывает результат
в `agent_runs` или `agent_suggestions`, не меняет обращение и не отправляет клиенту
письмо. Таблицы для будущего агента уже существуют, но их использование относится
к следующему этапу. Инструменты агента, проверка лицензии через tool calling,
поиск по документам и RAG здесь ещё не подключены.

## 2. Как проходит запрос

```text
Оператор / Swagger / curl
        │ POST /api/tickets/123/draft
        ▼
HTTP router → проверка положительного ID
        ▼
Service → чтение Ticket и Product из PostgreSQL
        ▼
Подготовка ограниченного контекста без загрузки клиента и лицензий
        ▼
LLM-клиент
  ├─ mock: предсказуемый учебный ответ
  └─ openai: Responses API + схема Structured Outputs
        ▼
Проверка структуры ответа → JSON черновика → оператор
```

На примере обращения «После обновления не запускается сервер»:

1. Router получает ID обращения из адреса. JSON-тело для генерации не требуется.
2. Сервис ищет обращение и связанный продукт в уже существующей БД.
3. Из полей собирается текстовый контекст. Отдельно задаются инструкции модели.
4. Клиент выбранного провайдера формирует ответ согласованной структуры.
5. Приложение возвращает текст оператору; сохранение или отправка ответа не происходит.

Сервис сначала проверяет существование обращения, а затем создаёт клиент. Поэтому
неизвестный ID возвращает `404` даже при ненастроенном внешнем провайдере. Перед
ожиданием модели сервис копирует значения в `DraftContext` и вызывает
`session.rollback()`: это завершает открытую чтением транзакцию и возвращает
соединение в пул. Сессия принадлежит текущему HTTP-запросу и не содержит
пользовательских изменений, которые нужно сохранить. Ожидание внешнего API
не удерживает соединение PostgreSQL. Синхронный маршрут выполняется FastAPI
в рабочем потоке, поэтому ожидание SDK не занимает основной event loop.

HTTP-код `200` означает, что черновик сформирован в допустимом формате.
Он не означает, что предложенное решение верно. Оператор проверяет факты,
соответствие продукту и применимость действий к обращению клиента.

## 3. Термины простыми словами

**LLM** — языковая модель. Она получает инструкции и текст, затем формирует ответ.
Ей нужно явно объяснить задачу и передать необходимые сведения: прямого доступа
к нашей PostgreSQL у внешней модели нет.

**Провайдер** — реализация клиента, который получает результат. В проекте это
локальный `mock` или внешний `openai`. HTTP-контракт черновика одинаков в обоих
случаях, поэтому UI и тесты не зависят от способа получения текста.

**Модель** — конкретный идентификатор модели в аккаунте провайдера. Для OpenAI
его задаёт пользователь в `OPENAI_MODEL`; проект не подставляет случайный вариант.
Выбранная модель должна поддерживать используемые Responses API и Structured Outputs.

**Prompt** — инструкции и данные, передаваемые модели. Инструкция системы описывает
роль помощника и правила ответа. Пользовательская часть содержит обращение и продукт.
Текст клиента считается данными: содержащаяся в нём просьба «игнорируй инструкции»
не должна превращаться в правило работы приложения.

**Токены** — единицы обработки текста моделью. Они не совпадают один к одному
с символами или словами; соотношение зависит от текста и модели. Ограничение длины
контекста проекта измеряется в символах, а `LLM_MAX_OUTPUT_TOKENS` — в токенах ответа.
Эти две величины нельзя напрямую сравнивать.

**Structured Outputs** — запрос ответа по JSON Schema. SDK получает схему
Pydantic и возвращает разобранный объект. Это помогает согласовать структуру:
обязательные поля, допустимые категории и типы. При этом отказ модели, незавершённый
ответ или проблема соединения остаются отдельными возможными исходами.
Правильная структура сама по себе не доказывает правильность содержания.

Официальное описание механизма: [Structured Outputs в Responses API](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

Начни с `create_ticket_draft()` в `app/api/drafts.py`, затем прочитай
`create_draft()` в `app/services/drafts.py` и `generate()` выбранного клиента.
После этого прочитай схему ответа: она объясняет, какой объект должен вернуться
в HTTP. Настройки и обработку ошибок удобнее изучать уже после основного сценария.

В функциях используются русские docstring: они объясняют цель функции,
её входные данные, результат и причины важных проверок. Комментарии около
тайм-аутов, ограничений и обработки исключений объясняют поведение, которое
нельзя понять только по названию переменной.

## 5. Настройки: сначала безопасная локальная демонстрация

Настройки LLM вынесены отдельно от настроек PostgreSQL. Ошибочная модель или ключ
не должны ломать `/health` и проверку готовности БД `/ready`. Доступность самого
процесса, доступность базы и возможность генерации — разные проверки.

| Переменная | Для чего нужна | Начальное значение / ограничение |
| --- | --- | --- |
| `LLM_PROVIDER` | Выбор локального или внешнего клиента. | `mock`; допустимы `mock`, `openai`. |
| `OPENAI_API_KEY` | Серверный ключ OpenAI. | В mock не требуется; в openai обязателен. |
| `OPENAI_MODEL` | Идентификатор выбранной пользователем модели. | В openai обязателен, автоматической подстановки нет. |
| `LLM_TIMEOUT_SECONDS` | Предел ожидания одного запроса. | `30`; от `1` до `120` секунд. |
| `LLM_MAX_OUTPUT_TOKENS` | Передаваемый модели предел токенов ответа. | `1200`; от `128` до `4096`. |

Точные имена переменных сверяй с `.env.example` и `app/llm/config.py` текущей версии.
Настоящий ключ хранится только в локальном `.env` или серверном окружении.
Он не является параметром публичного HTTP-запроса, не возвращается статусом и
не помещается в исходники. Файлы `.env` исключены из Git и Docker-контекста;
в репозитории хранится только `.env.example` без настоящего секрета.

Ключ представлен типом `SecretStr`. Это скрывает его обычное строковое
представление, но не отменяет необходимости аккуратно обращаться с настройками.
Не печатай полный `.env` и не используй `docker compose config` без необходимости:
развёрнутая конфигурация может содержать значения переменных. Для проверки синтаксиса
Compose достаточно `docker compose config --quiet`.

`configured` в статусе означает готовность локальных настроек. Эта проверка не
выполняет тестовый запрос в OpenAI: она не доказывает наличие квоты, доступ к модели
или работу сети. Реальный внешний запрос выполняется только при генерации черновика
в режиме `openai`.

## 6. Установить зависимости и запустить Compose

Открой терминал в корне проекта:

Для последующих команд нужны Python 3.12+, установленный `uv` и работающий
Docker (Docker Desktop на macOS и Windows).

Установи зафиксированные зависимости:

```bash
uv sync --locked
```

Если окружение уже синхронизировано, для Python-команд можно использовать
`.venv/bin/python` вместо `uv run --locked python`. Наличие `.venv` не заменяет
обновление зависимостей после изменения `uv.lock`.

Создай локальные настройки только при отсутствии файла:

```bash
if [ ! -f .env ]; then
  cp .env.example .env
fi
```

Если `.env` уже существует, добавь недостающие LLM-переменные из нового образца.
Сохрани свои текущие настройки PostgreSQL. Начни с `LLM_PROVIDER=mock`:
для этого сценария ключ и имя OpenAI-модели не нужны.

Проверь Compose без вывода значений настроек, собери и запусти сервер:

```bash
docker compose config --quiet
docker compose up --build --detach --wait --wait-timeout 90 api
docker compose ps --all
```

Ожидается последовательность `db healthy → migrate exit 0 → api healthy`.
Стандартные локальные порты: HTTP API `8001`, PostgreSQL приложения `5433`,
отдельная тестовая БД `5434`. Внутри Docker API использует адрес `db:5432`.
Если изменён `API_PORT`, подставляй свой порт во все URL ниже.

Проверь сервер и новый статус:

```bash
curl --silent --show-error --fail-with-body http://127.0.0.1:8001/health
curl --silent --show-error --fail-with-body http://127.0.0.1:8001/ready
curl --silent --show-error --fail-with-body http://127.0.0.1:8001/api/llm/status
```

Последний ответ в режиме по умолчанию:

```json
{"provider":"mock","model":"mock-draft-v1","configured":true}
```

Он не выполняет SQL или внешнюю генерацию. Две новые операции также должны
появиться в [Swagger локального сервера](http://127.0.0.1:8001/docs).

## 7. Создать учебное обращение для полного прохода

Можно использовать существующее обращение из этапа 03 и сразу перейти к разделу 8,
подставив его ID. Ниже — самостоятельный воспроизводимый сценарий с вымышленными
данными. Он создаёт клиента, продукт и обращение в development-БД через обычный API.
Тесты, напротив, используют отдельную одноразовую БД.

Выполняй блоки по порядку в одном терминале: переменные используются между шагами.
Создай временную папку для JSON и уникальный суффикс:

```bash
STAGE04_TMP=$(mktemp -d)
STAGE04_SUFFIX=$(uv run --locked python -c 'import uuid; print(uuid.uuid4().hex[:12])')
```

Сформируй запрос клиента без ручного экранирования JSON:

```bash
uv run --locked python - "$STAGE04_SUFFIX" > "$STAGE04_TMP/customer-request.json" <<'PY'
import json
import sys

suffix = sys.argv[1]
print(json.dumps({
    "name": "Учебный клиент этапа 04",
    "email": f"stage04-{suffix}@example.com",
    "company": "Учебная компания",
}, ensure_ascii=False))
PY
curl --silent --show-error --fail-with-body \
  --request POST http://127.0.0.1:8001/api/customers \
  --header 'Content-Type: application/json' \
  --data-binary "@$STAGE04_TMP/customer-request.json" \
  --output "$STAGE04_TMP/customer-response.json"
STAGE04_CUSTOMER_ID=$(uv run --locked python -c \
  'import json,sys; print(json.load(open(sys.argv[1]))["id"])' \
  "$STAGE04_TMP/customer-response.json")
```

Создай продукт:

```bash
uv run --locked python - "$STAGE04_SUFFIX" > "$STAGE04_TMP/product-request.json" <<'PY'
import json
import sys

print(json.dumps({
    "name": "TechFlow Server, учебный пример",
    "code": f"stage04-{sys.argv[1]}",
    "description": "Серверное приложение для учебного сценария поддержки.",
}, ensure_ascii=False))
PY
curl --silent --show-error --fail-with-body \
  --request POST http://127.0.0.1:8001/api/products \
  --header 'Content-Type: application/json' \
  --data-binary "@$STAGE04_TMP/product-request.json" \
  --output "$STAGE04_TMP/product-response.json"
STAGE04_PRODUCT_ID=$(uv run --locked python -c \
  'import json,sys; print(json.load(open(sys.argv[1]))["id"])' \
  "$STAGE04_TMP/product-response.json")
```

Создай обращение, связанное с обоими объектами:

```bash
uv run --locked python - "$STAGE04_CUSTOMER_ID" "$STAGE04_PRODUCT_ID" \
  > "$STAGE04_TMP/ticket-request.json" <<'PY'
import json
import sys

print(json.dumps({
    "customer_id": int(sys.argv[1]),
    "product_id": int(sys.argv[2]),
    "subject": "После обновления не запускается сервер",
    "description": (
        "После обновления TechFlow Server служба останавливается при запуске. "
        "В журнале есть сообщение connection refused. "
        "Подскажите, какие сведения собрать для диагностики."
    ),
    "priority": "medium",
}, ensure_ascii=False))
PY
curl --silent --show-error --fail-with-body \
  --request POST http://127.0.0.1:8001/api/tickets \
  --header 'Content-Type: application/json' \
  --data-binary "@$STAGE04_TMP/ticket-request.json" \
  --output "$STAGE04_TMP/ticket-response.json"
STAGE04_TICKET_ID=$(uv run --locked python -c \
  'import json,sys; print(json.load(open(sys.argv[1]))["id"])' \
  "$STAGE04_TMP/ticket-response.json")
uv run --locked python -m json.tool --no-ensure-ascii "$STAGE04_TMP/ticket-response.json"
```

Ожидается созданное обращение с положительным `id` и статусом `open`.
Сохрани вывод или значение `STAGE04_TICKET_ID`: это ID для генерации.
Лицензия для этого этапа не нужна: модель ещё не вызывает инструмент проверки лицензий.

## 8. Получить первый mock-черновик

Сначала можно посмотреть сохранённое обращение:

```bash
curl --silent --show-error --fail-with-body \
  "http://127.0.0.1:8001/api/tickets/$STAGE04_TICKET_ID" \
  --output "$STAGE04_TMP/ticket-before.json"
```

Теперь вызови генерацию без JSON-тела:

```bash
curl --silent --show-error --fail-with-body \
  --request POST \
  "http://127.0.0.1:8001/api/tickets/$STAGE04_TICKET_ID/draft" \
  --output "$STAGE04_TMP/draft.json"
uv run --locked python -m json.tool --no-ensure-ascii "$STAGE04_TMP/draft.json"
```

Форма ответа:

```json
{
  "ticket_id": 123,
  "provider": "mock",
  "model": "mock-draft-v1",
  "content": {
    "summary": "Обращение №123: После обновления не запускается сервер",
    "category": "other",
    "draft_reply": "Демонстрационный черновик. Реальная модель не вызывалась. Далее идут уточняющие вопросы."
  },
  "usage": null,
  "requires_human_review": true
}
```

Это пример формы, а не дословный ожидаемый mock-текст. В реальном ответе `ticket_id`
совпадает с ID запрошенного обращения, `model` содержит имя из реализации,
а `draft_reply` начинается с «Демонстрационный черновик. Реальная модель не вызывалась.».
Поле `usage` при наличии
статистики содержит счётчики токенов; отсутствие статистики не делает ответ ошибкой.

Допустимы только четыре категории:

| Значение | Смысл |
| --- | --- |
| `technical_issue` | Техническая неисправность или ошибка продукта. |
| `license_question` | Вопрос о лицензировании. |
| `how_to` | Вопрос о том, как выполнить действие. |
| `other` | Иной запрос или недостаточно оснований для другой категории. |

Категория — часть структурированного результата модели. На этом этапе она не
изменяет поля сохранённого обращения и не запускает бизнес-процесс автоматически.

## 9. Убедиться, что генерация не меняет обращение

Прочитай запись после генерации и сравни ответы:

```bash
curl --silent --show-error --fail-with-body \
  "http://127.0.0.1:8001/api/tickets/$STAGE04_TICKET_ID" \
  --output "$STAGE04_TMP/ticket-after.json"
cmp "$STAGE04_TMP/ticket-before.json" "$STAGE04_TMP/ticket-after.json"
```

Успешный `cmp` не печатает различий и завершается с кодом `0`. Это показывает,
что поля HTTP-представления обращения, включая статус и время обновления, не изменились.
Более строгие тесты дополнительно проверяют отсутствие записей запуска/предложения
и отсутствие лишних изменений БД.

Временная папка содержит только вымышленные JSON данного прохода. После изучения
её можно удалить. Созданные через API записи останутся в development-БД, как
и записи учебного сценария этапа 03.

## 10. Подключить настоящий OpenAI

Этот шаг выполняется отдельно после успешного mock-прохода. Нужны серверный ключ,
доступ к выбранной модели и возможность обращения к API из среды запуска.
Настройки ключа и доступов проверяются в своём аккаунте OpenAI.

В локальном `.env` укажи:

```dotenv
LLM_PROVIDER=openai
OPENAI_API_KEY=REPLACE_WITH_YOUR_OWN_API_KEY
OPENAI_MODEL=REPLACE_WITH_MODEL_ID_AVAILABLE_TO_YOUR_ACCOUNT
LLM_TIMEOUT_SECONDS=30
LLM_MAX_OUTPUT_TOKENS=1200
```

Строки `REPLACE_...` — обозначения места для своих значений, а не рабочие настройки.
Выбери идентификатор модели, для которой доступны Responses API и Structured Outputs.
Ключ не нужно присылать в чат, помещать в curl или добавлять в GitHub-репозиторий.

После изменения окружения пересоздай API-контейнер:

```bash
docker compose up --detach --no-build --force-recreate \
  --wait --wait-timeout 90 api
curl --silent --show-error --fail-with-body http://127.0.0.1:8001/api/llm/status
```

Изменение `.env` не меняет окружение уже работающего процесса. Обычный
`docker compose restart api` также не передаёт новые значения; нужен новый контейнер.
Пересборка образа при изменении только настроек не требуется. При запуске через
Uvicorn на Mac нужно перезапустить процесс и учесть, что переменные, уже экспортированные
в терминале, могут иметь приоритет над `.env`.

Ожидаемый статус: `provider: "openai"`, выбранное имя модели и `configured: true`.
Статус ещё не делает внешний запрос. Чтобы получить настоящий ответ, повтори
`POST .../draft` из раздела 8. В этом режиме генерация обращается к OpenAI и может
расходовать квоту API. Результат по-прежнему нужно проверить человеку.

После ручной проверки можно вернуть `LLM_PROVIDER=mock` и снова пересоздать API.
Так последующие учебные команды не будут обращаться к внешнему провайдеру.

При разработке этого этапа платный запрос не выполняется без настроенного
пользователем ключа. Успех тестов с подменой транспорта не считается проверкой
реального аккаунта, сети, квоты или конкретной внешней модели.

## 11. Как устроен OpenAI-клиент

Внешний клиент создаётся внутри серверного кода. Он получает ключ, явное имя модели,
тайм-аут и ограничение ответа из LLM-настроек. SDK вызывается через
`client.responses.parse(...)` с Pydantic-моделью для `text_format`.

Порядок действий:

1. Подготовить системные инструкции: задача поддержки, заданный формат и требование
   не выдавать предположения за выполненные проверки.
2. Передать пользовательский контекст обращения отдельной частью запроса.
3. Установить `store=False` для создаваемого Response и `truncation="disabled"`,
   чтобы провайдер не отрезал входной контекст автоматически.
4. Указать `max_output_tokens` и тайм-аут.
5. Получить разобранный результат и при наличии статистику использования токенов.
6. Отдельно обработать отказ, незавершённость, ошибки сети и некорректную структуру.
7. Преобразовать ожидаемые ошибки SDK в безопасные ошибки приложения.

Базовый адрес SDK задан явно: `https://api.openai.com/v1`. Случайная переменная
`OPENAI_BASE_URL` не перенаправляет этот клиент на другой сервер. Новый SDK-клиент
закрывается после запроса, включая завершение с исключением.

Повторные попытки SDK отключены: `max_retries=0`. Один запрос пользователя не
должен незаметно превращаться в цепочку повторных внешних вызовов. После ошибки
оператор может явно повторить действие, разобравшись с её причиной.

`temperature` не передаётся: поддержка параметров зависит от выбранной модели.
Контракт проекта требует согласованный ответ по схеме, но не обещает одинаковый
текст при повторных запросах к реальной модели.

Предел `max_output_tokens` ограничивает выходной бюджет запроса, но не гарантирует,
что модель успеет сформировать весь JSON или что ответ окажется полезным.
Слишком низкое значение может привести к незавершённому ответу; такой результат
не выдаётся как готовый черновик.

См. официальные материалы: [Python SDK](https://developers.openai.com/api/reference/python)
и [параметры создания Response](https://developers.openai.com/api/reference/python/resources/responses/methods/create).

## 12. Какие данные передаются модели

Контекст — JSON с шестью полями: `ticket_id`, `subject`, `description`,
`priority`, `product_name`, `product_code`. Описание продукта, его даты, данные
клиента и лицензий сюда не добавляются. Клиент модели не получает доступ
к соединению SQLAlchemy и сам не выполняет SQL.

Сервис не загружает и не добавляет в prompt e-mail клиента, таблицу лицензий
или ключи лицензий. Это ограничение состава выбранных полей, а не автоматическая
анонимизация текста: если автор сам вставил секрет в `description` обращения,
такой фрагмент остаётся частью текста. Для настоящих данных оператору нужно
учитывать содержимое обращения до внешней генерации.

Готовый контекст ограничен **16 000 символами**. Проверяется
`len(context.model_dump_json())`, включая JSON-ключи, кавычки и экранирование,
а не только длина описания. Ограничение действует и в mock, и в openai,
до вызова SDK. При превышении возвращается `413`; приложение не отрезает
хвост молча, поскольку в нём могли находиться важные диагностические сведения.
Этот предел относится к политике нашего приложения и не равен контекстному окну
конкретной модели в токенах. У текущего HTTP API уже есть собственные пределы
длины полей обращения. Дополнительная проверка полного контекста защищает также
от более длинных записей, полученных, например, импортом напрямую в БД.

`store=False` — параметр запроса Response. Он не означает, что обращение вообще
не передавалось провайдеру, и не заменяет оценку содержания данных перед отправкой.

## 13. Формат результата и usage

Внешний JSON содержит метаданные генерации и вложенный `content`:

| Поле | Содержание |
| --- | --- |
| `ticket_id` | ID существующего обращения. |
| `provider` | Клиент, вернувший результат: `mock` или `openai`. |
| `model` | Название mock-реализации или фактическое имя модели из ответа OpenAI. |
| `content.summary` | Краткое описание проблемы. |
| `content.category` | Одна из четырёх согласованных категорий. |
| `content.draft_reply` | Текст, который оператор читает и исправляет. |
| `usage` | Неотрицательные целые `input_tokens`, `output_tokens`, `total_tokens`, если провайдер вернул статистику; иначе `null`. |
| `requires_human_review` | Всегда `true`. |

Схема `DraftContent` запрещает неизвестные поля и требует все три поля.
`summary` содержит от 1 до 2000 символов, `draft_reply` — от 1 до 6000;
внешние пробелы убираются. Пустой ответ не проходит проверку. Эти ограничения
относятся к полям результата и отличаются от токенового бюджета запроса.

Статистика usage помогает изучать потребление API, но не является суммой оплаты.
Стоимость зависит от модели, текущих тарифов и вида токенов. Проект не подставляет
фиксированную цену и не вычисляет счёт по приблизительному числу символов.

Например, форма статистики выглядит так:

```json
{"input_tokens":150,"output_tokens":80,"total_tokens":230}
```

Это иллюстрация формы, а не измерение текущего проекта. В mock возвращается
`usage: null`: локальная заглушка не расходует токены внешнего провайдера.
На этом этапе поле usage возвращается оператору в ответе и не сохраняется
в отдельный журнал расходов БД. Сбор метрик и история запусков — отдельная задача.

## 14. Ошибки и порядок диагностики

Ожидаемые ошибки имеют публичную форму `{"detail":"безопасное сообщение"}`.
Текст SDK, ключ, адрес БД, служебный request payload и стек исключения не включаются
в HTTP-ответ.

| Код | Причина | Что проверить |
| --- | --- | --- |
| `404` | Обращение с положительным ID не найдено. | Получить существующие обращения через `GET /api/tickets`. |
| `422` | ID равен нулю, отрицательный, не целый или вне диапазона. | Использовать ID, возвращённый созданием или чтением обращения. |
| `413` | Собранный контекст длиннее 16 000 символов. | Изучить текст обращения и сериализованный контекст; подготовить подходящий объём данных. |
| `502` | Отказ модели, незавершённый или некорректный ответ. | Проверить настройки модели/выходного бюджета и повторить вручную при необходимости. |
| `503` | Не хватает корректных LLM-настроек, недоступен сервис, ошибка авторизации/квоты или сеть. | Провайдер, ключ, модель, доступ и состояние сети; при ошибке БД — также PostgreSQL. |
| `504` | Внешний запрос не завершился за настроенное время. | Доступность провайдера и выбранный тайм-аут. |

Разные причины `503` не означают, что `/health` должен отвечать ошибкой.
Процесс может быть жив, БД готова, а LLM недоступна. Для диагностики начинай
с `/health`, затем `/ready`, затем `/api/llm/status` и только после этого
генерации существующего обращения.

Ответ ошибки не следует пересылать модели для «исправления» автоматически:
это не выполнит недостающую настройку ключа и может создать дополнительные запросы.
В проекте нет скрытого перехода из ошибочного `openai` в успешный `mock`.

## 15. Почему тесты не требуют ключа и интернета

Проверки разделены по уровню:

1. **Настройки:** допустимые значения, пределы времени/токенов, обязательность ключа
   и модели только для внешнего режима, скрытие секрета.
2. **Контракт клиента:** mock, структурированный ответ, допустимые категории,
   проверка строки, usage и ошибок.
3. **SDK transport:** подмена HTTP-транспорта OpenAI SDK, чтобы проверить реальный
   формат вызываемого метода и обработку типовых ответов без обращения в сеть.
4. **HTTP:** статус LLM, корректный черновик, отсутствующее обращение, неверный ID,
   безопасные ошибки провайдера и ограничение контекста.
5. **PostgreSQL:** чтение существующего обращения и продукта, отсутствие изменений
   исходных данных и новых записей запуска/предложения.
6. **Контейнер:** новые маршруты доступны по настоящему HTTP в собранном образе,
   где включён mock.

Подмена транспорта отличается от вызова реального сервиса. Она проверяет,
как наш код формирует запрос и обрабатывает заданный ответ, но не подтверждает
доступность выбранной модели для аккаунта. Именно поэтому текущий CI воспроизводим
без API-ключей и затрат на генерацию.

Неверные настройки LLM дополнительно проверяются так, чтобы они не делали
неработоспособными `/health` и `/ready`. Публичный status не возвращает ключ
и не выполняет вызов модели.

## 16. Запустить проверки локально

Сначала запусти проверки исходников и unit-тесты:

```bash
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked python -m pytest -m 'not integration'
```

Для полного набора нужна отдельная тестовая PostgreSQL. Запусти только её:

```bash
docker compose --profile test up --detach --wait db-test
```

Затем явно укажи тестовый URL:

```bash
TEST_DATABASE_URL='postgresql+psycopg://support:support_ci@127.0.0.1:5434/ai_support_test' \
  uv run --locked python -m pytest
```

Здесь `5434` — тестовый порт по умолчанию. Если он изменён, исправь URL.
Тестовые сценарии могут сбрасывать схему и данные. Они допускаются только
для явно заданной отдельной базы с именем, заканчивающимся на `_test`.
Не подставляй `DATABASE_URL` development-базы вместо `TEST_DATABASE_URL`.

Без тестового URL интеграционные сценарии локально пропускаются; это не является
подтверждением полного набора. В CI отсутствие обязательной тестовой конфигурации
считается ошибкой. Успешный итог полного прогона должен указывать отсутствие
пропущенных интеграционных сценариев.

Новая миграция на этапе 04 не нужна: генерация читает существующие таблицы,
а результат не сохраняет. `alembic check` по-прежнему проверяет, что модели
не расходятся со схемой базы.

## 17. Smoke-проверка контейнера и CI

Обычный smoke по-прежнему проверяет HTTP и, с отдельными флагами, готовность БД
и чтение четырёх ресурсов API. Для LLM добавлен явный `--check-llm`, который
также включает проверки базы и API:

```bash
uv run --locked python scripts/smoke_test.py \
  --base-url http://127.0.0.1:8001 --timeout 30 --check-llm
```

Этот режим **создаёт три вымышленные записи** через HTTP: клиента, продукт и
обращение с уникальным суффиксом. Затем получает mock-черновик и повторно читает
обращение, чтобы проверить отсутствие изменения. Это действие самого smoke-скрипта;
маршрут генерации по-прежнему ничего не записывает. При локальном запуске три
созданные записи останутся в development-БД.

До первого POST скрипт читает `/api/llm/status` и требует одновременно
`provider: "mock"` и `configured: true`. При `openai` он останавливается до
создания учебных данных и генерации, чтобы эта проверка не запускала платный запрос.
Внутри CI mock задаётся явно, а ключ и имя внешней модели пусты.

Всего выполняются **14 HTTP-запросов**: прежние восемь проверок процесса, БД,
Swagger/OpenAPI и списков; статус LLM; три создания; генерация; повторное чтение
обращения. Также проверяется наличие двух новых операций в OpenAPI.

Подробности pipeline находятся в обновлённой [инструкции CI/CD](CI_CD.md).
Проверочный CI-стенд использует отдельный Compose-проект и временный том.
Его учебные записи удаляются вместе с этим проектом после проверки.

Порядок CI остаётся последовательным:

1. Установка зависимостей по lock-файлу.
2. Подъём тестовой PostgreSQL, миграции и проверка расхождений схемы.
3. Ruff, форматирование и полный Pytest, включая новые LLM-сценарии.
4. Сборка единственного Docker-образа.
5. Compose-проверка БД, API, mock-генерации и сохранности данных.
6. Публикация уже проверенного образа в GHCR при push в `main`.

API-ключ OpenAI для CI не требуется. Образ не пересобирается между проверкой
и публикацией. Успешный предыдущий запуск этапа 03 не подтверждает новый код:
этап 04 должен пройти собственный workflow для своего коммита.

## 18. Типичные затруднения

**В status остаётся mock после правки `.env`.** Пересоздай API-контейнер,
убедись, что редактируешь `.env` именно текущего репозитория и что переменная
не переопределена в терминале. Перезапуск старого контейнера не меняет его окружение.

**В status openai настроен, но генерация отвечает `503`.** Configured означает,
что настройки заполнены и допустимы. Проверь реальную доступность модели,
правильность ключа, квоту и сеть. Не публикуй ключ или полный конфигурационный вывод.

**`404` при генерации.** Проверь ID через `GET /api/tickets/{resource_id}`.
Идентификатор клиента или продукта не является ID обращения.

**`413`, хотя описание обращения короче 16 000 символов.** Ограничение применяется
ко всему подготовленному JSON: в него входят также название/код продукта,
приоритет, ID, ключи JSON и экранирование.
Число токенов и число символов — разные величины.

**`502` при очень маленьком бюджете ответа.** Структурированный ответ может
не успеть завершиться. Увеличение допустимого бюджета может помочь, но не гарантирует
успех и должно учитывать потребление API. При неверной модели проверь поддержку
используемого метода и схемы.

**В mock текст выглядит общим.** Это ожидаемо: локальная заглушка проверяет
контракт приложения и явно обозначает демонстрацию. Для оценки реального качества
нужен отдельный ручной прогон внешнего режима на подходящих данных.

**После успешного POST нет предложения в БД.** На этом этапе результат существует
только в HTTP-ответе. История запусков и согласование сохранённых предложений
ещё не подключены.

**Тесты прошли, но внешняя модель не работает.** Текущий автоматический набор
использует mock и подмену транспорта. Успех этих проверок не проверяет конкретный
внешний аккаунт; это отдельная ручная проверка после настройки ключа.

## 19. Как проверить готовность этапа

Этап готов локально, когда выполняются все наблюдаемые условия:

- Процесс и БД отвечают на `/health` и `/ready`.
- В status есть только безопасные метаданные LLM.
- Существующее обращение даёт структурированный mock-черновик по HTTP.
- Демонстрационный ответ явно помечен и требует проверки человеком.
- После генерации исходное обращение не меняется; запуска/предложения в БД не появляется.
- Неверные ID, слишком длинный контекст и ошибки модели возвращают ожидаемые безопасные ответы.
- Полный Pytest с отдельной PostgreSQL проходит без пропуска интеграции.
- Docker-образ проходит свою HTTP-проверку; CI для отправленного коммита проверяется отдельно.

Результаты конкретного прогона, число тестов, ограничения проверки внешнего
провайдера и состояние GitHub записываются в журнал, а не выводятся из этого списка.

## 20. Что изучать дальше

Следующий этап — агент с инструментами. Он должен получать данные клиента
и проверять лицензию через ограниченные функции приложения, хранить историю
запуска и предлагать оператору действие для согласования. Перед этим полезно
самостоятельно проследить текущий путь: маршрут → чтение БД → контекст → клиент
→ проверенная структура → HTTP-ответ.

RAG, индекс документов, голосовой интерфейс и автоматическая отправка ответов
не возникают от одного подключения LLM. У каждого из этих механизмов должны
появиться собственные контракты, проверки и понятный сценарий работы.
