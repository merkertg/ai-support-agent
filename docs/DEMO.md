# Демонстрация AI Support Agent

Цель показа — пройти понятную цепочку: обращение клиента → данные и лицензия →
документация → черновик агента → решение сотрудника → учебное сообщение.
Все продукты и участники сценария вымышлены. Режим `mock` работает без ключа
OpenAI; внешнее письмо не отправляется.

## 1. Подготовить перед показом

В корне проекта:

```bash
uv sync --locked --group ui
docker compose up --build --detach --wait --wait-timeout 180 ui
docker compose exec -T api python -m app.knowledge.ingest
uv run --locked python scripts/demo_scenario.py --url http://127.0.0.1:8001
```

В PowerShell на Windows ([аналоги команд](instructions/windows.md)):

```powershell
uv sync --locked --group ui
docker compose up --build --detach --wait --wait-timeout 180 ui
docker compose exec -T api python -m app.knowledge.ingest
uv run --locked python scripts/demo_scenario.py --url http://127.0.0.1:8001
```

Если `.env` ещё нет, сначала создай его по [быстрому запуску](instructions/quickstart.md).
Оставь `LLM_PROVIDER=mock` и `EMBEDDING_PROVIDER=mock`.
Сохрани выведенные `operator_id`, `customer_id`, `product_id`, `ticket_id`,
`run_id` и `suggestion_id`: они нужны для навигации в UI.

Команда уже создаёт pending-черновик. Повтор команды переиспользует записи;
после принятого решения не возвращает предложение в `pending`.
Для показа с чистого листа нужен отдельный учебный стенд, а не удаление
записей из рабочей БД. Подробности — [этап 10](STAGE_10.md).

## 2. План показа на 5–7 минут

| Время | Что показать | Что это доказывает |
| --- | --- | --- |
| 0:00–0:40 | Открыть UI, выбрать «Обзор», назвать используемые mock-провайдеры. | Приложение работает как единый локальный стенд; статистика считается сервером. |
| 0:40–1:40 | Ввести ID сотрудника, открыть `ticket_id` в «Обращениях», раскрыть клиента, продукт и лицензии. | Обращение связано с данными БД; UI читает их через API. |
| 1:40–3:00 | Открыть сохранённый `run_id`, показать итог, источники и трассу. | Агент читал тикет, клиента, историю, лицензию и базу знаний; сохранённый просмотр не запускает модель. |
| 3:00–4:00 | В «Базе знаний» найти статью по запросу о запуске сервера и коду `techflow-server`. | Видны текст фрагмента и исходный Markdown, по которому можно проверить рекомендацию. |
| 4:00–5:30 | В очереди открыть `suggestion_id`, исправить текст и явно одобрить его. | Ответ не уходит без человека; сохраняется утверждённая версия и автор решения. |
| 5:30–6:20 | Вернуться в обращение, показать `waiting_customer` и одно сообщение. | Решение продолжило граф и создало учебную доставку. |
| 6:20–7:00 | Открыть документацию и GitHub Actions конкретного коммита. | Есть воспроизводимые инструкции и результаты проверок, привязанные к версии кода. |

### Точный порядок в браузере

1. Открой [UI оператора](http://127.0.0.1:8502).
2. В боковой панели задай **ID сотрудника** = `operator_id` из сценария.
3. Выбери **Обращения**. В поле **Открыть обращение по ID** укажи `ticket_id`.
4. Раскрой **Клиент, продукт и лицензии**. Объясни, что ключи в таблице скрыты.
5. В истории открой `run_id`; покажи пять вызовов инструментов и маску `***`
   в аргументах `get_license`. Проверка должна показать `valid: true`.
6. Покажи ключи статей из `sources`. Это найденные документы, а не ссылка
   на несуществующий внешний источник.
7. Выбери **База знаний**: запрос `Сервер не запускается после обновления`,
   продукт `techflow-server`, затем **Найти статьи**. Раскрой подходящую статью.
8. Выбери **Очередь проверки** → **Ожидают проверки**. В поле
   **Открыть предложение по ID** укажи `suggestion_id`.
9. Прочитай и при необходимости исправь ответ. Выбери **Одобрить**, отметь
   подтверждение проверки и нажми **Сохранить решение**.
10. Вернись в карточку обращения. Проверь статус `waiting_customer` и одно
    сообщение оператора с утверждённым текстом.

Если для показа выбран отказ, вместо шага 9 укажи **Отклонить** и причину.
Тогда ожидается `rejected`, обращение остаётся `open`, нового сообщения нет.

## 3. Что объяснить простыми словами

**Агент** — цикл: модель просит разрешённый инструмент, сервер проверяет
аргументы и область доступа, выполняет чтение и возвращает результат.
Одна модель не получает произвольный SQL или функцию отправки письма.

**Поиск по документации** — Markdown-статьи разбиваются на фрагменты и
индексируются в Qdrant. Агент ищет фрагменты по своему продукту и общие статьи,
а итог сохраняет ключи реально найденных источников.

**LangGraph** — процесс, который останавливается на решении человека.
Ожидание хранится в PostgreSQL, поэтому перезапуск API не должен терять его.
Одобрение продолжает процесс до учебной доставки; отказ завершает его без неё.

**Mock** — предсказуемая демонстрация без платного запроса. Здесь он нужен,
чтобы проверить инструменты, сохранение, поиск и формы. Качество реальной
языковой модели по этому режиму не измеряется.

## 4. Автоматически проверить обе ветви

Для технического прогона на учебном стенде можно выполнить:

```bash
uv run --locked python scripts/demo_scenario.py \
  --url http://127.0.0.1:8001 --verify-review
```

В PowerShell на Windows ([аналоги команд](instructions/windows.md)):

```powershell
uv run --locked python scripts/demo_scenario.py `
  --url http://127.0.0.1:8001 --verify-review
```

Основной тикет остаётся человеку. На двух других тикетах скрипт проверяет
одобрение с одним сообщением и отклонение без сообщения. JSON содержит
`review_checks.approve` и `review_checks.reject` с ID и итоговыми состояниями.
Повторный запуск читает эти решения без повторного POST review.

## 5. Проверка готовности к показу

- `/ready` отвечает `200` с готовой БД.
- Статус модели показывает `mock`, статус эмбеддингов — `mock`.
- Индекс знаний `ready`, статьи проиндексированы.
- Первый демонстрационный запуск вернул `pending` / `awaiting_review`.
- UI открывает выведенные ID, а не условные числа из инструкции.
- Для выбранного коммита проверен результат **CI and GHCR**.
- В [VERIFICATION.md](VERIFICATION.md) перечислены фактически выполненные проверки.

## 6. Материалы для репозитория и скриншотов

Полезные кадры: обзор, карточка учебного обращения с источниками, pending-очередь,
утверждённое сообщение. Делай их на вымышленных данных после проверки UI
в настоящем браузере. Не включай `.env`, ключи API и реальные обращения.

Эта инструкция описывает кадры для съёмки; изображения добавляются только
после фактического получения и просмотра. Автоматические AppTest-проверки
не являются скриншотами браузера.

Документы для сопровождающего:
[интерфейс](STAGE_08.md), [оценки](STAGE_09.md), [упаковка](STAGE_10.md),
[CI/CD](CI_CD.md), [руководство PDF](guide/ai-support-agent-guide.pdf).

## 7. Что делать после демонстрации

Для продолжения разработки сначала выбери следующий проверяемый результат:

1. При появлении ключа отдельно проверить реальную модель и реальные
   эмбеддинги на вымышленных сценариях; сохранить стоимость, ошибки и качество.
2. Перед доступом реальных операторов добавить вход, роли и проверку доступа
   к каждой операции API.
3. При подключении настоящего email или helpdesk добавить надёжную доставку,
   учёт повторов, журнал попыток и тест отказа внешнего сервиса.
4. Для внешнего сервера отдельно настроить секреты, TLS, резервные копии,
   восстановление и наблюдение; текущий CD заканчивается публикацией в GHCR.

Историю учебного проекта и зелёный CI следует показывать как инженерные
результаты. Их не нужно выдавать за опыт работы с настоящими клиентами
или доказательство качества не проверенной реальной модели.
