# Восстановление брошенных запусков агента

## Какой сбой исправлен

Анализ сначала сохраняет `agent_runs.status = running`, затем обращается к
провайдеру и инструментам. Если процесс остановить между этими действиями и
финальной транзакцией, строка останется `running`, хотя анализ уже не работает.
Раньше такой запуск со временем переставал блокировать новый анализ, но сам
так и не получал конечный статус. Теперь сервер завершает его как `failed`.

Успешный запуск по-прежнему атомарно сохраняет `completed` и одно предложение
`pending`. Recovery не создаёт предложений, не принимает решение за оператора,
не меняет статус обращения и не отправляет сообщение клиенту. Уже имеющиеся
предложения завершённых запусков сохраняются.

## Шаг 1. Определить консервативную границу

Максимально разрешённый `AGENT_TIMEOUT_SECONDS` равен **120 секундам**. К нему
добавлен запас **60 секунд** для завершения SQL и краткой задержки worker.
Запуск считается брошенным, только если одновременно выполнены условия:

```text
status = running
started_at <= время PostgreSQL - 180 секунд
```

Используется верхняя граница 120, даже если текущий `.env` задаёт 60 или 1.
Иначе уменьшение настройки после рестарта могло бы слишком рано завершить
анализ, запущенный другим worker со старым допустимым лимитом. Unit-проверка
сопоставляет константу recovery с верхней границей Pydantic: изменение одного
предела требует изменить и другой. Сравнение и `finished_at` используют время
PostgreSQL, как и исходный `started_at`.

Порог включительный: ровно 180 секунд уже допускает recovery. Возраст
179,999 секунды ещё сохраняет `running`. При штатной работе таймера завершение
обычно происходит через 180–210 секунд; недоступная БД, занятая строка или
пауза процесса могут увеличить это время.

## Шаг 2. Автоматически завершать старые строки

Файл `app/services/run_recovery.py` содержит общий условный SQL `UPDATE`.
Он меняет только подходящие `running`-строки:

- `status` → `failed`;
- `finished_at` → время PostgreSQL;
- `error_message` → постоянный безопасный текст о прерванном запуске;
- `result` → SQL `NULL`.

Сохранённые `steps`, `tool_trace` и `usage` остаются для диагностики. Если
процесс упал до сохранения прогресса, recovery не может восстановить потерянные
шаги из памяти процесса. Анализ повторяется новым запросом оператора.

В API работают два пути вызова:

1. **Перед новым анализом того же обращения.** Под блокировкой `Ticket FOR
   UPDATE` recovery завершает старые строки, после чего сервер повторно
   проверяет отсутствие активного анализа и ожидающего предложения. Новый
   запуск и завершение старого фиксируются одной транзакцией. Ошибка откатывает
   всю эту транзакцию; фоновый проход сможет повторить recovery позднее.
2. **Каждые 30 секунд, даже без новых запросов.** Lifespan создаёт одну фоновую
   задачу на процесс API. Первый проход идёт через 30 секунд: импорт приложения
   и старт `/health` сами по себе не требуют соединения. SQL выполняется в
   отдельном потоке и не блокирует обработку HTTP event loop.

Ни один путь не запускает миграции и не вызывает LLM. База должна быть уже
подготовлена штатным сервисом `migrate`.

## Шаг 3. Не перезаписать успешный результат при гонке

Условие `status = running` входит в сам `UPDATE`, а не только в отдельный
предварительный `SELECT`. PostgreSQL повторно проверяет его после ожидания
блокировки. Если другой worker успел сохранить `completed`, recovery пропустит
эту строку.

Обратную гонку закрывает `finish_run`: он блокирует строку запуска через
`FOR UPDATE`, заново читает её и сохраняет результат только при `running`.
Если recovery уже зафиксировал `failed`, поздно вернувшийся worker получает
HTTP `409` с `run_id`, а новый `pending` не создаётся. Повторного вызова
`finish_run` для этого `409` нет. Аналогично защищены уже завершённые запуски.

Несколько процессов API могут выполнять монитор одновременно: изменит строку
только первый подходящий `UPDATE`, остальные получат пустой список изменений.
Дополнительная очередь, Redis, cron и миграция схемы для этого не нужны.

## Шаг 4. Ограничить SQL и корректно остановить монитор

Каждый recovery использует локальные настройки текущей транзакции:

```sql
SET LOCAL statement_timeout = '3s';
SET LOCAL lock_timeout = '1s';
```

Слишком долго занятая строка или недоступная БД приводят к откату, а не к
бесконечному ожиданию. Фоновый проход запишет безопасное событие об ошибке и
повторится на следующем тике. В начале нового анализа SQL-ошибка проходит
через существующий обработчик API с HTTP `503`.

При shutdown stop-событие немедленно прерывает ожидание следующего тика.
Если SQL уже выполняется, lifespan ждёт завершения ограниченного прохода,
и только затем закрывает пул PostgreSQL и checkpointer. Отдельного worker,
который продолжает recovery после закрытия пула, не остаётся.

## Шаг 5. Настройка и наблюдение

По умолчанию монитор включён:

```dotenv
RUN_RECOVERY_ENABLED=true
```

`false` отключает только фоновый таймер. Проверка брошенных запусков перед
новым анализом того же обращения остаётся активной. После изменения настройки
пересоздай процесс/контейнер API. В обычном стенде оставь значение `true`.

Успешный commit записывает JSON-событие `agent_run_recovered` с `run_id`,
`ticket_id` и `status = failed`. Неудачный проход — `agent_run_recovery_failed`
с классом ошибки и SQLSTATE, если он доступен. Ключи лицензий, адрес БД,
параметры SQL, текст обращения и содержимое ответа в эти события не входят.
Пустой проход не создаёт лишних сообщений.

Посмотреть логи API:

```bash
docker compose logs --since 10m api
```

Посмотреть известный запуск:

```bash
curl --fail-with-body --header "Authorization: Bearer $API_TOKEN" \
  http://127.0.0.1:8001/api/agent-runs/1
```

Подставь настоящий `run_id`. Для восстановленного запуска ожидаются `failed`,
непустые `finished_at`/`error_message`, `result: null` и `suggestion: null`.
Новый анализ выполняется обычной кнопкой интерфейса или `POST /analyze`.
Если у старого запуска есть поток LangGraph, чтение workflow штатно выровняет
его checkpoint по конечному `failed`; recovery не повторяет анализ и доставку.

## Шаг 6. Проверки и изоляция тестов

`tests/test_run_recovery.py` проверяет порог, условный SQL, ограничения,
отсутствие изменения terminal-статусов, безопасный журнал, остановку до первого
тика и ожидание уже выполняющегося SQL при shutdown. Сам SQL в этих unit-тестах
подменён: рабочая БД не используется.

`tests/integration/test_abandoned_runs.py` работает только через проверенный
`TEST_DATABASE_URL` с суффиксом `_test` и штатные миграции Alembic. Он проверяет:

- ровно 180 секунд и соседнюю ещё допустимую границу;
- сохранение `pending` у завершённого запуска и отсутствие автоматической
  доставки;
- ограничение одним обращением, идемпотентность и возврат соединений в пул;
- запрет позднего сохранения после recovery;
- победу успешного завершения, в том числе реальное ожидание блокировки двумя
  соединениями PostgreSQL и повторную проверку `WHERE`;
- уменьшение настройки времени после запуска другого worker;
- новый анализ после прерванного, один новый `pending` и ноль сообщений;
- фоновый проход без нового HTTP-запроса.

Общая autouse-фикстура в `tests/conftest.py` отключает фоновый монитор у всех
`TestClient`, чтобы длительный тест не прочитал `DATABASE_URL` из локального
`.env` и не изменил development-БД. Проверки монитора включают его явно и
подменяют SQL; интеграционные проверки передают только тестовый движок.

Команды из корня проекта:

```bash
uv run --frozen pytest tests/test_run_recovery.py -q
# TEST_DATABASE_URL должен указывать на отдельную БД *_test.
uv run --frozen pytest tests/integration/test_abandoned_runs.py -q
```

Интеграционные тесты сбрасывают схему своей тестовой БД. Их нельзя запускать
параллельно с другим прогоном, использующим ту же БД. Полные результаты
проверки проекта записываются в `docs/VERIFICATION.md`.
