# Этап 03. HTTP API клиентов, продуктов, лицензий и обращений

На этом этапе мы начинаем работать с данными через HTTP. Прежде записи можно было создать учебной командой
`python -m app.db.demo seed`. Теперь клиент отправляет JSON, приложение проверяет его, сохраняет запись в
PostgreSQL и возвращает результат с присвоенным идентификатором.

Инструкция рассчитана на последовательное выполнение. У каждого шага указаны цель, команда или файл и
ожидаемый результат. Фактические результаты проверки этой версии записываются в
[журнале разработки](DEVELOPMENT_LOG.md). Устройство базы, миграций и томов подробно разобрано в
[этапе 02](STAGE_02.md), а весь pipeline — в [инструкции CI/CD](CI_CD.md).

## 1. Какой результат получаем

Работают четыре ресурса:

- `customers` — клиенты поддержки;
- `products` — продукты;
- `licenses` — лицензии клиента на продукт;
- `tickets` — обращения клиента по продукту.

У каждого ресурса есть три операции: создать запись, получить список и прочитать запись по ID. Всего —
12 HTTP-операций. Новая запись сохраняется в той же PostgreSQL, что была подключена на этапе 02.

Это создание и чтение данных. Изменение, удаление, авторизация, сообщения в обращениях, запуск AI-агента,
RAG и работа оператора относятся к следующим этапам. Таблицы для части будущих возможностей уже существуют,
но сам по себе этот факт не создаёт соответствующие HTTP-операции.

Новая миграция не требуется: используются существующие таблицы `customers`, `products`, `licenses`, `tickets`.
Alembic по-прежнему отвечает за структуру БД; запуск FastAPI не вызывает `create_all()`.

## 2. Как запрос проходит через приложение

```text
curl / Swagger / будущий интерфейс
              │ HTTP + JSON
              ▼
FastAPI router: адрес, метод, параметры, код ответа
              │
              ▼
Pydantic schema: проверка тела, строк, ID, e-mail и дат
              │
              ▼
Service: существование связанных записей, SQL-запрос, commit
              │
              ▼
SQLAlchemy Session → psycopg → PostgreSQL
              │
              ▼
Pydantic response schema → JSON + HTTP-статус
```

Например, при создании лицензии:

1. FastAPI принимает `POST /api/licenses`.
2. Схема проверяет положительные ID, непустой ключ лицензии, допустимый статус и даты с часовым поясом.
3. Сервис проверяет, что указанные клиент и продукт существуют.
4. SQLAlchemy отправляет `INSERT` в PostgreSQL.
5. PostgreSQL проверяет внешние ключи и уникальность ключа лицензии.
6. Сервис подтверждает транзакцию; ответ содержит ID и сохранённые значения.
7. Следующий `GET` читает запись из БД новой сессией.

Схемы Pydantic и модели SQLAlchemy решают разные задачи. Схема описывает входной/выходной HTTP JSON, модель
описывает таблицу. Например, `TicketCreate` не разрешает поле `status`, хотя колонка `tickets.status`
существует: для нового обращения сервер сам использует `open`.

причины проверок; имя функции и аннотация типа помогают увидеть, какие данные она принимает и возвращает.

## 4. Подготовить проект и запустить стенд

**Цель:** обновить зависимости и запустить образ с новым кодом, готовой БД и применённой миграцией.

Открой терминал в корне проекта:

```bash
cd '/Users/arslanbakiev/Desktop/AI Forge/ai-support-agent'
```

На другом компьютере замени путь на свою папку репозитория. В ней должны находиться `pyproject.toml`,
`compose.yaml` и `Dockerfile`.

Сначала проверь, что `uv` доступен в текущем терминале через `PATH`:

```bash
uv --version
```

Затем установи зависимости из lock-файла:

```bash
uv sync --locked
```

Если команда `uv` не найдена, восстанови её доступность или установи инструмент по ссылке из
[инструкции быстрого запуска](instructions/quickstart.md). После изменения зависимостей нужен успешный `uv sync --locked`: наличие папки
`.venv` само по себе ещё не означает, что в ней установлены новые библиотеки.

Если окружение уже обновлено и нужно выполнить только Python-команды примеров, можно заменить
`uv run --locked python` на `.venv/bin/python`. Например, вместо
`uv run --locked python -m json.tool ответ.json` выполнить
`.venv/bin/python -m json.tool ответ.json`. Этот способ запускает существующее окружение, но не устанавливает
и не синхронизирует зависимости; он не заменяет шаг установки выше.

Для проверки e-mail используется `EmailStr` и библиотека `email-validator`. Это проверка формата адреса;
письмо для подтверждения владения почтой не отправляется. Версии устанавливаются по `uv.lock`.

Создай `.env` только при его отсутствии:

```bash
if [ ! -f .env ]; then
  cp .env.example .env
fi
```

При существующем `.env` сравни его настройки с `.env.example`. Текущие стандартные порты: API `8001`,
PostgreSQL для приложения на Mac `5433`, отдельная тестовая БД `5434`. Внутри Compose API обращается к
PostgreSQL по имени сервиса `db:5432`.

Собери и запусти приложение:

```bash
docker compose up --build --detach --wait --wait-timeout 90 api
```

**Ожидаемый результат:** `db` становится `healthy`, `migrate` успешно завершает `alembic upgrade head`, затем
`api` становится `healthy`. При повторном запуске уже применённая миграция не создаёт таблицы заново.

Посмотри состояние и проверь готовность:

```bash
docker compose ps --all
curl --silent --show-error --fail-with-body http://127.0.0.1:8001/ready
```

Ожидаемый JSON:

```json
{"status":"ok","database":"ok"}
```

Если в `.env` изменён `API_PORT`, используй его во всех URL ниже. Для варианта с Uvicorn на Mac адрес обычно
`http://127.0.0.1:8000`; команда запуска и различие URL базы разобраны в [этапе 02](STAGE_02.md).

## 5. Все HTTP-операции

| Метод | Путь | Результат |
| --- | --- | --- |
| `POST` | `/api/customers` | Создать клиента; `201`. |
| `GET` | `/api/customers` | Массив клиентов; `200`. |
| `GET` | `/api/customers/{resource_id}` | Один клиент; `200`, отсутствующий — `404`. |
| `POST` | `/api/products` | Создать продукт; `201`. |
| `GET` | `/api/products` | Массив продуктов; `200`. |
| `GET` | `/api/products/{resource_id}` | Один продукт; `200`, отсутствующий — `404`. |
| `POST` | `/api/licenses` | Создать лицензию; `201`. |
| `GET` | `/api/licenses` | Массив лицензий с необязательными фильтрами; `200`. |
| `GET` | `/api/licenses/{resource_id}` | Одна лицензия; `200`, отсутствующая — `404`. |
| `POST` | `/api/tickets` | Создать обращение; `201`. |
| `GET` | `/api/tickets` | Массив обращений с необязательными фильтрами; `200`. |
| `GET` | `/api/tickets/{resource_id}` | Одно обращение; `200`, отсутствующее — `404`. |

Обрати внимание на префикс `/api`. Проверки `/health` и `/ready`, а также Swagger `/docs` остаются без него.

Создание возвращает один объект. Список возвращает простой JSON-массив, а не объект с полями `items` и
`total`. Если подходящих записей нет, успешный список имеет вид `[]`.

## 6. Какие данные разрешено отправлять

### 6.1. Общие правила

- Неизвестные поля в JSON запрещены: опечатка или поле, которым управляет сервер, приводят к `422`.
- Пробелы в начале и конце строк убираются. Обязательная строка после этого должна оставаться непустой.
- `null` и отсутствующее поле — разные вещи. Если поле обязательное, оба варианта не проходят проверку.
  У необязательных полей `company`, `description` продукта и `expires_at` разрешён `null`.
- ID — положительное целое число от `1` до `9223372036854775807`, в пределах PostgreSQL `BIGINT`.
  В JSON поля `customer_id` и `product_id` принимают только целые числа: строка `"1"`, число `1.0`
  и логическое `true` дают `422`. В пути и query целое число передаётся текстом как часть URL.
- Поля `id` и серверные timestamps не присылай при создании. Особый случай — дата выдачи лицензии:
  её можно передать явно или дать серверу выбрать текущее время.
- Вложенные объекты клиента и продукта в ответ не разворачиваются. В лицензии и обращении возвращаются
  `customer_id` и `product_id`; подробности доступны отдельными `GET`.

### 6.2. Клиент

Тело `POST /api/customers`:

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `name` | Да | Непустая строка, до 200 символов. |
| `email` | Да | Адрес в формате e-mail до 320 символов; уникальность проверяется БД. |
| `company` | Нет | Непустая строка до 200 символов или `null`. |

Ответ содержит `id`, `name`, `email`, `company`, `created_at`.

### 6.3. Продукт

Тело `POST /api/products`:

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `name` | Да | Непустая строка, до 200 символов. |
| `code` | Да | Непустой уникальный код, до 64 символов. |
| `description` | Нет | Непустой текст до 10 000 символов или `null`. |

Ответ содержит `id`, `name`, `code`, `description`, `created_at`.

### 6.4. Лицензия

Тело `POST /api/licenses`:

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `customer_id` | Да | ID существующего клиента. |
| `product_id` | Да | ID существующего продукта. |
| `license_key` | Да | Непустая уникальная строка, до 255 символов. |
| `status` | Нет | `active`, `expired` или `revoked`; по умолчанию `active`. |
| `issued_at` | Нет | Дата со временем и часовым поясом; если поле отсутствует, выбирается текущее время UTC. Явный `null` запрещён. |
| `expires_at` | Нет | Дата со временем и часовым поясом или `null`; не раньше `issued_at`. |

Примеры даты: `2026-10-18T10:00:00Z` или `2026-10-18T15:00:00+05:00`.
`2026-10-18T10:00:00` без часового пояса не подходит. PostgreSQL хранит момент времени; текстовое
представление часового пояса при чтении может отличаться, хотя сам момент остаётся тем же.

Если задаёшь `expires_at`, можно явно задать и `issued_at`, чтобы порядок дат был очевиден.
Если срока окончания нет, передай `null` или опусти `expires_at`.

Ответ содержит `id`, `customer_id`, `product_id`, `license_key`, `status`, `issued_at`, `expires_at`.
Статус сохраняется как указанное значение. Автоматический перевод `active` в `expired` по расписанию
на этом этапе не реализован.

### 6.5. Обращение

Тело `POST /api/tickets`:

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `customer_id` | Да | ID существующего клиента. |
| `product_id` | Да | ID существующего продукта. |
| `subject` | Да | Непустая тема, до 300 символов. |
| `description` | Да | Непустое описание, до 10 000 символов. |
| `priority` | Нет | `low`, `medium`, `high` или `critical`; по умолчанию `medium`. |

Ответ содержит `id`, `customer_id`, `product_id`, `subject`, `description`, `priority`, `status`,
`created_at`, `updated_at`.

Новое обращение всегда получает `status: "open"`. Поле `status` во входном JSON запрещено: создание записи
ещё не является API изменения её жизненного цикла. Наличие активной лицензии не является условием создания
обращения; проверка прав клиента на поддержку и будущие действия агента — отдельные задачи.

## 7. Пройти сценарий через Swagger

**Цель:** увидеть запрос и ответ без написания отдельной клиентской программы.

1. Открой [Swagger](http://127.0.0.1:8001/docs).
2. Найди `POST /api/customers`, нажми **Try it out**.
3. Укажи вымышленные `name`, уникальный `email`, при желании `company`; нажми **Execute**.
4. Убедись, что `Server response` показывает `201`. Скопируй `id` из JSON.
5. Аналогично создай продукт через `POST /api/products`; сохрани его `id`.
6. В `POST /api/licenses` подставь **полученные** `customer_id` и `product_id` и новый `license_key`.
7. В `POST /api/tickets` используй те же ID, тему и описание. Поле `status` добавлять не нужно.
8. Прочитай каждую запись через её `GET /api/.../{id}`.
9. В `GET /api/licenses` или `GET /api/tickets` задай фильтр `customer_id`.

Не полагайся на ID `1`: в БД уже могут быть записи от этапа 02 или предыдущего прохода этой инструкции.
Повторный `POST` с тем же e-mail, кодом продукта или ключом лицензии вернёт `409`; для нового сценария
выбирай новые значения.

Swagger показывает текущую схему конкретного запущенного приложения. Если новых адресов нет, переходи к
разделу устранения ошибок: частая причина — ранее собранный образ без новой версии кода.

## 8. Полный воспроизводимый сценарий через curl

**Цель:** создать связанную цепочку из четырёх записей и затем прочитать сохранённые данные.

Команды ниже выполняй **в одном окне терминала**: следующие шаги используют переменные предыдущих. Все
данные вымышленные. Случайный суффикс позволяет повторять сценарий без конфликта уникальных значений.

### 8.1. Подготовить адрес, суффикс и папку результатов

```bash
API_URL='http://127.0.0.1:8001'
EXAMPLE_KEY="$(uv run --locked python -c 'from uuid import uuid4; print(uuid4().hex[:12])')"
EXAMPLE_DIR="$(mktemp -d "${TMPDIR:-/tmp}/ai-support-stage03.XXXXXX")"
printf 'Результаты: %s\n' "$EXAMPLE_DIR"
```

`API_URL` — адрес сервера, `EXAMPLE_KEY` — случайная строка из букв и цифр, `EXAMPLE_DIR` — временная папка
для JSON-ответов. Эта папка не попадает в Git.

### 8.2. Создать клиента

```bash
curl --silent --show-error --fail-with-body \
  --request POST "$API_URL/api/customers" \
  --header 'Content-Type: application/json' \
  --data "{\"name\":\"Учебный клиент\",\"email\":\"learner-$EXAMPLE_KEY@example.com\",\"company\":\"Учебная компания\"}" \
  --output "$EXAMPLE_DIR/customer.json" \
  --write-out 'HTTP %{http_code}\n'
uv run --locked python -m json.tool "$EXAMPLE_DIR/customer.json"
CUSTOMER_ID="$(uv run --locked python -c 'import json, sys; print(json.load(open(sys.argv[1]))["id"])' "$EXAMPLE_DIR/customer.json")"
```

**Ожидаемый результат:** `HTTP 201`, объект клиента, положительный `id`, серверная дата `created_at`.
Переменная `CUSTOMER_ID` получает именно ID из ответа. Если `curl` завершился ошибкой, сначала исправь её;
не продолжай извлечение ID из ответа об ошибке.

### 8.3. Создать продукт

```bash
curl --silent --show-error --fail-with-body \
  --request POST "$API_URL/api/products" \
  --header 'Content-Type: application/json' \
  --data "{\"name\":\"Учебный сервер\",\"code\":\"training-$EXAMPLE_KEY\",\"description\":\"Продукт для проверки HTTP API\"}" \
  --output "$EXAMPLE_DIR/product.json" \
  --write-out 'HTTP %{http_code}\n'
uv run --locked python -m json.tool "$EXAMPLE_DIR/product.json"
PRODUCT_ID="$(uv run --locked python -c 'import json, sys; print(json.load(open(sys.argv[1]))["id"])' "$EXAMPLE_DIR/product.json")"
```

**Ожидаемый результат:** `HTTP 201` и сохранённый продукт. `PRODUCT_ID` извлекается из ответа, как и ID клиента.

### 8.4. Создать лицензию

```bash
LICENSE_KEY="TRAINING-$EXAMPLE_KEY"
curl --silent --show-error --fail-with-body \
  --request POST "$API_URL/api/licenses" \
  --header 'Content-Type: application/json' \
  --data "{\"customer_id\":$CUSTOMER_ID,\"product_id\":$PRODUCT_ID,\"license_key\":\"$LICENSE_KEY\",\"status\":\"active\",\"expires_at\":null}" \
  --output "$EXAMPLE_DIR/license.json" \
  --write-out 'HTTP %{http_code}\n'
uv run --locked python -m json.tool "$EXAMPLE_DIR/license.json"
LICENSE_ID="$(uv run --locked python -c 'import json, sys; print(json.load(open(sys.argv[1]))["id"])' "$EXAMPLE_DIR/license.json")"
```

**Ожидаемый результат:** `HTTP 201`, собственный ID лицензии, переданные ID клиента и продукта, статус
`active`. Поле `issued_at` заполняется текущим временем; `expires_at` остаётся `null`.

Числовые ID в JSON отправляются без кавычек. В ответе `customer_id` и `product_id` должны совпасть с
переменными, полученными на предыдущих шагах.

### 8.5. Создать обращение

```bash
curl --silent --show-error --fail-with-body \
  --request POST "$API_URL/api/tickets" \
  --header 'Content-Type: application/json' \
  --data "{\"customer_id\":$CUSTOMER_ID,\"product_id\":$PRODUCT_ID,\"subject\":\"Сервер не запускается\",\"description\":\"После обновления служба завершается с ошибкой. Нужна проверка журнала.\",\"priority\":\"high\"}" \
  --output "$EXAMPLE_DIR/ticket.json" \
  --write-out 'HTTP %{http_code}\n'
uv run --locked python -m json.tool "$EXAMPLE_DIR/ticket.json"
TICKET_ID="$(uv run --locked python -c 'import json, sys; print(json.load(open(sys.argv[1]))["id"])' "$EXAMPLE_DIR/ticket.json")"
```

**Ожидаемый результат:** `HTTP 201`, приоритет `high`, статус `open`, серверные `created_at` и `updated_at`.
AI-ответ на обращение пока не создаётся.

### 8.6. Прочитать каждую запись по её ID

```bash
curl --silent --show-error --fail-with-body "$API_URL/api/customers/$CUSTOMER_ID"
printf '\n'
curl --silent --show-error --fail-with-body "$API_URL/api/products/$PRODUCT_ID"
printf '\n'
curl --silent --show-error --fail-with-body "$API_URL/api/licenses/$LICENSE_ID"
printf '\n'
curl --silent --show-error --fail-with-body "$API_URL/api/tickets/$TICKET_ID"
printf '\n'
```

**Ожидаемый результат:** четыре JSON-объекта с теми же ID и значениями, которые вернуло создание.
Это отдельные HTTP-запросы: чтение выполняется после подтверждения транзакций записи.

### 8.7. Получить списки и применить фильтры

```bash
curl --silent --show-error --fail-with-body \
  --get "$API_URL/api/licenses" \
  --data-urlencode "customer_id=$CUSTOMER_ID" \
  --data-urlencode "product_id=$PRODUCT_ID" \
  --data-urlencode "license_key=$LICENSE_KEY" \
  --data-urlencode 'limit=20' \
  --data-urlencode 'offset=0'
printf '\n'
curl --silent --show-error --fail-with-body \
  --get "$API_URL/api/tickets" \
  --data-urlencode "customer_id=$CUSTOMER_ID" \
  --data-urlencode "product_id=$PRODUCT_ID" \
  --data-urlencode 'status=open'
printf '\n'
```

**Ожидаемый результат:** JSON-массивы. В первом есть созданная лицензия, во втором — созданное обращение.
Фильтры сочетаются через **И**: запись должна удовлетворять каждому переданному условию.

`--get` помещает параметры в query URL; `--data-urlencode` корректно кодирует их значения.
Это не тело JSON. Такой способ удобен для ключей лицензий со специальными символами.

## 9. Списки, фильтры и постраничное чтение

Общие параметры всех четырёх списков:

| Параметр | Значение по умолчанию | Ограничение |
| --- | --- | --- |
| `limit` | `20` | От `1` до `100` записей. |
| `offset` | `0` | Целое число от `0` до `9223372036854775807`. |

Записи упорядочиваются по `id` по возрастанию. `offset=20&limit=20` пропускает первые двадцать подходящих
записей и возвращает следующие двадцать. Если записей меньше, массив короче; после конца списка будет `[]`.
Отдельное общее количество записей в ответе не возвращается.

```bash
curl --silent --show-error --fail-with-body \
  'http://127.0.0.1:8001/api/customers?limit=20&offset=0'
curl --silent --show-error --fail-with-body \
  'http://127.0.0.1:8001/api/products?limit=20&offset=20'
```

Кавычки вокруг URL сохраняют `&` частью адреса. Без них оболочка может разобрать команду иначе.

Дополнительные фильтры:

| Список | Фильтры |
| --- | --- |
| `/api/customers` | Только общие `limit`, `offset`. |
| `/api/products` | Только общие `limit`, `offset`. |
| `/api/licenses` | `customer_id`, `product_id`, точное совпадение `license_key`. |
| `/api/tickets` | `customer_id`, `product_id`, `status`. |

Для фильтра обращений допустимы `open`, `in_progress`, `waiting_customer`, `resolved`, `closed`. Новые
обращения этого этапа создаются как `open`; другие значения поддерживаются схемой и чтением существующих
записей, но HTTP-операций перевода между статусами ещё нет.

Фильтр ограничивает результат SQL-запроса и не требует отдельного существования клиента или продукта.
Если положительный ID не соответствует ни одной записи, список возвращает `200` и `[]`. Это отличается
от `GET /api/.../{resource_id}`, где запрашивается конкретный объект и его отсутствие означает `404`,
и от создания лицензии/обращения, где отсутствующая связанная запись также означает `404`.
Неизвестный статус, `limit=0`, `limit=101`, `offset` вне допустимого диапазона или неверный ID дают `422`.

## 10. Ошибки и как их понимать

| HTTP | Значение | Пример | Что сделать |
| --- | --- | --- | --- |
| `200` | Чтение успешно | Запись или список прочитаны. | Использовать JSON-ответ. |
| `201` | Создание успешно | Клиент сохранён. | Сохранить возвращённый ID. |
| `404` | Запись отсутствует | Неверный ID записи, клиента или продукта. | Прочитать существующие данные и подставить их ID. |
| `409` | Конфликт уникальности | Тот же e-mail, код продукта или ключ лицензии. | Прочитать существующую запись либо выбрать новое значение. |
| `422` | Некорректный запрос | Пустое имя, e-mail без формата, неправильная дата, лишнее поле, неверный query-параметр. | Исправить поле из `detail`. |
| `503` | БД не готова или недоступна | Ошибка подключения, настройки или SQL-доступа. | Проверить Compose, `/ready`, миграции и логи. |

У предметной ошибки ответ обычно содержит текстовое поле `detail`, например:

```json
{"detail":"..."}
```

У стандартной ошибки валидации FastAPI `detail` — массив описаний. Поле `loc` показывает место ошибки:
`body` относится к JSON, `query` к параметрам URL, `path` к ID в пути. Точный текст диагностики может
зависеть от типа проверки; ориентируйся на HTTP-код, `loc` и правило поля.

### 10.1. Проверить ошибку формата e-mail

В том же терминале, где заданы `API_URL` и `EXAMPLE_DIR`:

```bash
curl --silent --show-error \
  --request POST "$API_URL/api/customers" \
  --header 'Content-Type: application/json' \
  --data '{"name":"Проверка валидации","email":"это-не-email"}' \
  --output "$EXAMPLE_DIR/invalid-email.json" \
  --write-out 'HTTP %{http_code}\n'
uv run --locked python -m json.tool "$EXAMPLE_DIR/invalid-email.json"
```

**Ожидаемый результат:** `HTTP 422`, в диагностике указан `email`. На этом шаге отсутствие
`--fail-with-body` намеренное: мы проверяем ожидаемый ошибочный HTTP-код и хотим сохранить ответ.

### 10.2. Проверить конфликт

Повтори создание клиента с тем же e-mail, который уже сохранён в шаге 8:

```bash
curl --silent --show-error \
  --request POST "$API_URL/api/customers" \
  --header 'Content-Type: application/json' \
  --data "{\"name\":\"Повторный клиент\",\"email\":\"learner-$EXAMPLE_KEY@example.com\"}" \
  --output "$EXAMPLE_DIR/duplicate.json" \
  --write-out 'HTTP %{http_code}\n'
uv run --locked python -m json.tool "$EXAMPLE_DIR/duplicate.json"
```

**Ожидаемый результат:** `HTTP 409`. Существующий клиент не перезаписывается. Создание не является
операцией обновления или автоматическим поиском с последующим возвратом старой записи.

### 10.3. Проверить серверное поле статуса

```bash
curl --silent --show-error \
  --request POST "$API_URL/api/tickets" \
  --header 'Content-Type: application/json' \
  --data "{\"customer_id\":$CUSTOMER_ID,\"product_id\":$PRODUCT_ID,\"subject\":\"Проверка\",\"description\":\"Поле status нельзя прислать\",\"status\":\"closed\"}" \
  --output "$EXAMPLE_DIR/extra-status.json" \
  --write-out 'HTTP %{http_code}\n'
uv run --locked python -m json.tool "$EXAMPLE_DIR/extra-status.json"
```

**Ожидаемый результат:** `HTTP 422`, запрещённое дополнительное поле `status`. Аналогично не нужно

## 11. Что происходит с транзакцией

**Сессия** — рабочий объект SQLAlchemy для запросов к БД. **Транзакция** — группа изменений, которую можно
подтвердить целиком (`commit`) или отменить (`rollback`).

Один HTTP-запрос получает свою сессию через `get_api_session`. Зависимость использует базовый `get_session`
этапа 02 и закрывает сессию после запроса. Для записи сервис явно вызывает `commit`; скрытого commit
после любого GET или POST в зависимости нет.

При успешном создании сервер возвращает запись после подтверждения транзакции. Поэтому `201` означает,
что запись действительно сохранена, а не просто добавлена в список объектов Python. Последующий запрос
использует другую сессию и читает PostgreSQL.

Ошибка до успешного commit приводит к откату незавершённой транзакции. Например, два клиента не могут занять одно и то же уникальное значение
`email`: ограничение БД защищает данные и при одновременных запросах. Проверка в Python сама по себе не
заменила бы это ограничение, потому что между проверкой и INSERT другой запрос мог бы записать такое же
значение.

После commit сервис обновляет ORM-объект через `refresh`, чтобы получить присвоенные БД значения.
Если БД станет недоступна именно после подтверждения, HTTP-запрос может завершиться `503`, хотя запись
уже сохранена: последующий rollback не отменяет успешный commit. При таком сбое проверь списки по
уникальному значению, прежде чем считать повторный POST созданием новой записи. Отдельного ключа
идемпотентности для POST на этом этапе нет.

Внешние ключи также защищают связи. Сервис даёт понятную ошибку для отсутствующего клиента/продукта,
а БД дополнительно не допускает сохранения некорректной ссылки.

Ошибки подключения и SQL-доступа превращаются в безопасный `503`. HTTP-ответ не копирует исключение
драйвера с URL подключения и паролем. Диагностику состояния стенда начинай с `/ready` и Compose-логов.

## 12. Проверить сохранность HTTP-данных

**Цель:** убедиться, что созданные через API данные переживают пересоздание контейнеров.

Заверши создание и чтение из шага 8, затем в том же терминале:

```bash
curl --silent --show-error --fail-with-body \
  "$API_URL/api/licenses/$LICENSE_ID" \
  --output "$EXAMPLE_DIR/license-before.json"
docker compose down
docker compose up --detach --no-build --wait --wait-timeout 90 api
curl --silent --show-error --fail-with-body \
  "$API_URL/api/licenses/$LICENSE_ID" \
  --output "$EXAMPLE_DIR/license-after.json"
cmp "$EXAMPLE_DIR/license-before.json" "$EXAMPLE_DIR/license-after.json"
```

**Ожидаемый результат:** после повторного `up` API снова готово, `cmp` завершается с кодом `0` без вывода:
ответы совпадают. Между `down` и чтением **не выполняется новый POST**. Иначе повторная запись могла бы
скрыть потерю старых данных.

Обычный `docker compose down` удаляет контейнеры и сеть, но сохраняет именованный том PostgreSQL.
Для этого сценария не добавляй `--volumes` или `-v`: они удаляют хранилище. Удаление томов отдельного
одноразового проекта в CI имеет другую цель — завершить и очистить тестовую среду.

Этот шаг останавливает сервисы текущего Compose-проекта. Если в это время запущены интеграционные тесты
с его `db-test`, сначала дождись завершения тестов.

## 13. Проверить код и полный набор тестов

### 13.1. Статические проверки

**Цель:** проверить ошибки Python и единый формат.

```bash
uv run --locked ruff check .
uv run --locked ruff format --check .
```

Ожидаемый результат: оба процесса завершаются с кодом `0`. Эти команды только проверяют формат;
`ruff format --check` не изменяет файлы.

### 13.2. Отдельная настоящая PostgreSQL для тестов

**Цель:** проверить HTTP-операции и ограничения на реальной БД, сохранив данные development-базы.

```bash
docker compose --profile test up --detach --wait db-test
TEST_DATABASE_URL='postgresql+psycopg://support:support_ci@127.0.0.1:5434/ai_support_test' \
  uv run --locked pytest -v
```

Если `POSTGRES_TEST_PORT` изменён, замени `5434` на выбранный порт. Тесты берут адрес именно из
`TEST_DATABASE_URL`, а не из development `DATABASE_URL`. Имя базы должно оканчиваться на `_test`.

Интеграционные fixtures удаляют и заново создают тестовую схему через миграции Alembic. Поэтому в URL должна
быть отдельная одноразовая БД. Подставлять обычную `ai_support` нельзя. Защитная проверка имени остановит
такой запуск, но назначение адреса всё равно нужно выбирать осознанно.

Не запускай два набора интеграционных тестов одновременно против одной и той же `ai_support_test`: они
сбрасывают общую схему и будут мешать друг другу. Запускай набор последовательно либо используй разные
одноразовые БД.

Полный набор охватывает старую основу и новый API: настройки, `/health`, `/ready`, миграции, ограничения БД,
создание четырёх ресурсов, чтение новой сессией, списки и фильтры, валидацию, конфликт и отсутствие записи,
безопасный ответ при недоступной БД.

Без `TEST_DATABASE_URL` локальный запуск `pytest` явно пропускает интеграционные проверки. Зелёный результат
с пропущенными тестами не подтверждает работу PostgreSQL. В CI отсутствие этой переменной считается
ошибкой. Конкретное число пройденных тестов этой версии смотри в [журнале](DEVELOPMENT_LOG.md).

### 13.3. Сверить миграцию с моделями

```bash
uv run --locked alembic current
uv run --locked alembic check
```

Ожидаемый результат: текущая ревизия соответствует `head`; `alembic check` сообщает, что новых операций
изменения схемы нет. Адрес этих команд берётся из обычного `DATABASE_URL`, то есть проверяется запущенная
development-БД.

Этап 03 добавляет HTTP-слой к существующим таблицам. Номер миграции остаётся прежним. Если модели и БД
расходятся, это нужно выяснить до продолжения; не создавай новую пустую миграцию только ради номера этапа.

## 14. Проверить реально работающий HTTP-сервер

**Цель:** убедиться, что новый код попал в запущенное приложение и отвечает по сети.

```bash
uv run --locked python scripts/smoke_test.py \
  --base-url http://127.0.0.1:8001 --timeout 30 --check-database --check-api
```

Обычная smoke-проверка проверяет `/health`, Swagger и OpenAPI. `--check-database` добавляет `/ready`.
`--check-api` дополнительно проверяет наличие 12 HTTP-операций в OpenAPI и читает четыре списка ресурсов
с `limit=1`. Он сам включает проверку `/ready`, даже если `--check-database` не передан; в команде оба
флага оставлены явно, чтобы был виден полный набор проверок.

Этот режим только читает: он не создаёт новых клиентов, продуктов, лицензий или обращений в development-БД.
Полный сценарий создания покрывается интеграционными тестами и ручным проходом из шага 8. Наличие маршрутов
в OpenAPI подтверждает контракт, а успешные GET подтверждают реальный доступ API к таблицам.

Если проверка не прошла, сначала проверь её базовый URL и `/ready`, затем убедись, что образ пересобран.
Тайм-аут относится к ограниченному ожиданию готовности; неправильный HTTP-ответ нельзя считать успешным
только потому, что сервер принимает TCP-соединение.

## 15. Что автоматически происходит на GitHub

После `git push` в `main` workflow `CI and GHCR` выполняет цепочку:

```text
Python checks
  зависимости из uv.lock
  PostgreSQL → Alembic upgrade → Alembic check
  Ruff + полный Pytest
          ↓
Build and smoke test Docker
  одна сборка образа
  Compose: db → migrate → api
  /health + /docs + /openapi.json + /ready
  контракт API и чтение четырёх списков
  проверка сохранности данных после пересоздания контейнеров
          ↓
Publish tested image to GHCR
  загрузка того же проверенного образа
  публикация SHA-тега
  latest для актуальной вершины main
```

Ошибка любого обязательного шага блокирует публикацию. В контейнерном задании используется одноразовый
Compose-проект, отделённый от тестовой БД Python job и локальных контейнеров разработчика. Образ после
проверок передаётся в следующее задание без повторной сборки.

Pull request в `main` и ручной запуск выполняют проверки; публикация в GHCR относится к push в `main`.
Локальный `git commit` сам по себе не запускает GitHub Actions: коммит должен оказаться на GitHub.

Чтобы проверить результат, открой репозиторий → **Actions** → **CI and GHCR**, выбери запуск именно своего
коммита и открой три задания. Старый зелёный запуск этапа 02 подтверждает старую версию; для нового кода
нужен его собственный успешный запуск. Состояние этой итерации записывается в журнале только после проверки.

Для реализации этапа 03, коммита `d223462`, пользователь 2026-10-18 подтвердил все три зелёных задания
`CI and GHCR`. Локально прошли 199 тестов; источник удалённого подтверждения и SHA-тег образа записаны
в [журнале разработки](DEVELOPMENT_LOG.md). Этот результат относится к указанному коммиту.

Внешний сервер не настраивался: результат CD на этом этапе — проверенный Docker-образ в GHCR. Подробности
прав, тегов, artifacts, логов и очереди публикации находятся в [CI_CD.md](CI_CD.md).

## 16. Частые затруднения

| Симптом | Возможная причина | Проверка и действие |
| --- | --- | --- |
| `/docs` открывается, новых маршрутов нет | Запущен старый образ или другой Uvicorn. | Проверь порт и выполни `docker compose up --build --detach --wait api`. |
| `/health` успешен, `/ready` даёт `503` | Процесс жив, но БД/схема не готова. | `docker compose ps --all`, логи `db migrate api`, `alembic current`. |
| `POST` даёт `404` | ID связанного клиента/продукта отсутствует. | Создай связанные записи и используй ID из ответов. |
| Список пустой при фильтре | Нет записей с указанными значениями, в том числе при неизвестном положительном ID. | Проверь ID и условия; успешный пустой список возвращается как `[]`. |
| `POST` даёт `409` | Значение уже занято. | Выбери новый e-mail/код/ключ либо прочитай старую запись. |
| `POST` даёт `422` и `extra_forbidden` | Прислано лишнее поле, например `status` обращения. | Удали поле и проверь актуальную схему в Swagger. |
| Дата лицензии даёт `422` | Нет часового пояса, передан `null` в `issued_at` или окончание раньше выдачи. | Используй ISO 8601 с `Z`/смещением, проверь порядок дат. |
| `GET` списка даёт `422` | Неверный ID, статус, `limit` или `offset`. | Сверь параметры с разделом 9. |
| `curl` отвечает `Connection refused` | Сервер не запущен или неверный порт. | Проверь `docker compose ps`, значение `API_PORT` и URL. |
| Локально часть тестов пропущена | Не задан `TEST_DATABASE_URL`. | Подними `db-test` и запусти полный набор командой из раздела 13. |
| Тесты нестабильно падают на таблицах | Два процесса используют одну тестовую БД. | Останови конкурирующий запуск и выполни набор последовательно. |
| После правки Python поведение старое | Контейнер работает с файлами, скопированными при сборке. | Пересобери образ; локальный `--reload` относится к Uvicorn на Mac. |

Для диагностики:

```bash
docker compose ps --all
docker compose logs --no-color --tail 100 db migrate api
curl --silent --show-error --include http://127.0.0.1:8001/ready
```

В локальном варианте API на Mac используй его порт `8000`. Сравнивай журнал и запросы одной среды:
обращение к контейнерному `8001` не проверяет отдельный Uvicorn на `8000`.

## 17. Завершить работу и понять следующий шаг

Остановить обычный стенд с сохранением данных:

```bash
docker compose down
```

Удалить только временные файлы примеров можно после их просмотра:

```bash
if [ -n "${EXAMPLE_DIR:-}" ] && [ -d "$EXAMPLE_DIR" ]; then
  rm -f "$EXAMPLE_DIR"/*.json
  rmdir "$EXAMPLE_DIR"
fi
```

Этот шаг удаляет JSON-файлы из созданной временной папки. Клиенты, продукты, лицензии и обращения остаются
в PostgreSQL: HTTP-операций удаления на этом этапе нет.

Результат этапа 03 — понятный и проверяемый путь от HTTP-запроса до сохранённой записи. Следующие этапы
добавят бизнес-возможности поддержки и AI по отдельности, с собственными тестами и инструкциями. Текущие
функции не отправляют ответы клиентам и не вызывают LLM.
