# CI/CD: проверки проекта и публикация API/UI образов

> **Текущая настройка подписи:** по выбору пользователя от 19.10.2026
> публичная keyless-подпись и SBOM attestations подготовлены, но **выключены**.
> Для включения владелец задаёт `GHCR_PUBLIC_SIGNING=true` в GitHub → Settings →
> Secrets and variables → Actions → Variables. Это разрешает публикацию metadata
> в Rekor. Без этой переменной установка cosign и шаг `sign` пропускаются;
> сборки, проверка SBOM, артефакт `sbom` и публикация API/UI в GHCR работают.
> Разделы о cosign ниже описывают поведение после явного включения.


Эта инструкция объясняет, что запускает GitHub после обновления проекта,
как устроены проверки и как получить готовый Docker-образ.

**Текущая цель:** после push в `main` или явного push релизного тега
`vX.Y.Z` проверить проект, собрать и проверить API и UI, затем опубликовать
именно эти два образа в GitHub Container Registry (GHCR):
`ghcr.io/merkertg/ai-support-agent` и `ghcr.io/merkertg/ai-support-agent-ui`.
Каждый публикуется для `linux/amd64` и `linux/arm64` под одним тегом.
Общий тег подписывается cosign keyless, к образу каждой архитектуры
прикладывается SBOM CycloneDX. Версию выбирает человек; CI не создаёт теги
автоматически. Старые SHA-версии main убирает отдельный workflow очистки.
[Подробная процедура выпуска, проверки подписи и восстановления публикации](RELEASES.md).

CD в этом проекте означает **Continuous Delivery — доставку готового образа
в реестр**. Развёртывание на сервере, покупка хостинга и запуск приложения
в интернете в текущую настройку не входят.

## 1. Какие слова нужно понимать

| Слово | Значение в этом проекте |
| --- | --- |
| Репозиторий | Папка проекта с историей Git; её копия хранится на GitHub. |
| Commit | Сохранённая версия изменений в локальной истории Git. |
| Push | Отправка локальных коммитов в репозиторий GitHub. |
| Pull request, PR | Предложение включить изменения из другой ветки в `main`. |
| Merge | Объединение изменений; после merge PR ветка `main` обновляется. |
| CI | Автоматическая проверка изменений: зависимости, стиль, тесты, контейнер. |
| CD | Публикация прошедшего проверки Docker-образа в GHCR. |
| Workflow | Сценарий GitHub Actions из файла `.github/workflows/ci.yml`. |
| Job | Отдельное задание внутри workflow; запускается на отдельном исполнителе. |
| Step | Шаг внутри задания: например, установить Python или запустить тесты. |
| Runner | Машина GitHub, на которой выполняется задание. |
| Docker-образ | Шаблон с приложением, Python и необходимыми зависимостями. |
| Контейнер | Запущенный экземпляр образа. |
| Реестр | Хранилище образов; здесь используется GHCR. |
| Smoke-проверка | Короткая проверка, что собранное приложение действительно запускается и отвечает по HTTP. |
| Артефакт Actions | Файл, сохранённый после задания; здесь это архив проверенного Docker-образа. |

**Локальный `git commit` сам по себе не запускает GitHub Actions.**
GitHub увидит изменения только после `git push` или merge в своём интерфейсе.
Поэтому фраза «проверять при коммите в main» здесь означает:
**проверять каждый push, который обновляет `main` на GitHub**.

## 2. Когда запускается pipeline

Pipeline — последовательность автоматических заданий.

| Событие | Проверить код | Собрать и проверить контейнер | Опубликовать в GHCR |
| --- | --- | --- | --- |
| `push` в `main` | Да | Да | Да, SHA обоих образов для amd64 и arm64; latest только для текущей вершины main |
| `push` выбранного тега `vX.Y.Z` | Да, после проверки тега и main ancestry | Да | Да, version-теги обоих образов без изменения latest |
| Создание или обновление PR в `main` | Да | Да | Нет |
| Ручной запуск `Run workflow` | Да | Да | Нет |
| Dispatch для ветки обновления зависимостей | Да | Да | Нет |
| Расписание очистки GHCR (воскресенье) | Нет | Нет | Нет; план удаления старых SHA-версий, удаление — только по явному разрешению |
| `push` в другую ветку без PR в `main` | Нет | Нет | Нет |
| Локальный `git commit` без `push` | Нет | Нет | Нет |

В событии `pull_request` фильтр `branches: [main]` относится к **целевой**
ветке PR. Например, PR из `feature/database` в `main` запускает проверки.
Изменения только в документации тоже запускают pipeline: исключений по путям
для текущего workflow нет.

Ручной запуск нужен, чтобы повторить проверки выбранной ветки.
Он не публикует образ, даже если в интерфейсе выбрана `main`.
GitHub показывает кнопку ручного запуска, когда workflow с `workflow_dispatch`
уже находится в ветке по умолчанию.

## 3. В каком порядке всё выполняется

```text
Push main / push vX.Y.Z / PR / ручная проверка
        │
        ▼
delivery: точный commit → для тега строгий SemVer и история main
        │
        ▼
checks: lock/возраст → workflow/docs → Alembic → Ruff → тесты/покрытие ≥85% → оценки
security: lock-файл → аудит известных уязвимостей зависимостей API и UI
portability: Linux, macOS, Windows → uv.lock → docs → Ruff → unit-тесты → запуск API/UI
        │ только при успехе всех трёх заданий
        ▼
container: API/UI → arm64 под QEMU → SBOM и Trivy (4 образа) → Compose/HTTP → тома → UI/демо → журнал → архив
        │ только при успехе и только push main либо проверенного vX.Y.Z
        ▼
publish: commit, 4 ID и SBOM → GHCR preflight → amd64 и arm64 → общий index
         → cosign: подпись digest index, SBOM-attestation, verify
```

На PR и при ручном запуске цепочка заканчивается после проверки контейнера.
На push в `main` или выбранного `vX.Y.Z` успешный pipeline заканчивается
публикацией обоих образов в GHCR.

### Задание `delivery`: проверить цель публикации

Первое короткое задание получает точный commit и полную историю Git.
На обычных ветках/PR оно не требует релизного тега. Для `refs/tags/v…`
скрипт `scripts/release_delivery.py validate` допускает только стабильный
`vX.Y.Z` без ведущих нулей и суффиксов, разрешает annotated tag до commit
и сравнивает его с SHA запуска. Этот commit должен входить в историю
`origin/main`; совпадение только с последней вершиной не требуется.
Изменённый тег или боковая ветка блокируют дальнейшие jobs.
Эта проверка выполняется повторно в `publish`; версии не создаются автоматически.

### Задание `checks`: проверить Python-проект

Задание получает файлы репозитория, устанавливает Python 3.12 и `uv` 0.12.23.
`uv` управляет зависимостями и виртуальным окружением проекта.
Отдельный service запускает PostgreSQL 17 с одноразовой БД `ai_support_test`.
`DATABASE_URL` и `TEST_DATABASE_URL` указывают на неё; данные локальной
development-БД недоступны runner. С этапа 06 второй service запускает
Qdrant 1.19.1, а `TEST_QDRANT_URL` указывает на него. В образе Qdrant нет
`curl` для healthcheck, поэтому шаг `Wait for Qdrant` до 60 секунд ждёт
ответа `/readyz` с runner. Затем выполняются проверки:

```bash
uv sync --locked
uv run --locked python scripts/check_dependency_age.py --min-age-days 14
uv run --locked python scripts/check_project.py --require-powershell
uv run --locked alembic upgrade head
uv run --locked alembic check
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest --cov --cov-report=term-missing:skip-covered \
  --cov-report=xml --cov-report=json --cov-report=html
uv run --locked python -m evaluations.run --output reports/evaluations.json
```

- `uv sync --locked` создаёт окружение по `uv.lock`. Если описание зависимостей
  в `pyproject.toml` не соответствует lock-файлу, команда завершается ошибкой.
  CI не должен незаметно менять зафиксированные версии.
- `scripts/check_dependency_age.py` требует, чтобы каждый пакет в `uv.lock`
  был опубликован на PyPI не меньше 14 дней назад, а дата `[tool.uv]
  exclude-newer` в `pyproject.toml` была не ближе той же границы. Даты берутся
  из самого lock-файла. Свежий выпуск блокирует доставку, пока ему не исполнится
  две недели или пока lock не вернут на более раннюю версию.
- `scripts/check_project.py` проверяет локальные ссылки Markdown, синтаксис
  примеров Bash, PowerShell и JSON и наличие docstrings у функций и классов.
  PowerShell-примеры разбирает установленный на runner `pwsh`, ничего не выполняя;
  флаг `--require-powershell` превращает непроверенные блоки в ошибку. Ошибка
  инструкции блокирует доставку так же, как ошибка Python-кода.
- `actionlint` 1.7.12 проверяет YAML и выражения GitHub Actions. Workflow
  скачивает официальный Linux-бинарник и перед запуском сверяет SHA256,
  записанный прямо в workflow. Исключена только диагностика нового `queue: max`;
  остальные ошибки завершают шаг неуспешно. Внешние необязательные интеграции
  ShellCheck/Pyflakes отключены явно, чтобы результат не зависел от их наличия
  и версий в runner.
- `alembic upgrade head` создаёт или обновляет схему явными миграциями.
- `alembic check` сравнивает реальную схему с metadata моделей; незаписанное
  изменение схемы блокирует публикацию.
- `ruff check .` ищет ошибки и нарушения правил кода, включая порядок импортов.
- `ruff format --check .` проверяет форматирование. Ключ `--check` означает,
  что CI сообщает о различиях и не переписывает файлы на машине GitHub.
- `pytest` находит тесты в `tests/`. Новый тест в этой папке включается
  в общий запуск, если его имя и имя тестовой функции соответствуют правилам Pytest.
  Интеграционные тесты проверяют настоящую PostgreSQL, миграции и ограничения.
  При `CI=true` отсутствие `TEST_DATABASE_URL` или `TEST_QDRANT_URL`
  считается ошибкой, а не пропуском. Тесты базы знаний создают и удаляют
  только собственные коллекции `test_*`; эмбеддинги — mock, без ключей.
- Покрытие измеряется настоящим выполнением кода `app`, `operator_ui`,
  `evaluations` и `scripts`; PDF-генератор исключён, тесты не учитываются
  как проверяемый продуктовый код. Порог `fail_under = 85` из `pyproject.toml`
  превращает недостаточное покрытие в ошибку job. XML, JSON и HTML сохраняются
  в `coverage-report` на 7 дней, включая результаты упавшего тестового запуска,
  если отчёт успел создаться. Сам процент не доказывает качество утверждений:
  тесты отдельно проверяют ошибки, границы доступа и восстановление состояния.
- `python -m evaluations.run` (этап 09) измеряет поиск по 32 размеченным
  вопросам и проверяет 12 сценариев безопасности агента без сети и ключей.
  Нарушение порога из `evaluations/thresholds.json` — код `1` и красный job.
  Отчёт загружается артефактом `evaluation-report`. Подробно — в [STAGE_09.md](STAGE_09.md).
- Группа `dev` включает группу `ui`, поэтому `uv sync --locked` ставит Streamlit,
  а Pytest выполняет AppTest-проверки интерфейса вместе с остальными тестами.
- `uv run --locked` запускает инструмент в окружении проекта и сохраняет
  требование актуального lock-файла.

Обычный API-тест вызывает FastAPI через `TestClient`: отдельный Uvicorn и
сетевой порт для него не нужны. Позже контейнер проверяется через настоящий HTTP.

### Задание `portability`: Linux, macOS и Windows

Матрица из трёх runner: `ubuntu-24.04`, `macos-15` (arm64) и `windows-2025`.
На каждом ставятся те же uv 0.12.23, Python 3.12 и зависимости из `uv.lock`,
затем выполняются проверка возраста зависимостей, `check_project.py`, Ruff,
все unit-тесты (без `tests/integration`), автономные оценки и
`scripts/check_local_start.py`. Последний запускает настоящие процессы Uvicorn
и Streamlit на этой ОС, проверяет `/health`, JSON 503 от `/ready` без базы,
`X-Request-ID` и отрисовку страницы оператора, затем останавливает их.

`fail-fast: false` сохраняет результат всех ОС, даже если одна упала.
Интеграционные тесты с PostgreSQL/Qdrant и Docker остаются на Linux: на macOS-
runner нет Docker, а Windows-runner запускает только Windows-контейнеры.
На Windows `bash` берётся из Git for Windows, окончания строк LF фиксирует
`.gitattributes`, а скрипты и тесты читают и печатают UTF-8 явно.

Минуты macOS и Windows в закрытом репозитории тарифицируются с множителем
(в GitHub — ×10 и ×2 к минутам Linux). Если бюджет ограничен, матрицу можно
оставить на PR и ручных запусках, но тогда push в `main` не будет её ждать.

### Задание `security`: проверить известные уязвимости зависимостей

Оно запускается параллельно с `checks` и не требует PostgreSQL, Qdrant
или ключей OpenAI. Проверяется полный набор runtime-зависимостей из `uv.lock`,
включая транзитивные зависимости, применимые к Python 3.12 на runner.

```bash
mkdir -p reports
uv export --locked --no-dev --group ui --no-emit-project --format requirements.txt \
  --output-file reports/runtime-requirements.txt > /dev/null
uv tool run --python 3.12 --from pip-audit==2.10.1 pip-audit \
  --strict --require-hashes --disable-pip --progress-spinner off \
  -r reports/runtime-requirements.txt \
  --format json --output reports/pip-audit.json
```

`uv export --locked` сохраняет версии и hashes из lock-файла и отказывается
работать при его расхождении с `pyproject.toml`. `--no-dev` соответствует
финальным Docker-образам: инструменты разработки не попадают в runtime.
`--group ui` с этапа 08 добавляет Streamlit и его зависимости из образа
интерфейса: аудит покрывает оба образа одним списком.
`pip-audit` зафиксирован на 2.10.1 и запускается в отдельном окружении инструмента.
`--disable-pip` и hashed requirements позволяют проверить список без установки
проверяемых пакетов. Данные об известных уязвимостях запрашиваются у PyPI;
сама база уязвимостей обновляется, поэтому результат относится к дате запуска.

Найденная уязвимость, неудачный сбор зависимостей или ошибка сети приводят
к ошибке задания. В workflow нет подавления ошибок, автоматического `--fix`
или списка игнорируемых уязвимостей. Исправление зависимости выполняется
отдельным изменением lock-файла с повторной проверкой проекта.

Шаг загрузки артефакта использует `always()`: `dependency-audit` содержит
экспортированный список и JSON-отчёт также при находках. При ранней сетевой
ошибке JSON может не появиться; лог объяснит причину, а публикация останется
заблокированной. Это аудит известных уязвимостей Python-пакетов; отдельный
аудит системных библиотек базового Docker-образа в него не входит.

Локальная проверка 2026-10-18 тем же `pip-audit==2.10.1` в контейнере
`uv` 0.13.1 с Python 3.12: **91 пакет API и UI, 0 известных уязвимостей**
(до этапа 08 — 69 пакетов API). Это результат локального запуска,
а не подтверждение выполнения нового задания GitHub Actions.

### Задание `container`: проверить собранное приложение

Это задание содержит `needs: [checks, security, portability]`. GitHub запускает
его после успешного завершения проверок кода, аудита зависимостей и матрицы
Linux/macOS/Windows; ошибка любой из них блокирует сборку и публикацию.

Основные действия:

1. Собрать Docker-образ API по `Dockerfile` и `uv.lock` один раз, затем
   образ интерфейса `--target ui`. Отдельным `docker run` проверить UID/GID
   10001 и отсутствие Pytest, Ruff и исполняемого `uv` в обоих образах.
   В образе UI дополнительно не должно быть кода `app/`, FastAPI, SQLAlchemy,
   драйвера PostgreSQL, LangGraph, клиента Qdrant и SDK OpenAI.
   Обычный HTTP smoke не заметил бы нарушения этих требований к образам.
2. Запустить изолированный Compose-проект `ai-support-ci`: PostgreSQL,
   затем миграции, затем API из этого образа; `--no-build` запрещает пересборку.
3. Проиндексировать базу знаний: `python -m app.knowledge.ingest` внутри `api`.
   Отчёт должен содержать проиндексированные статьи и не содержать удалённых.
4. Выдать суточный токен администратора командой `python -m app.tokens issue`
   внутри `api` (первого администратора иначе не создать: без токена `/api/*`
   закрыт). Токен маскируется (`::add-mask::`) и попадает в `API_TOKEN` через
   `$GITHUB_ENV`; smoke, демо и AppTest читают его оттуда, а не из аргументов.
   Дождаться healthcheck и выполнить `scripts/smoke_test.py --check-review`.
   Вывод сохраняется в `smoke.log`: из него следующий шаг берёт ID запуска агента.
   Затем `--check-agent` оставляет ещё один запуск в ожидании решения (`pending.log`).
5. Записать вымышленные demo-данные через `python -m app.db.demo seed`,
   прочитать созданный запуск агента `GET /api/agent-runs/{id}` и выдачу
   поиска для известного запроса (curl с заголовком `Authorization`).
   Сохранить три JSON-снимка, выполнить
   `docker compose down` **без `--volumes`**, снова запустить сервисы и прочитать
   то же самое. `cmp` проверяет идентичность снимков: записи PostgreSQL и индекс
   Qdrant должны пережить удаление контейнеров благодаря томам. Повторный seed
   между снимками запрещён: он мог бы скрыть потерю данных. Повторная индексация
   после пересоздания обязана сообщить `indexed: []` и `removed: []`.
   `--review-run` продолжает отложенный граф LangGraph уже в новых контейнерах:
   ожидание решения сотрудника переживает пересоздание, а токен из PostgreSQL
   по-прежнему действует. Затем полный smoke `--check-review` выполняется ещё раз.
6. Запустить сервис `ui` (этапы 08 и 10): Compose ждёт healthy API, затем
   healthcheck Streamlit `/_stcore/health`. `scripts/demo_scenario.py
   --verify-review` должен оставить основное предложение `pending` /
   `awaiting_review`, а на двух дополнительных обращениях подтвердить
   одобрение (одно сообщение, `delivered`) и отклонение (нет сообщений,
   `rejected`). Повторный запуск обязан вывести байт-в-байт тот же JSON:
   сценарий только читает существующие записи. Наконец, внутри контейнера
   `ui` настоящая страница отрисовывается Streamlit AppTest против API:
   без токена она не показывает данных, после ввода `API_TOKEN` в боковую
   панель — показывает метрики и не содержит исключений и ошибок.
7. Просканировать Trivy 0.75.0 все четыре образа: API и UI для amd64 и arm64.
   Сканер запускается образом, закреплённым по digest, а не через
   `aquasecurity/trivy-action`: в марте 2026 теги этого действия и образы
   Trivy 0.69.4–0.69.6 были подменены вредоносным кодом (CVE-2026-33634).
   Шаг падает при уязвимостях HIGH или CRITICAL, для которых уже выпущено
   исправление (`--ignore-unfixed`). Полный JSON-отчёт по каждому образу,
   включая уязвимости без исправления, сохраняется артефактом `image-scan`.
   Уязвимости базового Debian без исправления не блокируют сборку: их нечем
   исправить, пока дистрибутив не выпустит обновление.
   Перед сканированием тот же Trivy записывает SBOM каждого из четырёх образов
   в CycloneDX: `reports/sbom/ai-support-agent-ci.cdx.json`,
   `…-ci-arm64.cdx.json` и то же для UI. База уязвимостей для SBOM не нужна.
   Файлы сохраняются артефактом `sbom` на 30 дней, в том числе при найденной
   уязвимости. Свойство `aquasecurity:trivy:ImageID` в каждом SBOM равно ID
   образа: `publish` по нему убеждается, что SBOM описывает именно
   опубликованный образ.
8. Проверить журнал API после smoke и демо: в нём есть JSON-строки запросов
   с `user_id` и события `auth_failed`, но нет ключей лицензий `SMOKE-…`
   и `DEMO-STAGE10…`, хотя smoke и демо передавали их в теле и в фильтре
   `?license_key=`, и нет ни одной строки вида токена `asa_…` (сама строка
   при совпадении не печатается).
9. Для push в `main` или проверенного `vX.Y.Z` сохранить четыре проверенных
   образа (API и UI для amd64 и arm64) одним артефактом `tested-docker-images`,
   включая полный SHA commit и все image ID. Перед экспортом проверяется
   платформа каждого образа. На PR и при ручном запуске архив не создаётся.
10. При ошибке показать Compose-логи; при любом результате удалить контейнеры
   и тома **только изолированного CI-проекта**. Финальный `down --volumes`
   допустим здесь, поскольку это временные данные runner.

   База уязвимостей Trivy скачивается отдельным шагом с тремя попытками
   и паузой: реестр иногда отвечает ограничением или обрывом, и это не должно
   ронять сборку. Все четыре образа сканируются из уже скачанной базы.

   До сканирования те же образы собираются для `linux/arm64` под QEMU
   (`tonistiigi/binfmt` по digest): проверяются `aarch64`, UID 10001,
   отсутствие инструментов разработки, импорт приложения и ответы
   `/health` и `/_stcore/health` запущенных arm64-контейнеров. Именно эти
   arm64-образы потом публикуются: отдельной сборки для GHCR нет.

Проверяются:

| Запрос | Что он подтверждает |
| --- | --- |
| `GET /health` | HTTP 200 и ожидаемый JSON со статусом `ok` и именем `ai-support-agent`. |
| `GET /ready` | HTTP 200 и точный JSON `{"status":"ok","database":"ok"}`; PostgreSQL доступна, версия Alembic актуальна. |
| `GET /docs` | HTTP 200 и HTML содержит `SwaggerUIBundle` — признак страницы Swagger UI. |
| `GET /openapi.json` | HTTP 200, `info.title` равен `AI Support Agent` и есть операции `GET /health` и `GET /ready`. |

Таким образом, успешная сборка сама по себе недостаточна: контейнер должен
запуститься и обслуживать запросы. Скрипт использует
один общий срок для ожидания и всех запросов (`--timeout 30` — 30 секунд).
При старте он повторяет сетевые ошибки запроса `/health`, например отказ
в соединении, пока Uvicorn ещё запускается. Неожиданный HTTP-код,
перенаправление, неверный JSON или неправильный контракт сразу завершают
проверку ошибкой. После успешного `/health` проверяются `/ready`, `/docs` и
`/openapi.json`. Без `--check-database` остаётся исходный режим трёх HTTP-проверок.
Скрипт использует стандартную библиотеку Python;
дополнительные зависимости ему не нужны.

С этапа 03 CI также передаёт `--check-api`. Этот флаг включает `/ready`,
требует в OpenAPI все 12 операций создания/списка/чтения для клиентов,
продуктов, лицензий и обращений, затем выполняет четыре запроса списков
`GET /api/<ресурс>?limit=1`. Ожидается HTTP 200 и массив длиной не более 1;
если запись есть, её `id` должен быть положительным целым числом.
Проверка ничего не записывает. Сквозные POST-запросы и ошибки 404/409/422/503
проверяются в Pytest с настоящей отдельной PostgreSQL-базой.

С этапа 04 CI передаёт ещё и `--check-llm`. Задания явно получают
`LLM_PROVIDER=mock`, пустые `OPENAI_API_KEY` и `OPENAI_MODEL`. Тесты реального
SDK используют подменённый HTTP-транспорт; ключи для них не требуются.

Перед любым POST дополнительный smoke читает `/api/llm/status` и требует
точно настроенный mock. При другом провайдере он завершается ошибкой без записи
и без запроса к модели. Затем он явно создаёт три вымышленные записи
(клиент, продукт, обращение), получает демонстрационный черновик и повторным
GET проверяет, что обращение не изменилось. Вместе с предыдущими этапами
это 14 HTTP-запросов и проверка 14 предметных операций в OpenAPI.

**Для локального запуска:** `--check-llm` добавляет три учебные записи в выбранную
БД. Сам endpoint черновика ничего не сохраняет. Без этого флага прежние
проверки остаются только читающими. В CI записи принадлежат отдельному
Compose-проекту и удаляются с его томом после задания.

С этапа 07 CI передаёт `--check-review`. Он включает `--check-agent`, затем
требует в OpenAPI `POST /api/users`, `POST /api/users/{id}/tokens`,
`DELETE /api/tokens/{id}`, `GET /api/agent-runs/{id}/workflow` и
`POST /api/suggestions/{id}/review`, проверяет, что граф стоит на
`human_review`, и проверяет права: решение без токена — `401`; созданный
учебный `operator` с суточным токеном — `403`; после отзыва его токена — `401`;
граф всё это время ждёт. Только затем предложение одобряется от имени
сотрудника `API_TOKEN` (нужна роль `admin`) с отредактированным текстом.
Ответ должен показать `approved`, автора решения и сообщения — владельца
токена, тот же текст, `waiting_customer` и итог графа `delivered`; повторное
решение обязано получить `409`. `--review-run RUN_ID` одобряет уже
сохранённый запуск и требует лишь роли `reviewer`. Каждый режим с `/api/*`
начинается с проверки `401` без токена и `GET /api/auth/me`.

С этапа 06 `--check-agent` включает также `--check-knowledge`. Этот режим только
читает: требует в OpenAPI `GET /api/knowledge/status` и `POST /api/knowledge/search`,
mock-эмбеддинги и статус `ready` (до проверки поиск не выполняется), находит
`KB-SERVER-START` первой для продукта `techflow-server` и убеждается, что для
`techflow-desktop` статьи сервера не видны. Проверка mock-LLM выполняется раньше
любого POST, включая поиск.

С этапа 05 CI передаёт `--check-agent`. Он включает все проверки `--check-llm`
и выполняется только после того же подтверждения mock. Дополнительно smoke
требует в OpenAPI `POST /api/tickets/{id}/analyze` и `GET /api/agent-runs/{id}`,
создаёт вымышленную лицензию для учебного клиента и продукта и запускает агента
с её ключом. Ответ `201` должен содержать `completed`, mock-модель `mock-agent-v1`,
три шага, пять успешных инструментов в порядке `get_ticket`, `get_customer`,
`get_ticket_history`, `get_license`, `search_knowledge`, замаскированный ключ `***`,
действующую лицензию, непустой `sources` только из найденных статей и одно
`pending`-предложение с демонстрационной пометкой. Описание учебного обращения
совпадает с общей статьёй `KB-SUPPORT-DATA`, поэтому цитирование проверяется
на каждом запуске. Сырой ключ
не должен появиться в ответе. Затем GET запуска обязан вернуть тот же JSON,
а обращение — остаться неизменным. Режим добавляет лицензию, запуск и
предложение; агент не меняет обращение и ничего не отправляет.

Код завершения скрипта: `0` — успех, `1` — ошибка проверки, `2` — неверные
аргументы командной строки. CI воспринимает ненулевой код как ошибку шага.

### Задание `publish`: отправить проверенные API и UI в GHCR

`needs: container` блокирует публикацию при любой ошибке предыдущих gates.
Условие `if` допускает только событие `push` в `refs/heads/main` или
проверенный релизный тег `refs/tags/vX.Y.Z`. PR, ручной запуск и dispatch
ветки обновления зависимостей ничего не публикуют.

`publish` получает `tested-docker-images`, проверяет commit и структуру
метаданных, выполняет `docker load` и сравнивает image ID **всех четырёх**
образов (API и UI для amd64 и arm64) с ID из `container`, а также платформу
каждого. **Повторной сборки нет:** Docker получает только `tag` и `push`
уже протестированных образов, а `docker buildx imagetools create` собирает
из их digest общий тег. Registry копирует ссылки; образы не скачиваются.

Для успешного main push появляются ссылки:

```text
ghcr.io/merkertg/ai-support-agent:sha-<полный SHA коммита>
ghcr.io/merkertg/ai-support-agent:sha-<полный SHA коммита>-amd64
ghcr.io/merkertg/ai-support-agent:sha-<полный SHA коммита>-arm64
ghcr.io/merkertg/ai-support-agent-ui:sha-<полный SHA коммита>
ghcr.io/merkertg/ai-support-agent-ui:sha-<полный SHA коммита>-amd64
ghcr.io/merkertg/ai-support-agent-ui:sha-<полный SHA коммита>-arm64
```

Тег без суффикса — image index двух архитектур: Docker на amd64-компьютере
скачает amd64-образ, на Mac с Apple Silicon или ARM-сервере — arm64.
Тег с суффиксом указывает на образ одной конкретной архитектуры.

Если проверяемый commit всё ещё является текущей вершиной `main` на момент
запроса GitHub API, оба пакета также получают `latest` — такой же index. Иначе SHA-теги
сохраняются, а `latest` пропускается. Все публикации используют общую очередь
`ghcr-delivery`: старый job не выполняется одновременно с новым publish.
Теги registry изменяемы; SHA-тег не заменяет адрес содержимого `@sha256:…`.

При явном push тега, например выбранного человеком `v0.1.0`, оба пакета
получают `:v0.1.0`, `:v0.1.0-amd64` и `:v0.1.0-arm64`. Такой запуск не меняет
ни `latest`, ни SHA-теги main. До первой записи скрипт проверяет **все шесть**
удалённых ссылок: отсутствующая разрешает запись; идентичный
config/manifest/index ID пропускается; общий тег принимается, только если это
index ровно с manifest проверенных тегов архитектур; другой образ завершает
job с ошибкой до записи API/UI. Ошибка сети, HTTP 401/403 или повреждённый
ответ не считаются свободным тегом.
После push проверяются удалённый идентификатор и SHA256 всего ответа, после
создания общего тега — что `linux/amd64` и `linux/arm64` в нём указывают
на опубликованные manifest. Записи attestation `unknown/unknown` пропускаются,
любая другая платформа отклоняется.
Classic Docker использует config ID одиночного manifest; containerd может
вернуть ID самого manifest или OCI index с attestations. Для index
принимается только совпадение digest всего index, а не одного его потомка.
Поддерживаются Docker manifest/list и OCI manifest/index; schema 2,
media type и непустые index descriptors проверяются до сравнения ID.

В сводке для API и UI появляются общий тег, digest index, digest каждой
архитектуры и состояние `latest`. Для скачивания точного содержимого используй
адреса `@sha256:…` из одной сводки: digest index выбирает архитектуру сам,
digest архитектуры фиксирует и её. Различай SHA коммита исходного кода
и digest manifest образа.

При обрыве посередине возможен повтор failed publish с тем же артефактом:
совпавшие теги пропускаются, недостающие теги архитектур и общий index
допубликуются. SHA-тег main при повторной сборке того же commit
переписывается целиком. Пересборка всех jobs
может изменить image ID и потребовать новой версии. Полная процедура
выбора тега, повторов и запуска пары образов описана в [RELEASES.md](RELEASES.md).

#### Подпись cosign и SBOM-attestation

До первой записи `publish` проверяет четыре SBOM из артефакта `sbom`: файл
есть, это CycloneDX, `ImageID` совпадает с ID проверенного образа. Затем
ставит cosign 3.1.3 из официального выпуска со сверкой SHA256 — без cosign
job останавливается до публикации. После публикации отчёт
`published-images.json` содержит digest каждого index и manifest архитектур.
Шаг `Sign indexes and attach SBOM attestations` выполняет
`release_delivery.py sign`:

1. `cosign sign --yes ghcr.io/…@sha256:<index>` для API и UI — подписывается
   digest, а не тег. Если у `latest` digest другой, подписывается и он.
2. `cosign attest --type cyclonedx` прикладывает SBOM к manifest каждой
   архитектуры из этого index. Образы не пересобираются.
3. `cosign verify` и `cosign verify-attestation` с identity
   `https://github.com/merkertg/ai-support-agent/.github/workflows/ci.yml@<ref>`,
   издателем `https://token.actions.githubusercontent.com` и
   `--certificate-github-workflow-sha` проверяемого commit. Ошибка — красный job.

Подпись keyless: ключей и секретов нет. `id-token: write` разрешён только
`publish`; GitHub выдаёт OIDC-токен, Fulcio — сертификат на 10 минут.
Подпись и сертификат записываются в публичный журнал Sigstore (Rekor):
имя закрытого репозитория, путь workflow, ref и SHA commit станут видны
публично. В сводке появляется раздел «Подписи и SBOM». Команды проверки
для пользователя образа — в [RELEASES.md](RELEASES.md).

cosign 3 хранит подписи OCI-артефактами в том же пакете GHCR. Если registry
не поддерживает OCI Referrers API, добавляется тег `sha256-<digest образа>`
со списком подписей. Такие теги нельзя удалять вручную.

Публикация доставляет образы в реестр. Автоматическое обновление внешнего
сервера или локального dev-стенда в этот workflow не входит.

## 4. Зачем нужны `permissions`, `needs`, `if` и `concurrency`

| Настройка | Зачем она нужна |
| --- | --- |
| `permissions: contents: read` | Разрешает заданиям читать код репозитория. |
| `packages: write` только в `publish` | Разрешает этому заданию публиковать образ в GHCR. |
| `id-token: write` только в `publish` | OIDC-токен GitHub для keyless-подписи cosign; остальные задания его не получают. |
| `needs: delivery` | Проверки кода и аудита ждут корректную цель запуска. |
| `needs: [checks, security, portability]` | Контейнер ждёт успешные проверки кода, аудит и матрицу Linux/macOS/Windows. |
| `needs: container` | Не позволяет публиковать непроверенный контейнер. |
| `if` в `publish` | Допускает только push main или проверенного version-тега; PR и dispatch пропускаются. |
| `concurrency` | Отменяет устаревшие проверки одного PR и ставит публикации в общую очередь. Все push в `main` сохраняют свои проверки. |
| `timeout-minutes` | Ограничивает время выполнения задания, если команда зависла. |
| `if: failure()` на логах | Показывает логи контейнера при ошибке. |
| `if: always()` на очистке | Удаляет временный контейнер после успеха, ошибки или отмены. |

Проверки внутри `checks` независимы после установки зависимостей: ошибка
Ruff не скрывает результат форматирования и тестов. Общий результат задания
всё равно будет неуспешным, если упала любая проверка. Если не установились
зависимости, эти шаги не запускаются.

Внешние actions закреплены полными SHA-коммитами, а рядом в комментарии
записана версия для чтения человеком. Это фиксирует исполняемый код action.
Обновлять SHA нужно осознанно вместе с проверкой новой версии.

Задания работают на `ubuntu-24.04`. `checks` ограничен 10 минутами,
`container` и `publish` — 30 минутами каждый: сборка arm64 под QEMU,
четыре образа, подписи и SBOM занимают время.

Для PR новая версия изменений отменяет старый запуск этого же PR.
Каждый `push` в `main` получает отдельную группу и проходит свои проверки;
следующий push не отменяет предыдущие `checks` и `container`.
Публикации main и релизов используют общую группу `ghcr-delivery`, `cancel-in-progress: false`
и очередь `queue: max` до 100 ожидающих заданий. SHA-проверка вершины `main`
дополнительно регулирует обновление `latest`: одна только очередь не
гарантирует, что тесты коммитов закончатся в порядке их появления.

Каждое задание получает свой временный `GITHUB_TOKEN`. GitHub создаёт его
автоматически для запуска Actions. Токен не нужно копировать из интерфейса,
вписывать в код или создавать вручную в `Secrets`.

У заданий проверки нет права публикации. Право `packages: write` задано
непосредственно в `publish`; оно не выдаётся всему pipeline без необходимости.
Публикация из PR, включая PR из fork, не выполняется.

## 5. Какие файлы за что отвечают

| Файл | Назначение |
| --- | --- |

### Как устроен `Dockerfile`

В сборке несколько стадий:

1. `python-base` задаёт общий базовый образ `python:3.12-slim`, закреплённый
   по digest индекса: тот же образ для arm64 на Mac и amd64 в CI, и никакая
   перезапись тега в реестре не меняет сборку незаметно.
2. `builder` получает `uv` 0.12.23 (тоже по digest) и выполняет
   `uv sync --locked --no-dev`: создаёт Linux-окружение `.venv`
   только с зависимостями работающего API.
3. `runtime` получает `.venv`, `app/`, `migrations/` и `alembic.ini`.
   По умолчанию запускает Uvicorn; сервис `migrate` переопределяет команду
   на `python -m alembic upgrade head`.
4. `ui-builder` и `ui` (этап 08) собирают отдельный образ интерфейса:
   `uv sync --locked --only-group ui` ставит только Streamlit и httpx, а в образ
   копируется лишь `operator_ui/`. Эта цель выбирается явно (`--target ui`
   или `target: ui` в Compose). `runtime` остаётся последней стадией, поэтому
   `docker build .` без `--target` по-прежнему собирает API.
   Healthcheck UI запрашивает `/_stcore/health`; телеметрия Streamlit отключена.

Uvicorn запускается с `--no-access-log`: его журнал доступа печатает query string,
а в ней бывает `license_key`. Запросы записывает само приложение — JSON-строкой
с `request_id`, путём без параметров, кодом и длительностью.

Все сторонние образы — `python`, `uv`, `postgres`, `qdrant` и сканер Trivy —
указаны как `имя:тег@sha256:…` в `Dockerfile`, `compose.yaml` и workflow.
Тест `tests/test_image_pins.py` не пропустит тег без digest или разные digest
одного образа. Чтобы обновить образ, получи digest индекса и замени его во всех
файлах сразу:

```bash
docker buildx imagetools inspect python:3.12-slim --format '{{json .Manifest}}'
```

Затем пересобери образы и повтори сканирование и тесты.

В финальный образ не копируются локальная `.venv` с Mac, тесты, инструкции,
кеш сборки и `uv`. Использование одного Python-базового образа в builder и
runtime позволяет перенести созданное окружение между стадиями.

Приложение запускается от пользователя `app` с UID/GID `10001`, а не от root.
Внутри контейнера Uvicorn слушает `0.0.0.0:8000`, чтобы опубликованный порт
принимал запросы снаружи контейнера. `EXPOSE 8000` описывает порт образа;
реальный проброс на компьютер задаёт `ports` в Compose.

`HEALTHCHECK` периодически запрашивает `/ready` внутри контейнера и сверяет
точный JSON. Интервал — 30 секунд, тайм-аут — 5 секунд, начальный период —
10 секунд, порог неудач — 3. Это отдельная диагностика Docker.
В Compose интервал переопределён на 3 секунды, порог неудач — 20.
Она не заменяет HTTP smoke-проверки, включая предметное API и сама по себе не перезапускает
контейнер. Увидеть состояние можно через `docker ps` или `docker inspect`.

При сборке в CI к образу добавляются OCI-метки `source` и `revision`:
адрес GitHub-репозитория и SHA исходного коммита.

Контейнер использует зависимости для работы приложения. Инструменты
разработчика (`pytest`, `ruff`, `httpx` из группы `dev`) проверяются в `checks`;
для работы API они не требуются.

## 6. Что проверить в GitHub перед первым запуском

Исходные файлы workflow можно подготовить локально. Доступ к реестру и реальный
запуск на runner подтверждаются только выполнением Actions на GitHub.

1. Открой репозиторий [merkertg/ai-support-agent](https://github.com/merkertg/ai-support-agent).
2. В `Settings → Actions → General` убедись, что GitHub Actions разрешены.
   Если включён список разрешённых actions, он должен допускать actions,
   указанные в `.github/workflows/ci.yml`.
3. Workflow явно запрашивает нужные права через `permissions`.
   Не нужно выдавать всем workflow максимальные права только ради публикации.
   Если настройка организации ограничивает запись в Packages, её должен
   разрешить администратор этой организации.
4. Отправь файлы в `main` или создай PR в `main`. PR проверит CI, а публикация
   произойдёт после merge или прямого `push` в `main`.
5. Открой вкладку `Actions` и проверь, что все задания этого запуска завершились успешно.
6. После успешного `publish` открой пакет `ai-support-agent` в `Packages`
   у владельца репозитория и проверь SHA-тег. Если это актуальная вершина
   `main`, также проверь `latest`.

Для текущего workflow не нужны Docker Hub, платный сервер, ключ OpenAI,
пароль базы данных или отдельный PAT для публикации.

Новый пакет GHCR по умолчанию создаётся закрытым. Публичность репозитория
не означает автоматическую публичность образа. Видимость пакета меняется
отдельно в настройках самого пакета, если это потребуется.

Если пакет с таким именем существовал раньше, его настройки должны разрешать
этому репозиторию запись через GitHub Actions. При ошибке доступа открой
настройки пакета и проверь связь с репозиторием и доступ Actions.

## 7. Как отправить изменения и запустить проверку

Команды ниже — пример для самостоятельной работы в терминале.
Перед коммитом проверь список изменений: `git status` и `git diff`.

```bash
git status
git diff
```

После проверки добавь только нужные файлы, создай коммит и отправь его:

```bash
git add .github/workflows/ci.yml Dockerfile .dockerignore .gitignore scripts tests docs README.md
git commit -m "Add CI checks and GHCR image delivery"
git push origin main
```

Пример предполагает, что ты работаешь в ветке `main` и нужные файлы ещё
не сохранены коммитом. Проверить текущую ветку можно командой:

```bash
git branch --show-current
```

Если работа идёт в другой ветке, отправь эту ветку и создай PR в `main`.
Не переключай ветку и не выполняй merge автоматически, не посмотрев состояние Git.

## 8. Где смотреть результат

Во вкладке `Actions` выбери workflow **CI and GHCR**, затем запуск
с нужным коммитом.
В интерфейсе задания называются:

| ID в YAML | Название в Actions |
| --- | --- |
| `delivery` | `Validate delivery target` |
| `checks` | `Python checks` |
| `security` | `Audit runtime dependencies` |
| `portability` | `Python on ubuntu-24.04`, `Python on macos-15`, `Python on windows-2025` |
| `container` | `Build and smoke test Docker` |
| `publish` | `Publish tested image to GHCR` |

Для успешного push в `main` или выбранного `vX.Y.Z` должны завершиться
все шесть заданий; `portability` — это три запуска, по одному на ОС.
В историческом подтверждённом запуске `061c2a7` заданий было четыре.
Для PR и ручного запуска `publish` имеет ожидаемый статус `Skipped`.

Открой задание и раскрой шаг с командой. В его логе видны сообщения Ruff,
результат Pytest, вывод сборки Docker и результат HTTP-проверки.
В разделе `Artifacts` сохраняются:

| Артефакт | Когда появляется | Содержимое | Срок хранения |
| --- | --- | --- | --- |
| `coverage-report` | После Pytest с покрытием, если отчёты созданы; включая ошибку порога | `reports/coverage.xml`, `reports/coverage.json` и `reports/coverage-html/` | 7 дней |
| `pytest-report` | После Pytest, если он создал файл отчёта; включая упавшие тесты | `reports/pytest.xml`, отчёт JUnit XML | 7 дней |
| `evaluation-report` | После оценок, если отчёт создан; включая нарушение порога | `reports/evaluations.json` с метриками, каждым вопросом и сценарием | 7 дней |
| `dependency-audit` | Шаг запускается всегда, включая найденную уязвимость; при ранней ошибке файлы могут отсутствовать | `runtime-requirements.txt` с hashes и `pip-audit.json`, когда он создан | 7 дней |
| `image-scan` | После сканирования, включая найденную уязвимость | `reports/image-scan/*.json` — отчёт Trivy по образам API и UI | 7 дней |
| `sbom` | После сборки четырёх образов, включая найденную уязвимость | `reports/sbom/*.cdx.json` — SBOM CycloneDX API и UI для amd64 и arm64 | 30 дней |
| `tested-docker-images` | После успешного container, на push main или version-тега | `tested-images.tar` с API/UI и `tested-images.json` с commit и обоими ID | 1 день |

Архив образа передаёт сборку между заданиями; его также можно скачать для
разбора. Истечение срока хранения артефакта не удаляет опубликованный образ
из GHCR. Однако поздний повтор только задания `publish` может не сработать
после удаления архива. Для main можно повторить полный workflow.
Для частично опубликованного релиза пересборка может изменить ID: выбери
новую версию либо используй прежний артефакт, как описано в [RELEASES.md](RELEASES.md).

Если задание упало, найди **первый шаг с ошибкой**. Последующие задания со
статусом `Skipped` часто являются следствием этой ошибки, а не отдельной проблемой.

В меню завершившегося запуска GitHub доступен повторный запуск:
`Re-run failed jobs` или `Re-run all jobs`. Повторный запуск исходного события
`push` в `main` при успехе снова выполнит публикацию. Отдельная кнопка
`Run workflow` создаёт новое событие `workflow_dispatch`, для которого
публикация отключена. Для release-тегов повтор failed job с прежним
артефактом идемпотентен; повтор всех jobs может потребовать нового номера.

## 9. Как выполнить проверки локально

### Проверить Python-код и настоящую PostgreSQL

Команды выполняются из корня проекта:

```bash
uv sync --locked
cp -n .env.example .env
docker compose --profile test up --detach --wait db-test qdrant-test
export TEST_DATABASE_URL='postgresql+psycopg://support:support_ci@127.0.0.1:5434/ai_support_test'
export TEST_QDRANT_URL='http://127.0.0.1:6336'
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest -v
unset TEST_DATABASE_URL TEST_QDRANT_URL
docker compose --profile test stop db-test qdrant-test
```

`cp -n` сохраняет существующий `.env`. Без явного `TEST_DATABASE_URL` локально
интеграционные тесты пропускаются: такой запуск не подтверждает исправность БД.
Разрешены только отдельные тестовые базы с именем, оканчивающимся на `_test`.
Тесты выполняют `downgrade/upgrade`, поэтому адрес development-БД запрещён.
В CI переменная задана обязательно; автоматический пропуск исключён.

Если Ruff сообщает о форматировании, выполни `uv run --locked ruff format .`
и посмотри `git diff`. При изменении зависимостей отдельно выполни `uv lock`
и `uv sync --locked`; в коммит входят `pyproject.toml` и `uv.lock`.

Чтобы получить более новые версии, сдвинь `exclude-newer` в `pyproject.toml`
на дату не ближе 14 дней к текущей, затем выполни `uv lock` и проверку возраста:

```bash
uv lock
uv run --locked python scripts/check_dependency_age.py --min-age-days 14
```

Скрипт читает даты публикации из `uv.lock` и называет каждый слишком свежий
пакет. Сеть ему не нужна.

### Собрать и запустить полный стенд

Запусти Docker Desktop, затем:

```bash
docker version
cp -n .env.example .env
docker compose up --build --detach --wait api
docker compose exec -T api python -m app.knowledge.ingest
export API_TOKEN="$(docker compose exec -T api python -m app.tokens issue \
  --email admin@example.com --name 'Administrator' --role admin)"
uv run --locked python scripts/smoke_test.py \
  --base-url http://127.0.0.1:8001 --timeout 30 --check-review
docker compose exec -T api python -m alembic check
```

Compose ждёт PostgreSQL и Qdrant, выполняет миграции и после этого запускает API.
Локальный API доступен на порту 8001, PostgreSQL — на 5433, Qdrant — на 6335;
внутри сети Compose адреса — `db:5432` и `qdrant:6333`. Индексация явная:
без неё `--check-agent` остановится с просьбой выполнить `ingest`. Настройки, команды и типичные ошибки разобраны
в [инструкции этапа 02](STAGE_02.md).

В браузере:

- [Процесс API](http://127.0.0.1:8001/health).
- [Готовность БД и схемы](http://127.0.0.1:8001/ready).
- [Документация API](http://127.0.0.1:8001/docs).

Повтори проверку постоянного тома из CI:

```bash
docker compose exec -T api python -m app.db.demo seed > /tmp/ai-support-before.json
docker compose down
docker compose up --detach --no-build --wait api
docker compose exec -T api python -m app.db.demo show > /tmp/ai-support-after.json
cmp /tmp/ai-support-before.json /tmp/ai-support-after.json
```

`cmp` без вывода и с кодом 0 означает, что снимки совпали. Между записью
и чтением контейнеры были удалены; том сохранился. Обычная остановка:

```bash
docker compose logs --tail 100 api migrate db
docker compose down
```

`down --volumes` удаляет данные development-БД, поэтому в обычной инструкции
остановки этот ключ не используется.

## 10. Как скачать опубликованный образ

После успешного `publish`:

```bash
export APP_IMAGE=ghcr.io/merkertg/ai-support-agent:latest
export UI_IMAGE=ghcr.io/merkertg/ai-support-agent-ui:latest
docker compose pull api ui
docker compose up --detach --no-build --wait --wait-timeout 180 ui
```

Если пакет закрытый, сначала войди в GHCR с GitHub-аккаунтом, у которого есть
доступ к пакету. Для локального входа используется **personal access token
(classic)** с правом `read:packages`. Передай токен в скрытый ввод или через
`--password-stdin`; не добавляй его в команду, сохраняемую в истории терминала.

Простой вариант — интерактивный вход:

```bash
docker login ghcr.io --username merkertg
```

В поле пароля вставь PAT. Это пароль для локального клиента Docker;
CI использует автоматически созданный `GITHUB_TOKEN`.
Не помещай PAT в `.github/workflows/ci.yml`, `.env`, Dockerfile или Git.

Чтобы запустить конкретный коммит, скопируй SHA этого коммита из GitHub
и замени `<полный SHA коммита>` в примере на реальное значение:

```text
ghcr.io/merkertg/ai-support-agent:sha-<полный SHA коммита>
```

Перед запуском нужен `.env`, как в разделе 9. Compose использует опубликованный
образ и для миграций, и для API. Проверка, логи и остановка — те же команды
Compose, что для локального стенда. Для возврата к локальному образу выполни
`unset APP_IMAGE UI_IMAGE` и
`docker compose up --build --detach --wait --wait-timeout 180 ui`.

Опубликованные теги содержат образы для `linux/amd64` и `linux/arm64`:
Docker сам скачивает подходящую архитектуру, поэтому на Mac с Apple Silicon
и ARM-ноутбуках образ из GHCR работает без эмуляции. Оба варианта собраны
из одних Dockerfile и `uv.lock`; arm64 собирается в CI под QEMU и проверяется
на архитектуру `aarch64`, пользователя, состав и ответы `/health` API и UI.
Архитектура запущенного API: `docker compose exec api uname -m`
(`aarch64` или `x86_64`). Конкретную архитектуру выбирает тег с суффиксом,
например `sha-<полный SHA коммита>-amd64`.

## 11. Что делать, если pipeline красный

| Ошибка или симптом | Как проверить и исправить |
| --- | --- |
| Actions не появился после commit | Выполни `git push`; убедись, что обновилась `main` или есть PR в `main`, workflow находится в `.github/workflows/`, Actions разрешены. |
| `uv sync --locked` сообщает об устаревшем lock-файле | Проверь изменение `pyproject.toml`, локально выполни `uv lock`, проверь diff и включи `uv.lock` в коммит. |
| Ruff сообщает о нарушениях | Выполни ту же команду локально; исправь указанные строки. Для форматирования используй `ruff format .`. |
| Тест упал | Прочитай traceback и условие `assert`, воспроизведи через `uv run --locked pytest`, исправь код или контракт теста. |
| `Coverage failure: total of … is less than fail-under=85` при зелёных тестах | Посмотри таблицу покрытия: файл с 0%, который должен быть исключён, означает неверный шаблон `omit`. Шаблоны вида `*/путь` не зависят от рабочей папки дочерних процессов. |
| Упала только одна ОС в `portability` | Открой её журнал: чаще всего это кодировка (нужен `encoding="utf-8"`), разделитель пути или CRLF. Повтори на своём компьютере `uv run --locked pytest --ignore=tests/integration`. |
| Миграция или `alembic check` упали | Открой первый ошибочный SQL/traceback; проверь миграции и metadata. Не меняй уже применённую версию без новой миграции. |
| PostgreSQL или `/ready` не готовы | Проверь Compose-логи `db` и `migrate`, адрес БД, пароль и текущую версию Alembic. |
| Проверка сохранности не прошла | Проверь `postgres_data` и mount `/var/lib/postgresql/data`. Не добавляй повторный seed после пересоздания контейнеров. |
| Не собирается Docker | Открой первый неуспешный шаг `docker build`; проверь имя копируемого файла, lock-файл и доступ к базовому образу. |
| Smoke-проверка не дождалась сервиса | Посмотри `docker logs`; API должен слушать `0.0.0.0:8000` внутри контейнера. При проверке снаружи нужен проброс порта. |
| Smoke-проверка получила неожиданный JSON | Сверь ответ `/health` с контрактом; при согласованном изменении API обнови тесты и smoke-проверку. |
| `denied`, `unauthorized`, `permission_denied` в `publish` | Проверь `packages: write`, доступ репозитория к пакету и ограничивающие настройки организации. Не вставляй PAT в код для обхода ошибки. |
| `publish` имеет статус `Skipped` | Для PR и ручного запуска это ожидаемо; для push в `main` проверь, прошли ли предыдущие задания. |
| `docker pull` локально сообщает об отсутствии доступа | Убедись, что пакет уже опубликован, проверь его видимость и локальный `docker login` с правом `read:packages`. |
| `Нет корректного SBOM` / `SBOM … не относится к проверенному` в `publish` | Проверь шаг `Generate SBOM for tested images` и артефакт `sbom` этого запуска. Публикация не начиналась. |
| `cosign sign` не получил OIDC-токен | Проверь `id-token: write` у `publish`. Образы уже в GHCR: `Re-run failed jobs` пропустит совпавшие теги и повторит подпись. |
| Ошибка `cosign verify` в `publish` | Подпись не совпала с identity `ci.yml@<ref>`, issuer или SHA commit; не публикуй такой digest как проверенный. |
| Очистка GHCR: HTTP 403 | У репозитория нет роли Admin в `Manage Actions access` пакета; job остановился до удаления. |
| `port is already allocated` | Порт занят другим контейнером или Uvicorn; останови старый процесс либо выбери 8001. |
| `Conflict. The container name ... is already in use` | Проверь `docker ps -a`; удали старый учебный контейнер с этим именем или выбери другое имя. |
| `Cannot connect to the Docker daemon` | Запусти Docker Desktop и дождись готовности Docker. |

Если не прошёл `checks`, контейнер и публикация не запускаются.
Если не прошёл `container`, публикация не запускается.
Если публикация завершилась ошибкой, предыдущий опубликованный образ остаётся
в реестре; исправление кода не появляется там автоматически без успешной публикации.
Если при публикации нескольких тегов сеть прервалась, проверь каждый тег:
запись двух тегов не является одной атомарной операцией.

## 12. Как запретить merge с ошибками: необязательная настройка GitHub

Workflow проверяет изменения и сообщает результат. Сам по себе файл workflow
не включает правила защиты ветки на GitHub.

После первого успешного запуска владелец репозитория может настроить
`Settings → Rules → Rulesets` либо правила защиты ветки, доступные для его
тарифа и типа репозитория:

1. Выбрать ветку `main`.
2. Включить требование успешных status checks перед merge.
3. Добавить проверки `Validate delivery target`, `Python checks`, `Audit runtime dependencies`
   и `Build and smoke test Docker`
   с именами, показанными в интерфейсе завершившегося PR-запуска.
4. При необходимости требовать PR перед обновлением `main`.

Публикацию `publish` не нужно делать обязательной PR-проверкой: на PR она
намеренно пропускается. Требовать стоит проверки кода и контейнера.
Эта инструкция описывает ручную настройку владельца; она не утверждает,
что защита ветки уже включена.

## 13. Как pipeline будет проверять будущие этапы проекта

Реализованы все десять учебных этапов. С этапов 08–10 pipeline также
выполняет автономные оценки поиска и безопасности агента, собирает и проверяет
отдельный образ интерфейса и прогоняет демонстрационный сценарий.
Сейчас публикация охватывает оба пакета, полный CI применяется и к
выбранным release-тегам, а покрытие кода должно быть не ниже 85%.

Когда появится новая возможность, добавляй проверку вместе с её реализацией:

| Будущая возможность | Что добавить в CI |
| --- | --- |
| Реальные эмбеддинги или модель | Отдельный ручной job с секретом и лимитом расходов; тот же набор `evaluations/` и отчёт о стоимости. |
| Реальное развёртывание | Отдельное задание после `publish`, конфигурацию выбранной площадки и проверку работающего сервиса. |

Быстрые тесты Python удобно добавлять в `tests/`: текущая команда `pytest`
их подхватит. Если тестам понадобятся БД, отдельные инструменты или новое
окружение, измени workflow и зависимости явно. Платный прогон OpenAI выполняется
отдельно после настройки ключа и доступной модели; текущие проверки используют
mock и подменённый SDK-транспорт и не требуют LLM-ключей.

После изменения контракта API синхронно обновляй `app/`, `tests/` и
`scripts/smoke_test.py`. Например, переименование `/health` без обновления
проверки остановит публикацию — это ожидаемое поведение.

## 14. Как понять, что настройка полностью заработала

Есть три отдельных подтверждения:

1. **Локальная проверка:** Ruff и Pytest проходят; если доступен Docker,
   образ собирается, запускается и проходит smoke-проверку.
2. **GitHub CI:** после push или PR во вкладке Actions успешно закончились
   `checks`, `security` и `container`.
3. **Доставка образа:** после push в `main` успешно закончился `publish`,
   в GHCR появился SHA-тег коммита; для актуальной вершины `main` также
   обновился `latest`. Образ скачивается и запускается.

Наличие файлов в репозитории подтверждает настройку pipeline, но не заменяет
первый настоящий прогон на GitHub. Оценивай результат по логам конкретного
запуска и наличию пакета в GHCR.

Историческая проверка первоначального CI/CD этапа 01 (2026-10-17):

- Полный набор: **16 тестов прошли**, осталось одно предупреждение совместимости Starlette/HTTPX.
- Ruff проверил код и форматирование без ошибок.
- Docker-образ собран на этом Mac для `linux/arm64`, запущен и прошёл три HTTP-проверки.
- Внутри контейнера подтверждены UID 10001 и отсутствие Pytest/Ruff.
- Экспорт и загрузка через `docker save` / `docker load` сохранили ID проверенного образа.

У actionlint 1.7.12 есть известное ограничение: он ещё не распознаёт ключ
`queue: max`, уже описанный в официальной документации GitHub. Этот параметр

## 16. Как обновляются зависимости

Отдельный workflow `.github/workflows/dependency-updates.yml` по расписанию
или вручную готовит обновление Python-зависимостей. Выпуски моложе 14 дней
по-прежнему запрещены; uv зафиксирован на 0.12.23. Подготовка изменений
отделена от задания, которому разрешено создать или обновить pull request.
Обновления не объединяются автоматически: человек оценивает diff,
результаты тестов, покрытия, аудита и контейнерного сценария.

Изменение PR через `GITHUB_TOKEN` само по себе не запускает следующий CI.
Поэтому workflow явно запрашивает `workflow_dispatch` для доверенной ветки
обновления; это событие проходит обычные gates без публикации образов.
После одобрения и merge в `main` запускается обычный main CI/CD.
Подробности прав, ветки и ручного повторения находятся в
[DEPENDENCY_UPDATES.md](DEPENDENCY_UPDATES.md).

## 17. Как очищаются старые SHA-образы в GHCR

Каждый push в `main` добавляет в каждый пакет три тега (`sha-<SHA>`,
`sha-<SHA>-amd64`, `sha-<SHA>-arm64`), а подписи и SBOM — ещё несколько
версий. Без очистки пакеты растут бесконечно. Workflow
`.github/workflows/ghcr-cleanup.yml` запускается по воскресеньям в 04:23 UTC
и вручную (`Actions → Clean up old GHCR SHA images → Run workflow`).

```text
plan (packages: read): версии обоих пакетов → manifest и подписи → план, сводка, артефакт
        │ только при отметке delete или GHCR_CLEANUP_DELETE=true
        ▼
delete (packages: write, очередь ghcr-delivery): план заново → удаление по одной версии
```

Как `scripts/ghcr_cleanup.py` выбирает версии:

1. Через REST API GitHub читает все версии пакета: digest, теги, даты.
2. Версия со всеми тегами вида `sha-<40 hex>`, `…-amd64`, `…-arm64` — SHA-версия.
   Она старая, если не менялась дольше срока (по умолчанию 30 дней;
   добавление тега обновляет дату). Версия с `latest`, `vX.Y.Z`, `vX.Y.Z-amd64`
   или любым другим тегом защищена.
3. От защищённых и свежих SHA-версий скрипт идёт по ссылкам: index → manifest
   архитектур и attestation BuildKit, образ → подписи и SBOM-attestation
   (теги `sha256-<hex>`, `.sig`, `.att` и поле `subject`). Всё найденное
   сохраняется. Сохраняются также связи всех версий, не относящихся к старым
   SHA: оставшийся index без тега не потеряет общий дочерний manifest.
   Сохраняемый OCI-артефакт сохраняет свой исходный образ из `subject`.
4. Удаляются старые SHA-версии и то, что достижимо только из них. Родитель
   index удаляется раньше дочернего manifest. Версии без тегов и связей
   скрипт не трогает. HTTP 404 перечисленного или связанного manifest,
   неизвестный формат, неверный index/subject и дубликаты ID/digest
   останавливают весь план: отсутствие сведений не доказывает отсутствие связей.
5. Сначала полностью строятся планы **обоих** пакетов. Перед первой DELETE
   повторно читаются полные списки версий API и UI; любое изменение требует
   нового запуска. Перед каждой DELETE дополнительно перечитывается её version ID
   и сравниваются digest, теги и дата со снимком. Изменённая версия не удаляется.

Удаления по умолчанию нет: job `plan` только показывает план в сводке
и в артефакте `ghcr-cleanup-plan` (30 дней). Чтобы удалить:

- разово — ручной запуск с отметкой `delete`;
- по расписанию — переменная репозитория `GHCR_CLEANUP_DELETE=true`
  (`Settings → Secrets and variables → Actions → Variables`).

Срок задаёт поле `days` ручного запуска или переменная `GHCR_CLEANUP_DAYS`;
допустимо от 1 до 3650 дней. Job `delete` стоит в той же очереди
`ghcr-delivery`, что и `publish`, и пересчитывает план непосредственно перед
удалением. Любая ошибка GitHub API или registry останавливает работу:
отсутствие ответа не считается разрешением удалить. API GitHub не даёт
атомарной транзакции между последним GET и DELETE. Общая очередь исключает
пересечение с публикациями этого проекта; внешние процессы с правом записи
в пакеты следует остановить на время удаления. Если ошибка возникла после
первой DELETE, уже удалённые версии не откатываются автоматически; их ID
остаются в журнале, восстановление выполняется через настройки пакета.
Очистка обращается только к версиям GHCR и не подключается к PostgreSQL,
Qdrant, Docker Compose или пользовательским данным приложения.

`GITHUB_TOKEN` может удалять версии, если у репозитория роль Admin в пакете.
Пакет, опубликованный этим репозиторием из Actions, получает её по умолчанию;
для пакета, созданного иначе, роль выдаётся в `Package settings → Manage
Actions access`. Удалённую версию можно восстановить в настройках пакета
в течение 30 дней. Пробный запуск на чужом форке или ветке не выполняется.

Локально план можно получить тем же скриптом с токеном `read:packages`
(без `--delete` он ничего не меняет):

```bash
read -r -s -p "GitHub token (read:packages): " GITHUB_TOKEN && echo
export GITHUB_TOKEN GITHUB_ACTOR=merkertg GITHUB_REPOSITORY=merkertg/ai-support-agent
uv run --locked python scripts/ghcr_cleanup.py --days 30 --output reports/ghcr-cleanup-plan.json
unset GITHUB_TOKEN
```
