# Этап 10. Упаковка и воспроизводимая демонстрация

Цель — дать другому человеку понятный путь от клонирования репозитория
до демонстрации: один локальный стенд, вымышленные данные, ожидающий проверки
черновик, решение сотрудника и проверяемые результаты CI/CD.

Этот этап опирается на [интерфейс оператора](STAGE_08.md),
[оценки агента](STAGE_09.md) и [настроенный CI/CD](CI_CD.md).
Короткий сценарий показа вынесен в [DEMO.md](DEMO.md). После этапа 10 API
получил токены сотрудников, роли и лимит изменений — см.
[раздел 9](#9-аутентификация-роли-и-лимит-изменений).

## 1. Что входит в поставку

| Артефакт | Назначение |
| --- | --- |
| `compose.yaml` | PostgreSQL, Qdrant, миграции, API и Streamlit UI. |
| `Dockerfile` | Образ API (цель по умолчанию) и отдельная цель `ui` из зафиксированного `uv.lock`; запуск без root. |
| `.github/workflows/ci.yml` | Проверки Python, документации, оценок и зависимостей; образы API и UI, демонстрационный сценарий; публикация проверенного образа API. |
| `scripts/demo_scenario.py` | Повторяемый HTTP-сценарий с отдельными вымышленными данными; работает от имени сотрудника токена `API_TOKEN`. |
| `app/tokens.py` | Команда `python -m app.tokens`: первый администратор, выдача, список и отзыв токенов. |
| `docs/DEMO.md` | Последовательность показа и признаки успешного результата. |
| `docs/guide/ai-support-agent-guide.pdf` | Наглядное руководство; инструкция пересборки рядом. |
| `docs/VERIFICATION.md` | Фактически выполненные проверки и их ограничения. |

CI/CD публикует оба проверенных образа в GHCR: API (`ghcr.io/merkertg/ai-support-agent`)
и UI (`ghcr.io/merkertg/ai-support-agent-ui`) — после push в `main` или выбранного
тега версии. Каждый тег содержит образы для amd64 и arm64; Docker скачивает
образ своей архитектуры, на Apple Silicon — без эмуляции. Подробности — в [RELEASES.md](RELEASES.md). Автоматический
деплой на внешний сервер не задан: ранее выбранный объём CD — контейнерные
образы. Имя, теги и точный порядок заданий описаны в [CI_CD.md](CI_CD.md).

## 2. Подготовить стенд

Нужны Docker Desktop/Engine с Compose и Python 3.12+ с `uv` для локальных
проверок. Подробные требования — в [быстром запуске](instructions/quickstart.md).

```bash
if [ ! -f .env ]; then
  cp .env.example .env
fi
uv sync --locked --group ui
docker compose up --build --detach --wait --wait-timeout 180 ui
docker compose exec -T api python -m app.knowledge.ingest
export API_TOKEN="$(docker compose exec -T api python -m app.tokens issue \
  --email demo-reviewer@example.com --name 'Учебный рецензент' --role reviewer)"
```

В PowerShell на Windows ([аналоги команд](instructions/windows.md)):

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
uv sync --locked --group ui
docker compose up --build --detach --wait --wait-timeout 180 ui
docker compose exec -T api python -m app.knowledge.ingest
$env:API_TOKEN = docker compose exec -T api python -m app.tokens issue `
  --email demo-reviewer@example.com --name 'Учебный рецензент' --role reviewer
```

Последняя команда создаёт учебного рецензента и печатает его токен один раз;
в БД хранится только SHA-256. Перед учебным проходом оставь
`LLM_PROVIDER=mock` и `EMBEDDING_PROVIDER=mock`. Ключ OpenAI не нужен.
Проверь [готовность API](http://127.0.0.1:8001/ready); статусы модели и базы
знаний (`/api/llm/status`, `/api/knowledge/status`) требуют токен — открой
[Swagger](http://127.0.0.1:8001/docs), нажми **Authorize** и вставь токен.

## 3. Создать данные и оставить решение человеку

```bash
uv run --locked python scripts/demo_scenario.py --url http://127.0.0.1:8001
```

В PowerShell на Windows ([аналоги команд](instructions/windows.md)):

```powershell
uv run --locked python scripts/demo_scenario.py --url http://127.0.0.1:8001
```

Команда делает следующее:

1. Читает токен из `API_TOKEN`; без него завершается до первого запроса.
   Токен передаётся только в заголовке `Authorization` и никогда не печатается.
2. Через GET проверяет готовность PostgreSQL и миграций, затем через
   `GET /api/auth/me` узнаёт сотрудника токена (`staff_id`) и его роль.
3. Через GET проверяет, что LLM и эмбеддинги используют `mock`, индекс знаний
   готов и в нём есть статьи. При нарушении завершает работу **до первого POST**.
4. Находит или создаёт вымышленного клиента `stage10-customer@example.com`.
5. Переиспользует продукт `techflow-server` либо создаёт его.
6. Находит или создаёт отдельную учебную активную лицензию без срока окончания.
   Ключ не включается в консольный JSON и сообщения ошибок.
7. Находит или создаёт отдельное обращение с темой
   `[Демо 10] Сервер не запускается после обновления`.
8. При отсутствии запусков анализирует обращение с подсказкой ключа лицензии.
   Если запуск уже есть, читает его вместо нового вызова агента.
9. Проверяет завершённый mock-запуск, пять успешных инструментов, действующую
   лицензию и маску ключа в трассе. Читает связанное состояние LangGraph.
10. Выводит идентификаторы и состояния в JSON. При первом успешном запуске
    предложение имеет `pending`, граф — `awaiting_review`.

Отдельного учебного сотрудника сценарий больше не создаёт: создавать
сотрудников может только администратор, а автором решений становится
сотрудник токена. Для подготовки и анализа хватает роли `operator`.

Структура вывода; числа ниже только объясняют поля и не являются фиксированными ID:

```json
{
  "customer_id": 11,
  "license_id": 14,
  "product_id": 13,
  "run_id": 16,
  "staff_id": 12,
  "suggestion_id": 17,
  "suggestion_status": "pending",
  "ticket_id": 15,
  "workflow_state": "awaiting_review"
}
```

На стенде с собственными данными первый запуск добавляет ровно по одной записи:
клиента, лицензию, обращение, запуск агента и предложение, а также строки
checkpoint LangGraph. Продукт `techflow-server` переиспользуется, если он уже
есть. Существующие записи не изменяются. До появления токенов команда так же
отработала на development-стенде 18.10.2026 (тогда она ещё создавала учебного
оператора): сравнение таблиц до и после показало только эти добавления.

После команды открой [UI](http://127.0.0.1:8502), вставь токен рецензента
в поле **Токен сотрудника**, затем открой `ticket_id` и `suggestion_id`. Дальше сотрудник самостоятельно проверяет
источники, исправляет текст и принимает решение. Сценарий показа — [DEMO.md](DEMO.md).

## 4. Что значит «повторяемый»

Последовательные запуски используют стабильные email, код продукта, ключ
учебной лицензии и точную тему тикета в области выбранного клиента и продукта.
Поиск идёт постранично, а не только по первым 20 записям. Удаление и перезапись
существующих записей отсутствуют.

Если предложение уже одобрено или отклонено через UI, команда покажет его
текущее состояние. Она не создаёт новый тикет, второй анализ или сообщение,
чтобы вернуть сцену к первоначальному виду. Для чистого повторного показа
используй отдельный учебный Compose-проект с отдельными томами.

Ограничения:

- Скрипт рассчитан на **последовательные** запуски. Одновременные запуски
  могут конфликтовать: у тем обращений в API нет уникального ключа.
- Для одного списка действует предел 100 страниц по 100 записей. При
  достижении предела сценарий останавливается вместо предположения, что записи нет.
- Если учебный тикет изменён, найдено несколько совпадений или несколько
  запусков, требуется ручная проверка. Скрипт не выбирает произвольный вариант.
- После `failed` или `running` нового анализа автоматически нет. Сначала
  разбери сохранённый запуск и состояние процесса.
- Сетевая ошибка POST не вызывает автоматического повтора. Запрос мог
  сохраниться; следующий **явный** запуск сначала ищет его результат.
- Стабильные адреса `stage10-…@example.com` зарезервированы этим сценарием
  для вымышленных данных. Не используй их для реальных клиентов.
- Решения прошлых запусков привязаны к сотруднику их токена. Если повторить
  `--verify-review` с токеном другого сотрудника, сценарий остановится:
  «рассмотрено с другим решением или сотрудником».

`app.db.demo seed/show` остаётся отдельной низкоуровневой проверкой сохранности
БД из этапа 02. Новый сценарий работает через API и не заменяет старую команду.

## 5. Явно проверить обе ветви решения

Этот режим принимает учебные решения автоматически, поэтому для проверки
он использует два **дополнительных** обращения. Основной тикет остаётся
ожидающим проверки человеком.

```bash
uv run --locked python scripts/demo_scenario.py \
  --url http://127.0.0.1:8001 --verify-review
```

В PowerShell на Windows ([аналоги команд](instructions/windows.md)):

```powershell
uv run --locked python scripts/demo_scenario.py `
  --url http://127.0.0.1:8001 --verify-review
```

Для тем с суффиксами `— approve` и `— reject` скрипт создаёт по одному анализу:

| Ветка | Проверяемый результат |
| --- | --- |
| `approve` | Предложение `approved`, автор — сотрудник токена (`staff_id`), ровно одно его сообщение с проверенным текстом, тикет `waiting_customer`, граф `delivered`. |
| `reject` | Предложение `rejected`, причина сохранена, сообщений нет, тикет `open`, граф `rejected`. |

Для `--verify-review` нужен токен роли `reviewer` или `admin`: с токеном
оператора сценарий остановится до первого POST. Повторный последовательный
запуск проверяет существующие решения через GET.
Повторного POST review или второй доставки нет. Если решение принял другой
сотрудник или выбрана противоположная ветвь, сценарий останавливается.
Внешний email не отправляется: доставка по-прежнему учебная, внутри БД.

## 6. Аргументы и ошибки

```bash
uv run --locked python scripts/demo_scenario.py --help
```

В PowerShell на Windows ([аналоги команд](instructions/windows.md)):

```powershell
uv run --locked python scripts/demo_scenario.py --help
```

| Аргумент | Значение |
| --- | --- |
| `--url` | Корень API; по умолчанию `http://127.0.0.1:8001`. Только HTTP(S), без credentials, пути и query. |
| `--timeout` | Общий тайм-аут от 1 до 600 секунд, по умолчанию 180. |
| `--verify-review` | Явная проверка двух отдельных ветвей согласования. |
| `API_TOKEN` (переменная окружения) | Токен сотрудника. Не аргумент: аргументы видны в списке процессов. |

Успех: JSON в stdout и код завершения `0`. Ошибка: понятная строка stderr
и код `1`. Ошибка аргументов: стандартная справка argparse и код `2`.
HTTP 401 подсказывает проверить `API_TOKEN`, 403 — роль токена, 429 —
подождать из-за лимита изменений. Логи не включают тело ошибочного
HTTP-ответа, лицензионный ключ, токен и адрес сервера.
Ответы ограничены 1 МиБ; перенаправления запрещены.

## 8. Что остаётся за пределами учебной поставки

Рабочая демонстрация не означает готовность публичного сервиса для реальных
клиентов. Токены, роли и лимит изменений уже есть (раздел 9). Перед реальной
эксплуатацией отдельно нужны корпоративный вход (SSO) поверх этих ролей,
TLS на внешнем адресе, общий лимит для нескольких реплик, реальные каналы
доставки с учётом повторов, резервное копирование и восстановление,
эксплуатационные лимиты и наблюдение.

Живые OpenAI-модели и эмбеддинги проверяются отдельно после предоставления
ключа и явного выбора провайдера. До этого результаты mock подтверждают
инженерный процесс и интеграции, а не качество ответов реальной модели.

## 9. Аутентификация, роли и лимит изменений

До этого дополнения любой, кто достучался до порта API, мог одобрить ответ
и отправить клиенту сообщение: автор решения брался из поля `reviewer_id`
тела запроса. Теперь каждый маршрут `/api/*` требует токен сотрудника
в заголовке `Authorization: Bearer <токен>`. Открыты только `/health`,
`/ready` и документация (`/docs`, `/redoc`, `/openapi.json`).

| Что | Как устроено |
| --- | --- |
| Токен | `asa_` и 43 символа base64url — 256 случайных бит из `secrets`. Показывается один раз при выдаче. |
| Хранение | Таблица `api_tokens` (миграция `0005_api_tokens`): SHA-256, подпись, префикс из 12 символов для списка, срок и время отзыва. Сам токен в БД не хранится. |
| Срок | По умолчанию 90 дней, от 1 до 365; бессрочных токенов нет. Отзыв действует со следующего запроса. |
| Роли | `operator` < `reviewer` < `admin`. Оператор читает данные, создаёт записи, запускает агента и ищет статьи; рецензент ещё и решает по предложениям; администратор ещё и управляет сотрудниками и токенами. |
| Автор решения | Берётся из токена. Поле `reviewer_id` в теле запрещено (422). Роль перечитывается из БД на каждый запрос и ещё раз под блокировкой решения. |
| Отказы | Нет, чужой, истёкший или отозванный токен, неактивный сотрудник — одинаковый 401 с `WWW-Authenticate: Bearer`; причина только в журнале (`auth_failed`). Недостаточная роль — 403. |
| Лимит | Каждое изменение (POST/PATCH/DELETE, включая поиск по базе знаний) берёт разрешение из «ведра» сотрудника: `WRITE_RATE_LIMIT_PER_MINUTE` (по умолчанию 60) в минуту. Превышение — 429 с `Retry-After`. Чтение не ограничено. |
| Журнал | Строка запроса содержит `user_id`. Токен и заголовок `Authorization` не записываются. |

Первый администратор создаётся командой в контейнере API — выдать первый токен
через API нельзя, ведь без токена API закрыт:

```bash
export API_TOKEN="$(docker compose exec -T api python -m app.tokens issue \
  --email admin@example.com --name 'Администратор' --role admin)"
docker compose exec -T api python -m app.tokens list --email admin@example.com
```

В PowerShell на Windows ([аналоги команд](instructions/windows.md)):

```powershell
$env:API_TOKEN = docker compose exec -T api python -m app.tokens issue `
  --email admin@example.com --name 'Администратор' --role admin
docker compose exec -T api python -m app.tokens list --email admin@example.com
```

Дальше администратор создаёт сотрудников с ролью (`POST /api/users`), выдаёт
им токены (`POST /api/users/{id}/tokens`), смотрит их список без секретов
и отзывает (`DELETE /api/tokens/{id}`). Примеры запросов — в
[инструкции по API](instructions/usage.md#authentication-roles-and-rate-limit).

Что изменилось вокруг API:

- **UI**: вместо поля «ID сотрудника» — скрытое поле «Токен сотрудника».
  Без токена страница не обращается к API. После входа видно имя и роль;
  форма решения показывается только рецензенту и администратору, создание
  сотрудников с выбором роли — только администратору. Токен живёт в сеансе
  браузера и не попадает в сообщения об ошибках.
- **Smoke-тест** читает токен из `API_TOKEN`. `--check-api` проверяет 401 без
  токена и `GET /api/auth/me`. `--check-review` (нужен admin) проверяет 401
  без токена, создаёт учебного оператора, выдаёт ему токен, получает 403,
  отзывает токен, получает 401 и только потом одобряет ответ от своего имени.
- **Демо** работает от имени сотрудника токена и выводит `staff_id`.
- **CI** в задании `container` выдаёт суточный токен администратора командой
  `python -m app.tokens issue`, маскирует его и передаёт smoke, демо и AppTest
  через `API_TOKEN`. Шаг журнала проверяет `user_id`, событие `auth_failed`
  и отсутствие строк вида токена. `check_local_start.py` проверяет 401 без
  токена на настоящем Uvicorn без БД.

Ограничения: лимит хранится в памяти одного процесса API и сбрасывается при
перезапуске; при нескольких процессах или репликах общий лимит нужно вынести
в шлюз или Redis. Токен передаётся по HTTP внутри локального стенда; на внешнем
адресе нужен TLS. Корпоративный вход (OIDC/SSO) и самостоятельная смена токена
сотрудником не реализованы.
