## 2. Исправления, найденные при проверке

### Сохранённый результат и checkpoint могут разойтись

Результат анализа или решение сотрудника сохраняется в предметных таблицах
PostgreSQL. LangGraph затем записывает своё состояние через checkpointer.
Если в этот момент хранилище checkpoint откажет, предметная транзакция уже
может быть завершена. Раньше удаление потока при ошибке анализа или потерянный
checkpoint решения мешали дальнейшей работе с таким запуском.

Теперь источником фактов служат `AgentRun` и `AgentSuggestion`. Чтение
`GET /api/agent-runs/{id}/workflow` при необходимости восстанавливает checkpoint
под той же advisory-блокировкой, что используется при рассмотрении предложения.
Запрос решения также восстанавливает ожидание перед продолжением процесса.
Восстановление не вызывает модель и не создаёт повторное сообщение.
Несовпадение идентификаторов запуска, обращения, предложения или потока
отклоняется. Уже принятое решение по-прежнему получает `409` при повторе.

Ошибка HTTP после сохранения данных не означает их откат. Если запрос анализа
завершился ошибкой хранилища, сначала проверь очередь
`GET /api/suggestions?status=pending&ticket_id=<id>` и существующий запуск.
Не повторяй анализ вслепую: после этапов 08–10 сервер отвечает `409`, пока
предыдущий анализ идёт или его предложение ждёт решения.

Отказы драйвера psycopg и ожидания пула checkpointer преобразуются в безопасный
`503`; адрес подключения и текст внутреннего исключения в ответ не попадают.

### Область продукта и общие статьи

Значение `general` раньше принималось как код продукта и попадало в общую
область поиска Qdrant. Статья такого продукта могла находиться для другого
продукта. Теперь общий валидатор `ProductCode` отвергает это служебное значение
в API и метаданных Markdown ещё до индексации. Общая статья задаётся отсутствием
`product_code`; существующие статьи и формат индекса сохранены. Негативные тесты
проверяют HTTP 422 и отказ загрузки до открытия индекса/БД.

### Дополнительные барьеры CI/CD

В workflow четыре задания: **`checks` и `security` → `container` → `publish`**.
Новые проверки блокируют публикацию наравне с тестами приложения:

1. `actionlint` проверяет сам workflow; скачиваемый архив сверяется по SHA256.
   Для `queue: max` есть одно точечное исключение: используемый выпуск
   actionlint 1.7.12 ещё не знает это поле GitHub.
2. `scripts/check_project.py` проверяет комментарии и документацию. Bash-примеры
   разбираются без выполнения команд, внешние ссылки не открываются.
3. `pip-audit` проверяет runtime-зависимости из экспорта lock с хешами.
   Найденная уязвимость, ошибка сети или пропуск пакета приводят к ошибке job.
   Проверяемые пакеты при аудите не устанавливаются. Отчёт сохраняется даже при ошибке.
4. Проверка образа подтверждает UID/GID 10001 и отсутствие инструментов разработки.

Миграции, интеграционные тесты, сквозной smoke и продолжение отложенного процесса
после пересоздания контейнеров уже входили в pipeline и сохранены.
CD заканчивается публикацией в GHCR, как выбрал пользователь.

## 3. Как повторить полную проверку

В корне проекта установи зависимости и запусти отдельные тестовые сервисы:

```bash
uv sync --locked
uv run --locked python scripts/check_project.py
uv run --locked ruff check .
uv run --locked ruff format --check .
docker compose --profile test up --detach --wait db-test qdrant-test
CI=true \
TEST_DATABASE_URL='postgresql+psycopg://support:support_ci@127.0.0.1:5434/ai_support_test' \
TEST_QDRANT_URL='http://127.0.0.1:6336' \
LLM_PROVIDER=mock OPENAI_API_KEY='' OPENAI_MODEL='' EMBEDDING_PROVIDER=mock \
LANGSMITH_TRACING=false \
  uv run --locked pytest -v --junitxml=reports/pytest.xml
```

Полная проверка должна завершиться без `skipped`. Интеграционные фикстуры
пересоздают схему только явно указанной БД с суффиксом `_test`.
Остановка временных сервисов не удаляет development-тома:

```bash
docker compose --profile test stop db-test qdrant-test
```

Отдельно проверь работающий mock-стенд. Следующая команда создаёт учебные
записи, одобряет предложение и сохраняет сообщение в PostgreSQL:

```bash
uv run --locked python scripts/smoke_test.py \
  --base-url http://127.0.0.1:8001 --timeout 30 --check-review
```

Для читающей проверки без создания записей используй `--check-knowledge`.
Для контейнерного прогона и проверки сохранности томов используй
[подробную инструкцию CI/CD](CI_CD.md). Не выполняй `down --volumes`
для development-проекта, если нужны его данные.

## 8. Журнал ошибок и закреплённые образы

- `app/observability.py`: JSON-строка на событие в stdout, `request_id`
  в каждой строке и в заголовке ответа `X-Request-ID`. Чужой id принимается,
  только если состоит из безопасных символов.
- Записываются запросы (метод, путь без query string, код, длительность),
  ошибки ресурсов, БД (класс и SQLSTATE), LLM (класс, HTTP-код и id запроса
  провайдера из `__context__`), итоги запусков агента и восстановление checkpoint.
- Непредвиденное исключение: JSON 500 с id запроса, traceback только в журнале.
- Журнал доступа Uvicorn выключен (`--no-access-log`): он печатал query string,
  где бывает `license_key`. UI показывает «Код запроса для администратора».
- Найдено при проверке: `fileConfig` в `migrations/env.py` отключал журналы,
  созданные до миграции. Теперь `disable_existing_loggers=False`.

### Образы

- `python`, `uv`, `postgres`, `qdrant` и сканер закреплены по digest индекса
  во всех файлах; `tests/test_image_pins.py` проверяет это и единство digest.
- CI сканирует образы API и UI Trivy 0.75.0 (выпуск 01.10.2026), запущенным по
  digest без `trivy-action` (CVE-2026-33634). Блокируют HIGH/CRITICAL с
  исправлением. Сейчас: по 44 HIGH в базовом Debian 13.7 без исправления,
  **0 исправимых** в обоих образах.
- CI проверяет, что ключи лицензий smoke и демо не попали в журнал API.
