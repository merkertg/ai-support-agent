## 2. Исправления, найденные при проверке

### Сохранённый результат и checkpoint могут разойтись

Результат анализа или решение сотрудника сохраняется в предметных таблицах
PostgreSQL. LangGraph затем записывает своё состояние через checkpointer.
Если в этот момент хранилище checkpoint откажет, предметная транзакция уже
может быть завершена. Раньше удаление потока при ошибке анализа или потерянный
checkpoint решения мешали дальнейшей работе с таким запуском.

Теперь источником фактов служат `AgentRun` и `AgentSuggestion`. Чтение
`GET /api/agent-runs/{id}/workflow` при необходимости восстанавливает checkpoint
под той же advisory-блокировкой, что используется при рассмотрении предложения.
Запрос решения также восстанавливает ожидание перед продолжением процесса.
Восстановление не вызывает модель и не создаёт повторное сообщение.
Несовпадение идентификаторов запуска, обращения, предложения или потока
отклоняется. Уже принятое решение по-прежнему получает `409` при повторе.

Ошибка HTTP после сохранения данных не означает их откат. Если запрос анализа
завершился ошибкой хранилища, сначала проверь очередь
`GET /api/suggestions?status=pending&ticket_id=<id>` и существующий запуск.
Не повторяй анализ вслепую: после этапов 08–10 сервер отвечает `409`, пока
предыдущий анализ идёт или его предложение ждёт решения.

Отказы драйвера psycopg и ожидания пула checkpointer преобразуются в безопасный
`503`; адрес подключения и текст внутреннего исключения в ответ не попадают.

### Область продукта и общие статьи

Значение `general` раньше принималось как код продукта и попадало в общую
область поиска Qdrant. Статья такого продукта могла находиться для другого
продукта. Теперь общий валидатор `ProductCode` отвергает это служебное значение
в API и метаданных Markdown ещё до индексации. Общая статья задаётся отсутствием
`product_code`; существующие статьи и формат индекса сохранены. Негативные тесты
проверяют HTTP 422 и отказ загрузки до открытия индекса/БД.

### Дополнительные барьеры CI/CD

В workflow четыре задания: **`checks` и `security` → `container` → `publish`**.
Новые проверки блокируют публикацию наравне с тестами приложения:

1. `actionlint` проверяет сам workflow; скачиваемый архив сверяется по SHA256.
   Для `queue: max` есть одно точечное исключение: используемый выпуск
   actionlint 1.7.12 ещё не знает это поле GitHub.
2. `scripts/check_project.py` проверяет комментарии и документацию. Bash-примеры
   разбираются без выполнения команд, внешние ссылки не открываются.
3. `pip-audit` проверяет runtime-зависимости из экспорта lock с хешами.
   Найденная уязвимость, ошибка сети или пропуск пакета приводят к ошибке job.
   Проверяемые пакеты при аудите не устанавливаются. Отчёт сохраняется даже при ошибке.
4. Проверка образа подтверждает UID/GID 10001 и отсутствие инструментов разработки.

Миграции, интеграционные тесты, сквозной smoke и продолжение отложенного процесса
после пересоздания контейнеров уже входили в pipeline и сохранены.
CD заканчивается публикацией в GHCR, как выбрал пользователь.

## 3. Как повторить полную проверку

В корне проекта установи зависимости и запусти отдельные тестовые сервисы:

```bash
uv sync --locked
uv run --locked python scripts/check_project.py
uv run --locked ruff check .
uv run --locked ruff format --check .
docker compose --profile test up --detach --wait db-test qdrant-test
CI=true \
TEST_DATABASE_URL='postgresql+psycopg://support:support_ci@127.0.0.1:5434/ai_support_test' \
TEST_QDRANT_URL='http://127.0.0.1:6336' \
LLM_PROVIDER=mock OPENAI_API_KEY='' OPENAI_MODEL='' EMBEDDING_PROVIDER=mock \
LANGSMITH_TRACING=false \
  uv run --locked pytest -v --junitxml=reports/pytest.xml
```

Полная проверка должна завершиться без `skipped`. Интеграционные фикстуры
пересоздают схему только явно указанной БД с суффиксом `_test`.
Остановка временных сервисов не удаляет development-тома:

```bash
docker compose --profile test stop db-test qdrant-test
```

Отдельно проверь работающий mock-стенд. Следующая команда создаёт учебные
записи, одобряет предложение и сохраняет сообщение в PostgreSQL:

```bash
uv run --locked python scripts/smoke_test.py \
  --base-url http://127.0.0.1:8001 --timeout 30 --check-review
```

Для читающей проверки без создания записей используй `--check-knowledge`.
Для контейнерного прогона и проверки сохранности томов используй
[подробную инструкцию CI/CD](CI_CD.md). Не выполняй `down --volumes`
для development-проекта, если нужны его данные.

В разделе 6 и в PDF было записано «пакеты не моложе двух недель». Это было

- В `pyproject.toml` добавлен `[tool.uv] exclude-newer = "2026-10-04T00:00:00Z"`.

### Брошенные запуски больше не остаются `running` навсегда

Добавлен [механизм recovery](RUN_RECOVERY.md). Он завершает `running`,
начавшийся не позднее чем 180 секунд назад: верхняя разрешённая длительность
агента 120 секунд плюс запас 60 секунд. Текущая настройка `.env` не уменьшает
эту границу после перезапуска другого worker. Время задаёт PostgreSQL.

Recovery работает под блокировкой перед новым анализом того же обращения
и фоновым проходом каждые 30 секунд, даже если к старому запуску больше никто
не обращается. Фоновую часть можно отключить `RUN_RECOVERY_ENABLED=false`;
проверка при новом анализе остаётся. По умолчанию монитор включён.

Условный SQL `UPDATE` меняет только старые `running` на `failed`, фиксирует
`finished_at` и безопасную ошибку, сохраняет доступный диагностический след.
Он не создаёт предложение и не выполняет доставку. `finish_run` теперь
блокирует строку и сохраняет результат только при `running`: поздний worker
не оживляет уже завершённый запуск. Завершённый `completed` и его предложение
не перезаписываются. Проверки охватывают точную границу 180 секунд,
уменьшение лимита после старта, идемпотентность, возврат соединений и реальную
гонку двух соединений PostgreSQL с ожиданием блокировки.

Таймер останавливается перед закрытием пула. SQL ограничен по времени;
ошибки БД дают безопасное событие журнала и следующую попытку. Общая фикстура
тестов отключает фоновый монитор, чтобы длительный `TestClient` не изменял
development-БД из локального `.env`; сами проверки recovery используют
подмены или явно выбранную PostgreSQL `_test`.

### Пять заданий и публикация проверенной пары API/UI

В [CI/CD](CI_CD.md) добавлен первый job **Validate delivery target**.
Текущая цепочка состоит из пяти заданий:

1. **Validate delivery target** — проверка цели доставки, формата release-тега
   и принадлежности commit истории `origin/main`.
2. **Python checks** — lock, возраст зависимостей, workflow, документация,
   миграции, Ruff, полный Pytest, покрытие и автономные оценки.
3. **Audit runtime dependencies** — независимый аудит точных зависимостей API/UI.
4. **Build and smoke test Docker** — после обоих предыдущих проверяющих заданий:
   сборка API/UI, состав образов, UID/GID, Trivy, HTTP, review, сохранность
   томов, восстановление процесса, UI и демонстрационный сценарий.
5. **Publish tested image to GHCR** — после успешных проверок: публикация
   именно экспортированной пары образов без повторной сборки.

Настройка доставки теперь охватывает `ghcr.io/merkertg/ai-support-agent`
и `ghcr.io/merkertg/ai-support-agent-ui`. Один артефакт содержит оба образа,
полный SHA исходного commit и оба image ID; после `docker load` ID проверяются
до публикации. Наличие настройки ещё не подтверждает появление нового пакета UI.

Для push в `main` используются SHA-теги и условное обновление `latest`.
Для явно выбранного человеком тега `vX.Y.Z` выполняется полный CI, после
которого публикуется версия обоих пакетов. До первого push проверяются
обе ссылки: существующая чужая версия блокирует доставку, идентичная
разрешает повторение того же артефакта. Выпуск не меняет `latest` и не
создаёт Git-тег или GitHub Release автоматически. Процедура, ограничения
registry и повтор частичного сбоя описаны в [RELEASES.md](RELEASES.md).

### Еженедельные обновления зависимостей через PR

Отдельный workflow **Update Python dependencies** подготавливает предложение
каждый понедельник в 06:17 UTC / 11:17 в Ташкенте либо по ручному запуску.
Он сдвигает только дату `exclude-newer`, обновляет `uv.lock` в существующих
ограничениях и проверяет четырнадцатидневное окно публикации.

Подготовка работает без write-прав и сборки пакетов. Отдельное задание

### Что ещё должен подтвердить GitHub и что делать пользователю

Новый удалённый запуск не подтверждён. Последняя попытка чтения закрытого
репозитория через подключённый API вернула HTTP `404`; это отсутствие
доступного результата, а не доказательство падения CI. Ранее пользователь
подтвердил все четыре зелёных задания только для `061c2a7` (раздел 4).
Это подтверждение не относится к `2d585fa` и последующим изменениям.

После push нового commit открыть GitHub → Actions → **CI and GHCR**:
проверить именно его SHA и результат **всех пяти заданий**. В сводке
публикации проверить две ссылки — API и UI — и digest каждого образа.
Сбой любого задания нужно разобрать по его логу; одного зелёного Pytest
для подтверждения полной доставки недостаточно.

Дальше можно работать через интерфейс оператора на mock: создать обращение,
запустить анализ, проверить источники и черновик, принять или отклонить
предложение. Это текущий выбор пользователя. Реальную модель, измерение
её качества/стоимости и внешнюю доставку подключают отдельным следующим
этапом после явной настройки; без ключа проект продолжает работать в mock.
Публикация GHCR сама по себе не развёртывает приложение на внешнем сервере.
