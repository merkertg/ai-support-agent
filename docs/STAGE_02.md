# Этап 02. PostgreSQL, модели данных и миграции

Эта инструкция ведёт от первого запуска базы до проверок в GitHub Actions. В ней объясняется, какую задачу
решает каждый файл, какие команды выполнять и как отличить работающий API от приложения, готового обращаться к
базе.

Документ относится к текущей версии файлов в репозитории. Конкретные результаты проверки этой итерации
записываются в [журнале разработки](DEVELOPMENT_LOG.md). Команда в инструкции описывает способ проверки;
успешный результат нужно подтвердить её выполнением.

## 1. Что должно получиться

После этапа 02 приложение получает PostgreSQL 17, постоянное хранилище, описание девяти таблиц через SQLAlchemy
и управление схемой через Alembic. Контейнер API начинает работу после готовности базы и применения миграций.

Простой учебный сценарий:

1. Запустить PostgreSQL.
2. Применить миграцию, которая создаёт таблицы.
3. Записать вымышленные данные клиента, продукта и лицензии.
4. Прочитать их отдельным запуском программы.
5. Пересоздать контейнер базы без удаления тома.
6. Снова прочитать ту же лицензию.
7. Запустить автоматические проверки.

Это проверяет главную задачу этапа: данные находятся в PostgreSQL и переживают перезапуск контейнеров.

API создания клиентов, лицензий и обращений относится к следующему этапу. Наличие таблицы ещё не даёт
HTTP-маршрут для работы с ней. Таблицы запусков агента и его предложений также пока являются схемой: вызовы LLM,
RAG и отправка ответов ещё не реализованы.

## 2. Как связаны компоненты

```text
.env / переменные окружения
             ↓
Settings → DATABASE_URL
             ↓
SQLAlchemy Engine → psycopg → PostgreSQL 17
             ↑
           Session
             ↑
     учебный demo-скрипт

Alembic → миграции → структура таблиц PostgreSQL

HTTP-клиент → FastAPI
                ├── /health → API обрабатывает запрос
                └── /ready  → SELECT 1 + версия схемы Alembic
```

| Компонент | Простое объяснение | Зачем нужен |
| --- | --- | --- |
| PostgreSQL | Отдельный сервер базы данных | Хранит записи между запусками приложения. |
| SQLAlchemy | Библиотека Python для SQL и объектов данных | Описывает таблицы и выполняет операции через Python. |
| psycopg | Драйвер PostgreSQL | Передаёт команды от Python в PostgreSQL. |
| Alembic | Инструмент изменения схемы | Создаёт и изменяет таблицы по сохранённым миграциям. |
| Pydantic Settings | Загрузка настроек | Читает переменные окружения и файл `.env`. |
| Docker Compose | Совместный запуск сервисов | Запускает базу, миграции и API с зависимостями. |
| Именованный том Docker | Хранилище вне файловой системы контейнера | Сохраняет данные PostgreSQL после пересоздания контейнера. |

## 4. Обновить Python-окружение

**Что делаем:** устанавливаем зависимости, зафиксированные в `uv.lock`.

**Зачем:** приложение, тесты и миграции должны использовать согласованные версии библиотек.

**Файлы:** `pyproject.toml` и `uv.lock`.

```bash
uv sync --locked
```

`--locked` проверяет, что lock-файл соответствует объявленным зависимостям. Если файлы расходятся, команда
завершается ошибкой и не выбирает произвольные новые версии молча.

Для этапа 02 нужны:

| Зависимость | Роль |
| --- | --- |
| `sqlalchemy` | Модели, соединения, SQL-запросы и сессии. |
| `psycopg[binary]` | Драйвер PostgreSQL 3 с готовыми бинарными компонентами. |
| `alembic` | Создание и применение миграций. |
| `pydantic-settings` | Настройки из переменных окружения и `.env`. |

В обычной работе после `git pull` используй `uv sync --locked`. Команда `uv lock` нужна при осознанном изменении
зависимостей, а не для исправления любой ошибки окружения. В lock попадают только выпуски старше двух недель:
`[tool.uv] exclude-newer` в `pyproject.toml` скрывает от uv более новые файлы PyPI, а CI проверяет даты
скриптом `scripts/check_dependency_age.py`.

Если меняешь список библиотек, проверяй и сохраняй в Git оба файла: `pyproject.toml` и `uv.lock`.

## 5. Создать локальный файл настроек

**Что делаем:** копируем пример настроек в локальный `.env`.

**Зачем:** параметры среды должны задаваться отдельно от Python-кода.

**Файлы:** `.env.example` — образец в Git; `.env` — локальные значения.

При первом запуске:

```bash
cp .env.example .env
```

Если `.env` уже существует, сначала открой его и сравни с `.env.example`. Повторное копирование перезапишет твои
локальные значения.

Открой пример и проверь названия параметров:

```bash
cat .env.example
```

Текущие значения для первого локального запуска:

```dotenv
POSTGRES_USER=support
POSTGRES_PASSWORD=local-development-only
POSTGRES_DB=ai_support
POSTGRES_PORT=5433
API_PORT=8001
POSTGRES_TEST_PORT=5434
DATABASE_URL=postgresql+psycopg://support:local-development-only@127.0.0.1:5433/ai_support
DATABASE_URL_DOCKER=postgresql+psycopg://support:local-development-only@db:5432/ai_support
```

`DATABASE_URL` читает Python на Mac. `DATABASE_URL_DOCKER` Compose передаёт в `api` и `migrate` как их
`DATABASE_URL`. Если меняешь пользователя, пароль, имя базы или порты, согласованно исправь соответствующие URL.
Compose не собирает URL из частей автоматически.

Пример предназначен для учебной локальной среды. Его пользователь и пароль демонстрационные. Для доступной извне
среды нужны отдельные настройки доступа и секреты.

`.env` исключён из Git. Проверить это можно так:

```bash
git check-ignore .env
```

Ожидаемый результат: Git выводит `.env`. Сам файл с локальными паролями не нужно добавлять через `git add -f`.

Настройки читаются приложением при первом получении объекта Settings. Если уже запущенный Uvicorn использует
старые значения, останови его и запусти снова после изменения `.env`.

`Settings` описывает поле `database_url`. Другие значения файла, например `POSTGRES_USER`,
использует Compose; `extra="ignore"` разрешает им находиться в том же `.env`,
не вызывая ошибку валидации настроек Python.

Переменная окружения процесса имеет приоритет над значением из `.env`. Если редактирование файла не меняет
поведение, проверь, не задана ли переменная раньше в терминале или конфигурации запуска.

## 6. Понять адрес подключения

Адрес базы имеет структуру:

```text
postgresql+psycopg://USER:PASSWORD@HOST:PORT/DATABASE
```

| Часть | Значение |
| --- | --- |
| `postgresql` | Тип СУБД. |
| `+psycopg` | Драйвер SQLAlchemy. |
| `USER` | Роль PostgreSQL, от которой подключается приложение. |
| `PASSWORD` | Пароль этой роли. |
| `HOST` | Адрес сервера базы с точки зрения текущего процесса. |
| `PORT` | Порт PostgreSQL с точки зрения этого процесса. |
| `DATABASE` | Имя конкретной базы внутри сервера. |

Точный локальный URL находится в `.env.example`. В контейнерах Compose имя хоста базы — `db`, порт — `5432`. На
Mac при запуске Python вне Docker используется `127.0.0.1:5433`. Точное значение внешнего порта задаётся
`POSTGRES_PORT`.

Это два адреса одного сервера из разных сред:

```text
Python на Mac → 127.0.0.1:внешний_порт → db:5432
API в Compose → db:5432
```

`localhost` внутри контейнера означает сам этот контейнер. API не найдёт отдельный контейнер PostgreSQL по
своему `localhost`.

Пароли с символами вроде `@`, `/` или `:` требуют корректного URL-кодирования при составлении строки вручную.
Для учебного запуска используй согласованные значения из примера, а при смене пароля меняй соответствующие
параметры вместе.

## 7. Запустить только PostgreSQL

**Что делаем:** сначала поднимаем базу отдельно от API.

**Зачем:** так проще увидеть последовательность и проверить подключение.

**Файл:** `compose.yaml`, сервис `db`.

```bash
docker compose up -d --wait db
docker compose ps
```

`-d` означает запуск в фоне. В списке сервисов должен появиться `db`. Через некоторое время healthcheck должен
показать `healthy`.

Healthcheck выполняет `pg_isready` внутри контейнера. Это проверка, что PostgreSQL принимает подключения. Она
ещё не означает, что таблицы нашего приложения уже созданы.

Посмотреть логи:

```bash
docker compose logs db
```

Если база инициализируется впервые, её логи содержат создание первоначальной базы и последующий запуск сервера.

Обычная остановка:

```bash
docker compose stop db
```

Повторный запуск:

```bash
docker compose start db
```

## 8. Разобраться с постоянным томом

В Compose данные PostgreSQL подключены к именованному тому. Том хранится Docker отдельно от конкретного
контейнера `db`.

```text
Контейнер db
    └── каталог данных PostgreSQL
             └── именованный том Docker
```

Команда `docker compose down` удаляет контейнеры и сеть проекта, но сохраняет именованный том по умолчанию.

```bash
docker compose down
docker compose up -d --wait db
```

После такого пересоздания таблицы и записи остаются в томе.

**Не добавляй `-v` при обычной остановке.** Команда `docker compose down -v` удаляет тома проекта вместе с
данными. Она подходит только для осознанного сброса одноразовой среды.

Переменные `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD` в официальном образе используются при первой
инициализации пустого каталога данных. Изменение `.env` не переименовывает существующую базу и не меняет пароль
в уже заполненном томе.

Если поменял пароль в файле и получил ошибку подключения, не удаляй том автоматически. Верни согласованные
значения либо выполни осознанное изменение роли в PostgreSQL. Сначала реши, нужны ли сохранённые данные.

## 9. Создать таблицы через Alembic

**Что делаем:** применяем миграции к базе.

**Зачем:** описания Python-моделей сами по себе не создают таблицы.

**Файлы:** `alembic.ini`, `migrations/env.py`, `migrations/versions/` и модели в `app/db/`.

После запуска `db`:

```bash
uv run --locked alembic upgrade head
```

`head` — последняя версия схемы в текущем коде. Alembic выполняет ещё не применённые миграции по порядку. На
новой базе первая миграция создаёт таблицы и ограничения.

Проверить состояние:

```bash
uv run --locked alembic current
uv run --locked alembic heads
```

Ожидаемый результат: применённая ревизия из `current` совпадает с вершиной из `heads`. После применения текущей
последней миграции возле ревизии может отображаться `(head)`.

Запусти ту же миграцию повторно:

```bash
uv run --locked alembic upgrade head
```

Уже применённая миграция не должна создавать таблицы второй раз. Alembic хранит текущее состояние в служебной
таблице `alembic_version`.

Проверить, не расходятся ли модели и миграции:

```bash
uv run --locked alembic check
```

Ожидаемый результат для согласованной схемы: новых операций для автогенерации не обнаружено.

Важно: `alembic check` использует настроенную базу. Сначала должны быть применены актуальные миграции.

## 10. Что делает миграция

Миграция — Python-файл с идентификатором ревизии и двумя направлениями изменений.

- `upgrade()` применяет изменения вперёд.
- `downgrade()` описывает обратное изменение.

Первая миграция этого проекта явно создаёт девять таблиц. Она фиксирует структуру на момент создания ревизии.
Она не вызывает `Base.metadata.create_all()` и не зависит от будущего содержимого изменяемых классов моделей.

Почему это важно: через несколько месяцев запуск старой миграции должен по-прежнему создавать именно её
историческую версию схемы.

`Base.metadata` — описание таблиц в Python-процессе. Сам импорт моделей ничего не меняет на сервере PostgreSQL.
Реальная схема меняется после выполненных SQL-команд, в этом проекте — после применения Alembic.

`alembic_version` появляется дополнительно к девяти предметным таблицам. Это служебная таблица инструмента, а не
десятая сущность продукта.

Миграции хранятся в Git вместе с моделями. Если добавить поле в класс и забыть миграцию, у разработчика и у CI
могут оказаться разные представления о схеме.

## 11. Какие таблицы добавлены

Названия классов и точные поля смотри в `app/models/entities.py`.

| Модель | Что хранит | Основная связь |
| --- | --- | --- |
| `User` | Профиль сотрудника: имя, email, роль, признак активности. | Автор сообщения оператора и рецензент предложения агента. |
| `Customer` | Организацию-клиента и контактные данные. | У клиента могут быть лицензии и обращения. |
| `Product` | Продукт, по которому оказывается поддержка. | Один продукт связан с лицензиями и документами базы знаний. |
| `License` | Номер, статус и срок лицензии. | Лицензия принадлежит клиенту и относится к продукту. |
| `Ticket` | Обращение в поддержку: тема, описание, статус и приоритет. | Обязательно относится к клиенту и продукту. |
| `TicketMessage` | Сообщение в истории обращения. | Всегда связано с конкретным обращением. |
| `KnowledgeDocument` | Метаданные документа и путь к Markdown-файлу. | Может относиться к продукту. |
| `AgentRun` | Запуск будущего агента и его состояние. | Связан с обращением. |
| `AgentSuggestion` | Предложение ответа, подготовленное в рамках запуска. | Связано с `AgentRun`. |

Это основа хранения данных. Она не реализует регистрацию, проверку пароля, авторизацию или работающий
AI-процесс.

`User.email` уникален, а `role` ограничена значениями `operator` и `admin`. Эти поля описывают профиль
сотрудника. Они пока не проверяют права доступа. Наличие роли в базе не означает готовой системы входа и
авторизации.

`KnowledgeDocument` описывает документ. Это ещё не чтение Markdown-файлов, разбиение текста на фрагменты,
вычисление embeddings или поиск в векторной базе.

Предложение агента связано с обращением через запуск:

```text
Ticket → AgentRun → AgentSuggestion
```

В `AgentSuggestion` не дублируется `ticket_id`: обращение уже определяется через `agent_run_id`. Это убирает
возможность записать предложение с запуском одного обращения и одновременно указать другое обращение в отдельном
поле.

## 12. Как читать поля модели

Пример формы объявления:

```python
id: Mapped[int] = mapped_column(primary_key=True)
```

| Часть | Что означает |
| --- | --- |
| `id` | Имя атрибута Python и колонки. |
| `Mapped[int]` | SQLAlchemy-атрибут со значением Python-типа `int`. |
| `mapped_column(...)` | Параметры соответствующей колонки базы. |
| `primary_key=True` | Колонка входит в первичный ключ таблицы. |

Этот фрагмент объясняет синтаксис. Точные объявления и дополнительные параметры смотри в текущих моделях.

Основные ограничения:

| Термин | Что проверяет | Пример смысла |
| --- | --- | --- |
| Primary key, PK | У каждой строки есть уникальный идентификатор. | Два клиента не получают одинаковый `id`. |
| Foreign key, FK | Связанная строка существует. | Лицензия не ссылается на несуществующего клиента. |
| Unique | Значение или набор значений не повторяется. | Два экземпляра лицензии не используют один номер. |
| Check | Значение удовлетворяет SQL-условию. | Статус входит в предусмотренный список. |
| Not null | Поле обязательно. | Нельзя сохранить обязательное имя как `NULL`. |
| Identity | База генерирует числовой идентификатор. | PostgreSQL выдаёт следующий `id` при вставке. |
| Timestamp | Временная отметка. | Время создания записи. |

`NULL` в SQL означает отсутствие значения. Это не пустая строка `""` и не число `0`.

Ограничения нужны и при работе через Python, и при прямых SQL-запросах. Они защищают данные независимо от
будущих HTTP-маршрутов.

При удалении связанных строк действуют разные правила:

- `RESTRICT` запрещает удаление родителя, пока существуют зависимые записи.
  Например, нельзя удалить клиента с лицензиями.
- `CASCADE` удаляет составные части вместе с родителем:
  сообщения и запуски принадлежат обращению, предложения принадлежат запуску.
- `SET NULL` сохраняет документ базы знаний после удаления продукта,
  убирая его необязательную ссылку на этот продукт.

`created_at` получает серверное время создания; используется тип `DateTime(timezone=True)`. Обновляемые поля
`updated_at` имеют `onupdate=func.now()` для UPDATE через SQLAlchemy. Это не серверный триггер: при прямом SQL
время изменения нужно передавать явно.

`ForeignKey(...)` описывает ограничение в базе. `relationship(...)` описывает удобный переход между объектами
Python. Один механизм не заменяет другой. В текущих моделях заданы внешние ключи; свойства `relationship()` пока
не объявлены. Связанные записи читаются явными запросами по идентификаторам.

## 13. Engine и Session

Это два разных уровня работы с базой.

`Engine` хранит настройки подключения и управляет пулом соединений. Он может переиспользовать существующие
соединения, чтобы не создавать новое сетевое подключение для каждой операции.

`Session` — короткая рабочая область операции Python. Она отслеживает добавленные и изменённые объекты и
выполняет действия в рамках транзакции.

```text
Один Engine приложения
     ├── Session операции A
     ├── Session операции B
     └── Session операции C
                ↓
       пул соединений
                ↓
           PostgreSQL
```

Сессию не нужно хранить как общий изменяемый объект для всех запросов. Её открывают для конкретной операции и
закрывают после завершения.

В этом проекте Engine создаётся лениво: импорт `app.main` не обязан немедленно подключаться к PostgreSQL. Это
позволяет выполнять быстрые тесты API без работающей базы.

Ограничение времени подключения не даёт бесконечно ждать недоступный сервер при проверке готовности.

## 14. Транзакция, commit и rollback

Транзакция объединяет связанные изменения в одну логическую операцию.

Представь: нужно создать клиента и его лицензию. Если запись лицензии не прошла, часто нужно отменить и создание
клиента, чтобы не оставить половину учебного сценария.

- `session.add(...)` сообщает сессии о новом объекте.
- `session.flush()` отправляет накопленные изменения в текущую транзакцию.
- `session.commit()` подтверждает изменения.
- `session.rollback()` отменяет неподтверждённую транзакцию.
- `session.close()` освобождает ресурсы сессии.

`flush()` позволяет получить сгенерированный `id` до завершения всей транзакции. Это не то же самое, что
окончательное сохранение через `commit()`.

В проекте подтверждение записи задаёт вызывающий код. Само получение сессии не должно незаметно подтверждать
изменения. В `demo.py` используется `with session.begin()`: успешный выход из этого явно открытого блока
подтверждает транзакцию, исключение откатывает её. В других операциях можно вызвать `session.commit()` напрямую.

При исключении вспомогательный код откатывает транзакцию. Закрытие выполняется и при успехе, и при ошибке.

После ошибки ограничения PostgreSQL текущая транзакция не готова к следующим обычным операциям, пока не выполнен
rollback. Продолжать запросы в сломанной транзакции нельзя.

## 18. Почему нужны /health и /ready

`GET /health` отвечает на простой вопрос: «Процесс API способен обработать HTTP-запрос?»

`GET /ready` отвечает на другой вопрос: «Этот экземпляр API может обращаться к нужной базе с ожидаемой текущим
кодом схемой?»

Проверка готовности выполняет:

1. Проверку наличия настройки подключения.
2. Простой запрос `SELECT 1` к PostgreSQL.
3. Сравнение применённых ревизий Alembic с вершинами миграций в коде.

Одна успешная команда `SELECT 1` не доказывает готовность схемы. База может принимать подключения, когда таблицы
приложения ещё не созданы. Поэтому проверяется и версия миграций.

`/ready` сверяет соединение и отметку версии. Он не выполняет полную проверку структуры всех таблиц
при каждом запросе. Расхождения структуры выявляют миграции, `alembic check` и интеграционные тесты.

| Состояние | /health | /ready |
| --- | --- | --- |
| API запущен, база и миграции готовы | `200` | `200` |
| API запущен, настройка базы отсутствует | `200` | `503` |
| API запущен, PostgreSQL недоступен | `200` | `503` |
| API запущен, миграции отстают или отличаются | `200` | `503` |
| Сам API не запущен | Нет HTTP-ответа | Нет HTTP-ответа |

`503 Service Unavailable` здесь — понятный сигнал о временной неготовности зависимости. Он не означает, что
пользовательский JSON некорректен.

Ответ не должен раскрывать пароль, полный URL базы или внутренний текст исключения драйвера.

## 19. Запустить весь проект через Compose

**Что делаем:** запускаем базу, одноразовое применение миграций и API.

**Зачем:** воспроизводим схему запуска в контейнерах.

```bash
docker compose up --build -d --wait api
docker compose ps -a
```

Порядок:

```text
db запускается
    ↓
db становится healthy
    ↓
migrate выполняет alembic upgrade head
    ↓
migrate завершается с кодом 0
    ↓
api запускается и отвечает на /ready
```

Контейнерный API по умолчанию доступен на порту **8001**:

- [Состояние API в Compose](http://127.0.0.1:8001/health).
- [Готовность API в Compose](http://127.0.0.1:8001/ready).
- [Документация API в Compose](http://127.0.0.1:8001/docs).

Порт 8000 из раздела локального Uvicorn и порт 8001 из Compose — два варианта запуска. Значение Compose меняется
через `API_PORT`.

`migrate` — одноразовый сервис. Его статус `Exited (0)` после успешного выполнения ожидаем. Он не должен
оставаться постоянно работающим сервером.

API и миграции используют тот же код и образ приложения. Это позволяет запускать именно те миграции, которые
соответствуют текущей контейнерной версии.

Логи по отдельности:

```bash
docker compose logs db
docker compose logs migrate
docker compose logs api
```

Поведение Compose зависит от конфигурации `depends_on`:

- Для базы используется условие успешного healthcheck.
- Для API требуется успешное завершение `migrate`.
- Healthcheck API использует готовность приложения.

Если миграция завершилась ошибкой, сначала разберись с ней. Просто повторять запуск API, игнорируя ошибку схемы,
бесполезно.

После изменения кода образ нужно пересобрать:

```bash
docker compose up --build -d --wait api
```

Остановка с сохранением базы:

```bash
docker compose down
```

## 21. Быстрые тесты без PostgreSQL

**Что делаем:** проверяем части кода, которым база не нужна.

**Зачем:** получать быстрый результат при редактировании приложения.

```bash
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest -m "not integration"
```

Ruff сначала проверяет правила кода, затем форматирование. Оба результата нужны: проверка стиля и форматирования
решает разные задачи.

Быстрые тесты могут использовать управляемые подмены настроек или проверки готовности. Это позволяет проверить
HTTP-коды и обработку ошибок без зависимости от работающего контейнера.

Успех быстрых тестов не подтверждает работу PostgreSQL. Для неё предназначены интеграционные проверки ниже.

## 22. Отдельная тестовая база

Интеграционный тест работает с настоящим сервером PostgreSQL, но с отдельной одноразовой базой.

У приложения и тестов разные переменные:

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | База локального приложения и демо-сценария. |
| `TEST_DATABASE_URL` | База только для интеграционных тестов. |

Имя тестовой базы обязано заканчиваться на `_test`. Защитная проверка помогает не направить очистку тестовых
данных в обычную базу по ошибке.

Сам суффикс не превращает важную базу в одноразовую: назначай тестам отдельную базу, в которой нет нужных
данных.

На сервере PostgreSQL сначала должна существовать сама тестовая база. Миграции создают таблицы внутри базы, а не
сервер и не всегда саму базу.

В Compose для этого есть сервис `db-test` с профилем `test`. Он запускает отдельный PostgreSQL 17 на порту 5434
и создаёт базу `ai_support_test` при инициализации. Его данные находятся в `tmpfs`: это одноразовое хранилище в
памяти, а не постоянный том development-базы. После остановки этого контейнера тестовые данные сохранять не
нужно.

Не подставляй обычный `DATABASE_URL` как тестовый только ради запуска всех проверок.

## 23. Запустить интеграционные тесты

Порядок работы:

1. Запустить PostgreSQL.
2. Подготовить отдельную базу с именем, оканчивающимся на `_test`.
3. Указать её адрес в `TEST_DATABASE_URL`.
4. Запустить интеграционные тесты.
5. Проверить, что они действительно выполнились, а не были пропущены.

Запусти только одноразовую тестовую базу:

```bash
docker compose --profile test up -d --wait db-test
```

Задай адрес в текущем терминале. Пароль ниже относится только к локальной одноразовой тестовой базе из Compose:

```bash
export TEST_DATABASE_URL='postgresql+psycopg://support:support_ci@127.0.0.1:5434/ai_support_test'
uv run --locked pytest -m integration -v
```

`export` действует для команд этого терминала и их дочерних процессов. В новом терминале переменную нужно задать
снова. Она специально не берётся из обычного `DATABASE_URL` как запасной вариант.

Для каждого интеграционного теста fixture применяет `downgrade base → upgrade head`, а после теста снова удаляет
схему. Так проверяется создание таблиц именно миграциями. Поэтому URL должен вести только в одноразовую `*_test`
базу. На GitHub отсутствие `TEST_DATABASE_URL` считается ошибкой.

Полный набор при настроенной тестовой базе:

```bash
uv run --locked pytest
```

Смотри не только на итоговый код возврата, но и на строки `passed`, `failed` и `skipped`. Без тестовой БД
интеграционные проверки могут быть пропущены. Это полезно для быстрого локального запуска, но не является
доказательством проверки хранения данных.

Текущие интеграционные тесты проверяют:

- `upgrade → downgrade → upgrade` и отсутствие расхождений с metadata;
- чтение сохранённых записей новой сессией;
- откат неподтверждённых изменений при закрытии сессии;
- уникальный email и невозможность ссылки на отсутствующего клиента;
- допустимые статусы, приоритеты и порядок дат;
- согласованность автора сообщения с идентификатором оператора;
- заполнение рецензента и времени при принятии или отклонении предложения;
- `RESTRICT`, `CASCADE`, `SET NULL` на связанных строках;
- настоящий `/ready` на мигрированной PostgreSQL.

Тесты не измеряют качество AI-ответов: работающего AI-агента пока нет.

Точный набор утверждений соответствует файлам тестов текущей версии; итог фактического запуска записан в журнале
разработки.

После проверки можно удалить только одноразовый тестовый контейнер:

```bash
docker compose --profile test stop db-test
docker compose --profile test rm -f db-test
unset TEST_DATABASE_URL
```

Эти команды не удаляют постоянный том сервиса `db`.

## 24. Что теперь проверяет GitHub Actions

Pipeline запускается после `push` в `main`, на PR в `main` и при ручном запуске.

```text
Python checks
  ├── uv sync --locked
  ├── Ruff
  ├── PostgreSQL 17
  ├── Alembic upgrade head
  ├── Alembic check
  └── Pytest с интеграционными тестами
             ↓
Build and smoke test Docker
  ├── сборка API-образа
  ├── PostgreSQL + migrate + API через Compose
  ├── HTTP-проверки, включая /ready
  ├── demo seed → down (сохранить том) → up → demo show → cmp
  └── сохранение проверенного образа
             ↓
Publish to GHCR
  └── только успешный push в main
```

CI поднимает собственную тестовую PostgreSQL. Она не обращается к базе на твоём Mac и не очищает её.
Контейнерное задание также создаёт изолированный Compose-проект `ai-support-ci`.
После записи демо оно выполняет `docker compose down` без удаления томов,
заново создаёт `db`, `migrate`, `api`, ждёт готовности и сравнивает JSON через `cmp`.
Между снимками не выполняется повторный `seed`.
Так проверяется сохранение данных после удаления и пересоздания контейнеров,
а не только перезапуск процесса PostgreSQL.
Завершающая очистка `down --volumes` в CI относится только к этому одноразовому проекту runner.

Если ошибка возникает в модели, миграции, подключении или контейнере, следующее задание публикации не должно
выпустить эту версию.

Образ для GHCR проходит проверки до публикации. Уже проверенный образ передаётся между заданиями; этап
публикации не должен незаметно собирать другой код заново.

Все существующие тесты запускаются на текущем проекте. Будущие этапы продукта нужно сопровождать новыми
проверками: CI не может доказать работу ещё не написанного AI-функционала.

Как открыть логи и скачать образ: [подробная инструкция CI/CD](CI_CD.md).

Локальный успех и успех на GitHub — отдельные факты. Без запуска Actions нельзя утверждать, что именно эта
версия прошла проверки на GitHub. Для этапа 02 такой запуск подтверждён — см. раздел 28 и
[журнал разработки](DEVELOPMENT_LOG.md).

## 25. Как добавлять следующую миграцию

Пример будущего изменения: у клиента появляется новое поле.

Рабочий порядок:

1. Изменить модель.
2. Убедиться, что текущая база обновлена до прежней вершины.
3. Сгенерировать черновик новой миграции.
4. Прочитать его и исправить вручную при необходимости.
5. Применить к одноразовой тестовой базе.
6. Проверить данные и тесты.
7. Сохранить модель и миграцию одним изменением в Git.

Команда создания черновика:

```bash
uv run --locked alembic revision --autogenerate -m "describe schema change"
```

`--autogenerate` сравнивает metadata моделей с реальной базой. Это помощник, который создаёт предлагаемые
операции.

Автогенерация не знает смысл бизнес-изменения. Например, переименование может выглядеть как удаление старой
колонки и создание новой. Без проверки это способно потерять данные.

Перед применением прочитай `upgrade()` и `downgrade()`, названия ограничений, nullable, типы и значения по
умолчанию.

После осознанного изменения:

```bash
uv run --locked alembic upgrade head
uv run --locked alembic check
```

Не исправляй уже разошедшуюся по средам старую миграцию ради нового поля: создавай следующую ревизию. Так
сохраняется воспроизводимая история изменений.

## 26. Проверка downgrade — только на одноразовой базе

Начальная миграция создаёт таблицы. Её `downgrade` удаляет их вместе с находящимися в них данными.

Это не команда ежедневной остановки приложения.

Пример проверки относится только к заранее созданной пустой или одноразовой базе с суффиксом `_test`. Сначала
явно проверь, какой URL будет использован. Повтори запуск `db-test` и `export TEST_DATABASE_URL` из раздела 23,
если уже остановил тестовую базу или открыл другой терминал.

```bash
DATABASE_URL="${TEST_DATABASE_URL:?Сначала укажи отдельную тестовую базу}" uv run --locked alembic upgrade head
DATABASE_URL="${TEST_DATABASE_URL:?Сначала укажи отдельную тестовую базу}" uv run --locked alembic downgrade base
DATABASE_URL="${TEST_DATABASE_URL:?Сначала укажи отдельную тестовую базу}" uv run --locked alembic upgrade head
```

Пара `downgrade/upgrade` проверяет обратимость структуры, но не гарантирует восстановление удалённых записей.
Для данных нужны резервные копии и отдельный план миграции.

Не выполняй эти команды с URL базы, в которой нужны данные.

## 27. Типичные ошибки

| Симптом | Причина и следующий шаг |
| --- | --- |
| `Cannot connect to the Docker daemon` | Запусти Docker Desktop и проверь `docker version`. |
| `port is already allocated` | Внешний порт занят; проверь работающие сервисы и измени внешний порт согласованно с URL локального приложения. |
| `connection refused` | База не запущена, не готова либо указан неверный адрес/порт; проверь `docker compose ps` и логи `db`. |
| `password authentication failed` | Пароль URL не совпадает с ролью в PostgreSQL; учти, что новый `.env` не меняет пароль в старом томе. |
| `database ... does not exist` | Указано другое имя базы либо тестовая база ещё не создана. |
| `relation ... does not exist` | Подключился к базе без миграций либо к другой базе; выполни `alembic current` и `upgrade head` для нужного URL. |
| `Target database is not up to date` | Сначала примени существующие миграции; только потом генерируй новые. |
| `alembic check` нашёл операции | Модели и схема расходятся; проверь применённую ревизию и необходимость новой миграции. |
| `/health` отвечает, `/ready` возвращает `503` | Процесс работает, но настройка базы, соединение или версия схемы не готовы. |
| `migrate` завершился с ненулевым кодом | Открой `docker compose logs migrate` и исправь первую ошибку миграции. |
| `migrate` имеет статус `Exited (0)` | Это успешное завершение одноразового сервиса, а не сбой. |
| Интеграционные тесты `skipped` | Не задан `TEST_DATABASE_URL`; настрой отдельную тестовую базу и повтори запуск. |
| Тесты отвергают имя базы | Используй действительно отдельную одноразовую базу с суффиксом `_test`. |
| Импорт новой библиотеки не найден | Выполни `uv sync --locked` в корне проекта и запускай команды через `uv run --locked`. |
| `UniqueViolation` / `IntegrityError` | Нарушено ограничение; проверь ключ/значение и выполняй rollback после ошибки транзакции. |
| Данные исчезли | Проверь имя Compose-проекта, используемый том и не выполнялся ли `down -v`; новый том выглядит как новая пустая база. |

Если API запущен в Compose, проверяй адрес базы внутри контейнера, а не только URL для Python на Mac.

При разборе ошибок не публикуй полный URL с паролем. Для обсуждения достаточно скрыть пароль и показать тип
ошибки, имя сервиса, порт и название шага.
